# 下载传输生命周期释放修复复盘（DownloadEngine 未释放 dio 连接池）

- 日期：2026-10-23
- 快照基准：`366c297`（改动前工作区干净，快照即 HEAD）
- 提交：`b9dd480`
- 范围：`lib/core/download/`（引擎 / 传输 / 队列）+ `test/core/download/`。**不含**生产接线（属批次4）。

---

## 一、现象与取证

用户指令：调查 `DownloadEngine` 从未调用 `transport.close()` 导致的 dio 实例 / 连接池泄漏。

静态取证：

1. 传输抽象声明了释放能力，但无人调用：`download_transport.dart:46` `void close();`，注释明写「引擎不负责调用生命周期，由持有方管理」；全局搜 `transport.close`：`lib/core/download` 下仅命中 `download_engine.dart:302/353` 两处 `raf.close()`（**关文件句柄**，非关传输）。`DownloadEngine` **无** `dispose`/`close` 方法。
2. dio 实现持有需释放的资源：`dio_download_transport.dart:17` 每实例 `Dio(...)`；`:122` `close() => _dio.close(force: true)` —— `close()` 是唯一释放点。
3. 持有方（队列）同样不关：`download_queue.dart:186` `engineFactory().download(...)`，`engineFactory` 语义为**每次下载新建** `DownloadEngine(transport: DioDownloadTransport())`（`:41` 注释）；`_run` 的 `finally`（`:205-209`）只清运行态标记；`dispose()`（`:163-166`）只置 `_disposed`。
4. 测试佐证契约被忽视：两个 Fake 的 `close()` 均为空实现，断言无 close 校验 —— 单测全绿也发现不了。
5. 对照组：`hls_manifest.dart:217`、`bilibili_url_parser.dart:234` 均为「`HttpClient` → `try/finally { close(force:true) }`」正确范式，说明团队有此纪律，仅下载链遗漏。

## 二、定因

不是「漏写一行 close」，而是**生命周期所有权在架构上被声明却无人认领**：

- 抽象层把 close 推给「持有方」；
- 引擎为保持对网络栈零硬依赖（利于离线单测）选择不自动 close —— 合理；
- 但唯一可能的持有方（队列调度器）**只负责编排、不持有传输实例**（每次经工厂丢弃），于是**没有任何一层承担释放职责**。

叠加「每次下载新建 Dio」的工厂语义，泄漏随下载次数线性累积。旁证：生产接线（`DownloadQueueCoordinator` 实例化）**尚未落地**（路线图归入批次4，全 `lib` 排除 `core/download` 对该类零引用），故当时是**潜在缺陷**，一旦接线即真实暴露。

## 三、方案（方案 A：所有权明确化，最小改动）

把 close 职责落到**队列**（而非让引擎自动 close），保持引擎对网络栈零依赖、既有单测语义不变：

1. `download_engine.dart`：新增幂等 `void dispose() { if (_disposed) return; _disposed = true; transport?.close(); }`（新增 `_disposed` 标志），**不改变 `download()` 语义**。
2. `dio_download_transport.dart`：`close()` 增加 `_closed` 幂等保护，避免重复 close。
3. `download_queue.dart`：`_run` 捕获本次 `final engine = engineFactory();`，改调 `engine.download(...)`，并在 `finally` 中 `engine.dispose();` —— **每次下载结束即释放该次 Dio**。

设计取舍：`dispose()` 仅**请求取消**在途下载，不强制即时关断（避免把「取消→paused」误判为 failed）。资源在 `_run` 的 `finally` 中随取消收尾释放；Dio `receiveTimeout=30s` 为异常停滞提供上界。这与既有「取消粒度为分块级」的既定口径一致。

## 六、遗留与踩坑

1. **生产接线（批次4）仍未落地**：本修复是批次4「生产接线」的**前置**。接线时须确保：`engineFactory` 每次新建的引擎都在队列 `finally` 释放（本轮已保证），且若未来改为**共享单一 Dio**，则改由 App 级宿主持有并在退出时 close —— 届时需复核本方案 A 是否需升级为方案 B（长驻单例 Dio，复用连接池）。
2. **`dispose()` 不强制即时中断**：若传输完全忽略取消信号且无超时，释放会推迟；本轮依赖 Dio `receiveTimeout` 上界。属既有既定口径，未扩展。
3. **未做运行时复现**：因生产未接线，无存活 Dio 实例可实测 socket 计数；本轮为静态取证 + 机制推演 + 计数器单测，非实测泄漏数字。
4. 无新踩坑（快照命令首次误用 cmd 解释器，改 Git Bash 后正常）。

## 七、总结

本轮定位并修复下载链的**生命周期所有权缺口**：`DownloadEngine` 与其持有方 `DownloadQueueCoordinator` 均从未调用 `transport.close()`，导致每次下载新建的 `Dio` 及其连接池不被释放、随下载次数累积。方案 A 以最小改动把释放职责落到队列的 `_run finally`（引擎新增幂等 `dispose()`、dio 传输 `close()` 幂等保护），不改变引擎 `download()` 语义与既有单测口径。验证闭环：`dart analyze` 零问题、`flutter test` 全量 **+259**、下载包 **+58**、Debug/Release 双编译通过。该修复是批次4「生产接线」的前置，接线前落地可避免「接通即泄漏」。
