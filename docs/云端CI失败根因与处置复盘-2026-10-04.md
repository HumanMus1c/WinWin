# 云端 CI 编译失败根因与处置复盘 — 2026-10-04

> 五要素结构。范围：移除 `CI（Windows x64）` 工作流；`Release（Windows x64）` 工作流固定包源并启用 `--enforce-lockfile`；相关文档同步。
> 前置：CI（Windows x64）在 2026-10-03～10-04 连续 4 次失败（本地全绿）；用户指令：「解决云端编译错误问题，并且去除CI（Windows x64）工作流」。

## 一、分析根因 / 现状取证

**现象**：`CI（Windows x64）` 工作流 4 次运行全部失败（run #37142948850、#37176117011、#37177047057、#37178113643），失败点均为 `quality` 作业的「静态分析」步骤（`1 issue found` → 退出码 1）；`build-debug` 因 `needs` 被跳过。同期本地 `flutter analyze` 为 **No issues found!**。

**根因链（全部实测取证）**：

| # | 证据 | 内容 |
| --- | --- | --- |
| 1 | 云端日志（job 111364902916） | `Changed 127 dependencies!`；`* protobuf 6.1.0 (was 6.0.0)`；`info - 'create' is deprecated and shouldn't be used… - lib\grpc\bilibili\rpc.pb.dart:49:28 - deprecated_member_use` |
| 2 | 本地环境 | `PUB_HOSTED_URL=https://pub.flutter-io.cn`（User 级）；`pubspec.lock` 恰含 **127 处** `pub.flutter-io.cn` |
| 3 | 对照实验 A（本机镜像源） | `flutter pub get --enforce-lockfile` → 通过（lock 有效，0 变化） |
| 4 | 对照实验 B（本机切 `pub.dev` 源） | 同命令 → **失败（退出码 65）**：`Unable to satisfy pubspec.yaml using pubspec.lock`、`Would change 127 dependencies`（与云端 `Changed 127 dependencies!` 行为一致） |
| 5 | 版本对照 | protobuf **6.0.0**（本地缓存 `any.pb.dart:147`）：`static Any create() => Any._();` **无弃用标记**；**6.1.0**（下载源码，如 `empty.pb.dart:55`）：`@$core.Deprecated('Use Empty() / Empty.new instead')` **新增弃用** |
| 6 | 本地复现 | `flutter analyze` → **No issues found!**（10.6s / 11.0s 两次实测） |

**根因链**：本地镜像源（`pub.flutter-io.cn`）生成 `pubspec.lock` → 云端 runner 默认 `pub.dev` 与 lock 记录源不符 → `flutter pub get` 判定 lock 失效并**整体重解析升级 127 个依赖** → `protobuf 6.0.0 → 6.1.0` → 6.1.0 对 `create()` 新增弃用 → 生成代码 `rpc.pb.dart:49`（`$0.Any.create`，跨包引用）触发 `deprecated_member_use` → 严格 `flutter analyze`（info 亦致失败）→ 质量门禁失败。

> 说明：与上轮 lint 清零（`4194f73`）及严格分析恢复（`bde21ea`）无关——那两个提交的修复是正确且必要的；本次是**独立的云端环境性根因**。

## 二、设计修复 / 实现

**决策（用户批准的计划，默认项）**：

1. **移除 `CI（Windows x64）` 工作流**（用户指定）：本地已具备 analyze / test / 双构建完整验证链，云端 push 触发的质量门禁不再需要。
2. **Release 工作流根治漂移**（默认方案 A）：
   - job 级固定 `PUB_HOSTED_URL: https://pub.flutter-io.cn`（与本地、`pubspec.lock` 同源）；
   - 「拉取依赖」改为 `flutter pub get --enforce-lockfile`——云端严格遵循 lock；若未来 lock 与环境冲突则**明确失败**（而非静默重解析）。
3. **文档同步**：`docs/跨平台可行性评估-2026-10-04.md`（CI 移除说明 + 新工作流固定源要求）、`docs/Windows安装器与代码签名评估-2026-10-04.md`（措辞校准）。

**未采用（留档）**：

- 备选 B：不改 Release、接受云端重解析（每次构建依赖漂移，产物不可重现）；
- 备选 C：仅给生成代码补 `deprecated_member_use` ignore（治标，且依赖继续漂移时可能再现其他包的弃用）。

**取舍与风险注记**：方案 A 的唯一变量是 GitHub runner（海外）访问 `pub.flutter-io.cn` 的网络质量；若不可达，Release 构建将明确失败，届时回退备选 B 再议。该风险仅影响手动/tag 触发的发布流程，不影响日常开发。

## 四、本轮总结

- **改动面**：删除 1 文件（`.github/workflows/windows-x64-ci.yml`）；修改 1 工作流（`windows-x64-release.yml`）；同步 2 文档；新增本复盘。
- **行为预期**：云端不再自动跑 CI；保留的 Release 流程与本地依赖完全同源（lock 严格生效）；`flutter analyze` 在本地与云端具有一致的判定基础。
- **遗留项**：
  1. runner → `pub.flutter-io.cn` 网络质量为唯一变量（发布流程触发时观察；若失败回退备选 B）；
  2. 生成代码对 protobuf 6.1+ 的防御性 ignore 未做（若未来本地 `pub upgrade` 至 6.1+ 需处理；当前 lock 固定 6.0.0）；
  3. GitHub 上 4 次失败的历史运行记录将保留（90 天），随工作流移除不再增长。
