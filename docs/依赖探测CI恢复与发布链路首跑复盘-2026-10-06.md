## 一、分析根因（两件基建的缺口取证）

### 1.1 Release 发布工作流：从未云端实战 + 潜伏配置缺陷

- **首跑取证**（run `37486172828`，workflow_dispatch + tag `v0.1.0+26100601`）：
  构建 / 版本纪律门禁 / 打包 / 校验和**全部通过**，最终倒在上传产物：
  `When 'archive' is set to false, only a single file can be uploaded. Found 3 files to upload.`
- **根因链**：`actions/upload-artifact` 在 `archive: false` 下仅允许**单个文件**（glob 须展开为 1 个）；上游 PiliPlus 是「便携包」「安装器」**两个独立上传步骤**，本项目移植时与后加的 `checksums.txt` 合并为**一个三步合一步骤**——该缺陷只在云端首跑暴露。
- **连带影响**：上传失败 → 后续「发布（草稿）」步骤被跳过 → tag 与 Release 均未创建。

### 1.2 CI 工作流：上一轮因根因被移除，需以新形态恢复

- 2026-10-04 因「云端包源漂移导致 pubspec.lock 重解析」被移除（`f4afc24`，详见专项复盘）；本次以「**依赖版本探测驱动 + 节流闸**」形态恢复（`windows-x64-ci.yml`）。

## 二、设计修复 / 恢复计划（含关键决策）

### 2.1 Release 修复（commit `37af1d7`）

- 产物上传拆分三步：便携包 / 安装器 / 校验和（对齐上游模式，保持 `archive: false` 原文件形态）。

### 2.2 CI 恢复（commit `cdb1eb3`，`windows-x64-ci.yml`）

- **触发**：`schedule` 每 6 小时（UTC 0/6/12/18）+ `workflow_dispatch`（`force` 可跳过探测）；
- **probe**（ubuntu）：`flutter pub outdated` 提取「resolvable > current」可升级项（含传递依赖）→ 与 `actions/cache` 快照对比 → **出现新增/变化才触发**（同一批更新只跑一次）；
- **gate**（windows）：`pub upgrade`（升级验证）→ `analyze` + `test` + Debug 构建 → artifact（**7 天**）；
- **节流闸**：`concurrency(cancel-in-progress: false)` —— 同一时刻至多 1 个运行，前一个完成（失败或成功）后才开始下一个；
- **根因防护**：`PUB_HOSTED_URL` 固定与本地同源 + `--enforce-lockfile`；
- **产物治理**（经上游调研确认）：artifact（短期 7 天）+ tag→Release（永久 assets）；**不设单独分支**（对齐 PiliPlus / BiliPai）。
