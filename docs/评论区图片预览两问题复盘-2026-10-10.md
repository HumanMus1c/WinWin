# 评论区图片预览两问题复盘（2026-10-10）

## 1. 现象描述

1. 评论区（动态/专栏/空间同款画廊组件）**首次**点开图片预览时出现"图片加载失败"；关闭后重开同一张即恢复正常。
2. 某些比例的图片在预览中被**高度压扁**造成变形（竖长图最明显）。

现场实证（用户 12:23 复现会话）：

- 复现图片从磁盘缓存实测为 **JPEG 1080×2376**（手机竖长截图，宽高比 ≈ 0.4545）。
- 运行时日志（`D:\Documents\logs\runtime.log`）记录：`12:23:46.6 gallery opened` → `12:23:48.7 closed` → `12:23:49.5 重开` → `12:23:51.7 closed`（"首次失败→重开正常"的操作痕迹）。
- 缓存目录（`%TEMP%\cached_network_image_ce`）12:23:47 落盘两文件：
  `1420a261.jpg`（573KB 原图）、`1e6fac9.jpg`（27KB，实测为 **PNG 116×256**）。
- Hive 缓存元数据含键 `resized_w256_h256_https://i0.hdslb.com/bfs/new_dyn/e85c000e….jpg`。

## 2. 定因

### 2.1 问题 2（变形）根因链：双 memCache 精确解码（等价 BoxFit.fill）

```
主图同时传 memCacheWidth + memCacheHeight（decodeClamp 屏幕尺寸，双非空）
→ octo_image 包装 ResizeImage.resizeIfNeeded(w, h, provider)，默认 ResizeImagePolicy.exact
→ Flutter 框架文档明示：宽高双非空时"输出即为指定宽高，与源图宽高比无关，等价 BoxFit.fill"
→ 引擎按 min(w, 原宽) × min(h, 原高)（allowUpscaling=false 逐维 clamp）精确解码
→ 1080×2376 在 2048×1440 目标下解码为 1080×1440：高度被压掉 39% → 显示即变形
```

- 引入提交：`f59e500`（2026-09-27《内存遗留项与独立小问题修复复盘》补解码限制；`git log -S 'memCacheWidth'` 定位）。
- 反向验证：框架源码 `image_provider.dart` 838-856 行（ResizeImagePolicy.exact 文档）；参考实现 PiliPlus `gallery_viewer.dart` 单维传参（`ResizeImage.resizeIfNeeded(width, null, provider)`）从未双传。
- 说明"为什么时好时坏"：源图未超盒（≤目标盒）时逐维 clamp 等于原尺寸不触发变形；一旦仅单边超盒（竖长图除宽度外必超）即被拉伸。

### 2.2 问题 1（首次失败）根因链：同一 URL 并发下载的改名竞争

```
评论图片 img_src 无 @ 后缀（Hive 实据）→ thumbnailUrls == imageUrls == rawUrl
→ 画廊打开瞬间：尺寸探查器（getImageFile(256×256) 磁盘缩放管线）
   与主图（getFileStream）并发请求同一 URL
→ 缓存管理器 _pushFileToStream 对并发同 URL 无去重 → 双重下载
→ 两次下载先后 rename 到同一最终路径；慢方 rename 时若快方文件正被读取
→ Windows 语义：改名目标被读句柄占用 → Access denied（本机 dart:io 实验 B/F 复现：
   目标被 RandomAccessFile/openRead 占用时 rename 抛 PathAccessException errno=5；
   并发双 rename 与空闲目标覆盖本身正常，实验 A/D）
→ _processResponse 备份回退（finalFile.rename(backup)）同样失败 → rethrow
→ 主图流错误 → errorBuilder 显示"图片加载失败"
→ 重开时原图 + Hive 元数据已写盘，缓存命中直接显示 → "首次失败、重开正常"
```

- 取证实验（scratchpad/rename_race.dart）：A 空闲目标覆盖 OK；B 目标被 RAF 读句柄占用 FAIL；C readAsBytes 期间 OK（窗口极短）；D 并发双 rename OK；F openRead 活跃期间 FAIL。
- 时间线吻合：12:23:47 两文件同时在首次打开窗口内落盘（探查产物 116×256 与 573KB 原图）；重开不再有任何下载。
- 影响面：评论区/动态/专栏/空间 6 处入口全部 `thumbnailUrls: imageUrls`，共享 `_GalleryItemView` 同一加载结构。

## 3. 修复方案与关键决策

文件：`lib/common/widgets/image/image_gallery_viewer.dart`（仅此一个文件）

1. **问题 2**：主图解码口径改用包内建的**磁盘级等比缩放盒**：
   - 删除 `memCacheWidth/memCacheHeight`；改用 `maxWidthDiskCache/maxHeightDiskCache`
     （同源数值 `decodeClamp(container, max:2048)`）。
   - 依托 `_resizeImageFile` 的 fit 盒缩放（按等比因子收进 ≤2048 盒；探针产物 116×256 即其
     等比性实据），引擎解码受限文件 → 比例真实、解码内存 ≤2048² 盒内。
   - placeholder 缩略图同口径（max 1080 双维；小缩略图 `shouldResize=false` 零成本）。
2. **问题 1**：探查器不再自建独立管线、不触发第二次下载：
   - `_resolveImageDimensions`（旧 256 独立管线）改为 `_startSizeProbeIfNeeded`：
     resolve **与主图完全同键**的 provider（同 `rawUrl`、同磁盘缩放参数，其余字段全默认），
     与主图共享 ImageCache 条目 → 全程单次下载/解码。
   - 副产物收益：探测得到的位图即实际显示位图，"点击图片外关闭"的命中矩形与显示内容
     完全一致（此前基于 256 缩略图近似）。
   - 探测时机从 `initState` 移至首个 `LayoutBuilder`（需要 containerSize 计算与主图一致的
     磁盘盒参数），用 `_sizeProbeStarted` 保证仅一次。
3. **备选与否决理由**：
   - 单维 `memCacheWidth`（PiliPlus 同款）：竖长/超宽长图解码高度/宽度无界（长边可达数万像素，
     数十 MB 级），与内存治理方向冲突；且仅覆盖画廊内单一形态。
   - 等上游包支持 fit policy：需 fork 依赖，代价大，记入遗留观察。

## 7. 遗留与踩坑

1. 首次观看大图新增一次性"全解码 + PNG 重编码"（raster 线程；二次观看走缓存秒开）；
   磁盘缓存每图可能多一个 bounded 产物条目（TTL 30 天、200 条上限自动清理）。若后续体感强烈，
   可向上游提 fidelity/JPEG 输出建议或改用 fit policy 方案。
2. 上游包 `getFileStream` 在并发同 URL 场景无 in-flight 去重：除画廊外的其它"同规格双请求"
   场景理论上仍可能触发同类改名竞争（表现为局部占位灰块，无文字错误）。本次已排查其余
   8 处双参 memCache 点（会话头像 / 系列封面 / 搜索建议 / 空间头图等）：其源文件均为
   CDN 按显示盒比例裁剪出的缩略图且解码目标值 ≥ 文件尺寸，逐维 clamp 为 no-op，**视觉自洽**；
   真正暴露"原图直连 + 双维目标"形态的仅画廊一处，即本次修复对象。表情图（极小尺寸、
   双 cacheWidth/cacheHeight）对长条源图存在轻微同类拉伸可能，字面影响 20~40px 级，列入观察。
3. 动图（gif/动 webp）与超大不受支持扩展名图像不走磁盘缩放（`_supportedFileNames` 白名单），
   解码尺寸仍以原始为准（与更早版本行为一致）；后续如需可单独评估单维 memCacheWidth 兜底。
4. 窗口尺寸变化会改变磁盘盒参数 → 主图按新键触发一次重缩放（原图缓存命中，仅重缩放无重下载）。

## 8. 总结

两个问题的共同交汇点是 `image_gallery_viewer.dart` 的图片加载参数与尺寸探测管线：
变形源于双维 `memCache` 命中 exact 精确解码（等价 BoxFit.fill）；首次失败源于探查器与主图
并发抓取同一 URL 引发的 Windows 改名竞争。修复以"磁盘级等比缩放盒 + 探测共享主图同键
provider"两处变更闭环，既恢复比例真实，又将画廊全入口的并发同 URL 请求收敛为单次下载，
并顺带让"点击图片外关闭"的命中判定与显示内容精确一致。
