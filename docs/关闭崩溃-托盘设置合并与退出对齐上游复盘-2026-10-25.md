# 关闭窗口崩溃：托盘设置合并与退出对齐上游复盘（2026-10-25）

## 一、现象

- 局域网测试机（`192.168.10.7`，`DESKTOP-38QH2UA`，Intel UHD Graphics 730）点窗口关闭按钮 → **先无响应、后崩溃**。
- WER / Application Error 签名恒为：模块 **`igd10um64xe.DLL`（Intel 核显用户态驱动）**、异常码 **`0xc0000409`**、偏移 **`0x11a859`**；30 天内 **16/16 崩溃全同签名**，最早 `2026-10-01`（早于“最新 release”，**非新版回归**）。
- 控制变量实验（实机）：
  - 托盘「显示托盘图标 + 退出时最小化到托盘」两开关均开 → 关闭走 `hide()`，**不崩**（进程保活到托盘）；
  - 关掉开关 → 关闭走 `destroy()`（真正退出）→ **必崩**；
  - **启动后完全不进任何视频页**（无 `setMedia/prepare/ready`）→ 关闭**照样崩**。

⇒ 触发点在 **窗口/引擎销毁时的 GPU/D3D 资源析构**，**与 mdk 播放路径无关**。

## 二、定因

- 崩溃发生在 **Intel 核显用户态驱动内部**（栈/缓冲区越界被 /GS 捕获 → `__fastfail(0)` → `0xc0000409`）；WinWin 侧的 `windowManager.destroy()`（Flutter Windows 引擎 / ANGLE 的 D3D 设备与合成面销毁）**正好踩在这条有缺陷的析构路径上**。关闭前的“无响应”= 析构在驱动同步调用上阻塞。
- 上游 PiliPlus 从未暴露该崩溃，靠两处 **行为层差异**：
  1. `minimizeOnExit` 默认 **true** → 开箱即用“关窗进托盘”，**永不进入真正退出路径**；
  2. 真正退出用 **硬终止** `TerminateProcess(GetCurrentProcess(), 0)`（`DeviceUtils.exitApp()`），**不跑引擎的 D3D 析构**。
- 另查出**设计冗余**（CVO 提出、已核实）：`显示托盘图标`（默认开）与`退出时最小化`（默认关）经 `if (minimizeOnExit && showTrayIcon) hide() else destroy()` 的 **AND 门**合成关闭判定；`显示托盘图标` 单独开启时点开关**无任何效果** → 语义重复。上游之所以两项并存，是因其托盘图标本身带“点击切换隐藏/显示”的独立功能；WinWin 的原生托盘只实现了 `show`/`exit`，独立价值更弱。

> 与既往结论的关系：2026-10-23 的实验 3 排除的是“**退出前释放 mdk 播放器**”（无播放器实例同样崩）。本方案绕开的是**整个引擎 D3D 析构路径**，二者不矛盾。

## 三、方案（CVO 批注定稿）

按 CVO 批注执行 **方案 2（语义合并）+ 方案 3（退出对齐上游）**，并把 **方案 1 的默认值对齐并入兼容迁移**：

1. **合并为单一开关**「关闭窗口时最小化到托盘」，key **`closeToTray`**，**默认 true**（对齐上游）。
2. **兼容迁移**：`closeToTray` **继承旧 `minimizeOnExit`**（缺省 true），写好后清理旧 key；启动期一次执行（`Pref.migrateLegacyTrayKeys()`，由 `bootstrap._run()` 调用，幂等）。
3. **托盘图标恒显、不再可设置** → 删除「显示托盘图标」设置项及其图标 `AppIcons.trayIcon()`；`TrayController.refresh()` 恒 `setVisible(true)`（仅真正退出过程隐藏）。
4. **真退出统一走 `AppExit.exit()`**：`GStorage.compact()` → `GStorage.close()` → 隐藏原生托盘 → Windows `TerminateProcess(GetCurrentProcess(),0)` / 其它 `exit(0)`；**移除** `window_state_controller` 与 `tray_controller` 两处 `windowManager.destroy()`。

**改动清单**：

| 文件 | 改动 |
|---|---|
| `lib/core/window/app_exit.dart`（新增） | 应用真退出统一入口（ffi 调 `TerminateProcess` / `exit(0)`） |
| `lib/core/window/tray_controller.dart` | 托盘恒显；`exit` 事件改走 `AppExit.exit()`；移除 `allowRealExit` |
| `lib/core/window/window_state_controller.dart` | 关闭判定改 `Pref.closeToTray && !isReallyExiting`；真退出改 `AppExit.exit()` |
| `lib/core/storage/storage_key.dart` | 新增 `closeToTray`；旧两 key 标注“仅迁移读取” |
| `lib/core/storage/storage_pref.dart` | `closeToTray` getter（默认 true）+ `migrateLegacyTrayKeys()` |
| `lib/core/bootstrap.dart` | `_run()` 中调用迁移 |
| `lib/pages/setting/models/style_settings.dart` | 两项合并为一项 |
| `lib/theme/app_icons.dart` | 移除不再使用的 `trayIcon()` |
| `lib/main.dart` | 托盘初始化注释同步 |

## 五、遗留与踩坑

1. **合并后的取舍**：`closeToTray=false` 时点关闭=**真退出**（与上游一致）；旧用户「显示托盘图标=开 / 退出时最小化=关」迁移为 `false`（关窗退出，行为不变），但**不再有独立托盘开关**。
2. **跨平台**：托盘实现为 Windows 原生 MethodChannel（`native_tray.dart`），Linux/macOS 静默降级 → 该两平台本项无实际效果，与合并前一致。
3. **硬终止的副作用**：`TerminateProcess` 不触发 `window_manager` 的 `onWindowDestroy` 与引擎优雅清理；已先 flush 存储、隐藏托盘。**后续若新增需落盘的退出逻辑，必须并入 `AppExit.exit()`**。
4. **未收口的退出点**：`lib/core/diagnostics/stall_watchdog.dart:260` 与 `lib/pages/onboarding/user_agreement_page.dart:100` 仍直接 `exit(0)`（本轮未并入 `AppExit`，不阻塞）。
5. **驱动缺陷未根治**：本方案从**行为层绕开** Intel 驱动的 D3D 析构缺陷；若将来出现**其它进入 D3D 析构的路径**，仍可能复现。真正消除仍建议在测试机更新/回退 Intel 核显驱动（`32.0.101.7092`）。

## 六、总结

本次把“关闭窗口崩溃”从“Intel 核显驱动的 D3D 析构缺陷”收敛为**可绕开的行为层问题**：按 CVO 批注定稿，**合并**两项语义重复的托盘设置（单一 `closeToTray`，默认对齐上游、旧值兼容继承），**托盘图标改为恒显、不再可设置**，并把**真正退出对齐上游**——flush 存储 + 移除托盘 + `TerminateProcess` 硬终止，从而**不跑引擎 D3D 析构**。已通过 `dart analyze` 与 debug/release 双编译；**Intel 核显机 5 轮实机复验全部通过（见 §七）**。

## 七、Intel 核显机实机复验（2026-10-26）

### 复验方式

- 机器：`DESKTOP-38QH2UA`（192.168.10.7，i5-12400 + Intel UHD Graphics 730），经 SSH 远程操作。
- 代码：远端仓库由 `e8792cc` 快进到云端最新 **`8f7900e`**（远端 git 配了已失效的 `127.0.0.1:7890` 代理且无凭据，改用 **git bundle 增量传输**绕过）。
- 编译：**在核显机本体**执行（不搬本机产物）——`flutter analyze` → `No issues found! (14.8s)`；`build windows --debug` → 73.0s 通过；`build windows --release` → 91.8s 通过。
- 设置：Hive `setting.closeToTray = false`（关闭走 `AppExit.exit()` 硬终止分支）。
- 脚本：计划任务（`-LogonType Interactive`，确保窗口出现在控制台会话）逐轮启动 → 等主窗口出现（轮询非盲等）→ 停留 8s → `PostMessage WM_CLOSE` → 等退出并记录退出码/WER 事件。

### 结果

| 轮次 | 启动到出窗 | 关闭后退出 | 退出码 | WER 事件 |
| --- | --- | --- | --- | --- |
| 1~5 | 均 1s | 均 1s | 全 `0x00000000` | 无 |
| **汇总** | — | — | **crashes=0 / hangs=0 / no_window=0** | **0 条** |

**结论：Intel 核显机上点关闭不再崩溃**，1 秒内干净退出，无 `igd10um64xe.DLL` / `0xc0000409` 事件，无“先无响应”现象。

### 复验踩坑（对结论判定的影响）

1. **上一轮“仍崩溃”结论作废**：上次自动化脚本 01:26 启动后，脚本日志出现 9 小时间隙（`01:26 → 10:17`），`WM_CLOSE` 实际在 `10:17:23` 才发出，而 Application Error 1000 记录于 `10:17:20` —— 崩溃发生在**整机休眠唤醒瞬间**（D3D 设备丢失），**不是关闭路径崩溃**。本重复验全程用 `SetThreadExecutionState` 保持唤醒，排除了该干扰。
2. **SSH 会话结束会连带杀掉子进程**：`Start-Process` 挂起的构建在会话断开后进程消失（`analyze` 停在 “Analyzing WinWin...”）。改用**计划任务**托管长任务后稳定。
3. **PowerShell 5.1 的 `uint32` 坑**：`0x80000000` 会解析成负数 Int32，`SetThreadExecutionState` 直接抛转换异常（守卫静默失效）→ 必须显式 `[uint32]3221225473`。
4. **上传脚本必须 UTF-8 带 BOM**：无 BOM 的 UTF-8 被 PS 5.1 按 GBK 解码，中文注释行末字节会“吞掉”换行，把下一行 `Add-Type @"` 拼进注释 → here-string 解析失败、任务秒退无日志。新增 `-Command ... *> task_out.log` 重定向才定位到该 ParserError。
5. `flutter build` 在 SSH 下把 stderr 当错误会让 PowerShell 报 `NativeCommandError` 并返回 1，**不能据此判断失败**，应看 `cmd` 的退出码与产物时间戳。
