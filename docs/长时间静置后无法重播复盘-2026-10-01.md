# 长时间静置后无法重播（片尾重播态 → 未知状态）根因与修复复盘（2026-10-01）

## 1. 现象

视频自然播完后进入重播态（中央显示重播按钮）。程序**静置约 4 小时**后点击重播：

- **无法重播**——点击重播后画面无反应、不再播放；
- **当前视频处于未知状态**——重播按钮消失、进度条停在片尾、界面显示为"播放中"（暂停图标），任何点击（重播/播放/快进）均无反应。

## 2. 定因（取证）

### 2.1 取证材料

- `D:\Documents\logs\runtime.log`（AppLogger，Release 仅 W/E）
- `D:\Documents\logs\trace.log`（SeekProbe 心跳/状态/Raw 全量埋点，逐行落盘）
- 本次会话：同一视频 568599ms（9分28秒），双实例（主实例纯视频 + 第二实例纯音频），3 条 CDN 候选。

### 2.3 根因链

**R1（直接触发）——重播时流 URL 已过期，seek 必然失败。**
`replay()` 只做 `seek(0)`。B 站 playurl 的 `deadline` 实测为拉流时刻 +2h（本次 18:34 拉流 ⇒ 20:34 过期），22:49 重播时 URL 已过期约 2h15m，HTTP 连接也早已断开；mdk 要为位置 0 重新发起网络读取，被 CDN 拒绝 ⇒ `seek` 返回 -8（第一次 4.24s 后失败、第二次 11ms 快速失败）。

**R2（"未知状态"的直接来源）——seek 失败后状态机不一致。**
`_processSeekQueue` 的 finally 解冻逻辑**无条件按 `_userIntentPlaying` 强制 `player.state = playing`**（原 L4011-4013）。seek 失败后媒体仍停在片尾（EOS），底层随即被打回 paused；而 `onStateChanged` 的 UI 广播在"缓冲挂起抑制"路径下把 `playing.value` 留在 true，且 `completed` 已被 `replay()` 清 0、无人恢复 ⇒ 重播按钮消失 + UI 伪装"播放中" + 底层片尾暂停，此后每次点击都重复同一失败 seek。

**R3（无兜底）——片尾状态跳过全部看门狗，且无 URL 过期检测。**
片尾时轮询走 `completed-frozen` 早退分支（`pos >= dur-1000`，L1431-1438），缓冲/卡死看门狗全部跳过；代码中也不存在任何"URL 过期检测"或"片尾 seek 失败 → 重新拉流"的兜底路径 ⇒ 状态永久卡死（实测 30 分钟无自愈）。

## 3. 修复方案

改动文件：`lib/pages/video/player_controller.dart`

1. **记录流 URL 截止时间**：新增字段 `_streamDeadlineMs` + 静态解析 `_parseStreamDeadlineMs()`（解析实际使用 video/audio 直链的 `deadline` 秒级时间戳，取最早者）；`_openWithQuality` 在每次加载的重置段清空、在 URL 选定后重新解析。无该参数时为 null（不启用过期判定）。
2. **`replay()` 前置检测**（治本）：`state == stopped` **或** URL 已过期（距 deadline 不足 60s 安全边距 `_streamDeadlineSafetyMarginMs`）时，**不再 seek、直接 `load(start: Duration.zero, autoplay: true)`** 重新拉取 playurl（`load` 会重走 playurl API——缓存 TTL 10 分钟早已失效，必得新鲜 URL），并清空弹幕引擎；证据行 `REPLAY-RELOAD`。
3. **片尾 seek 失败兜底**（治标兜底，覆盖无 deadline/边距失效/连接已死等形态）：`_processSeekQueue` 新增 `eofSeekFail` 判定——`res < 0 && _userIntentPlaying && 位置仍被退回片尾（posAfter ≥ dur-1500）`；finally 解冻分支改为：
   - **不**执行"按意图强制 playing 起播"与第二实例起播（消除伪播放态）；
   - 显式 `playing.value = false`（UI 如实）；
   - 自动 `load(start: 目标位置, autoplay: true)` 恢复（目标为 0 即从头播）；证据行 `SEEK-FAIL-EOF-RELOAD`。
4. 判定字段（`eofSeekFail` / `durMsAtFail` / `lastSeekRes` / `lastSeekPosAfterMs`）因跨 try/finally 作用域，声明于 try 之外。

**行为预期**：

- 静置超过 URL 有效期后点重播：自动重新拉流从头播放（多一次 API + prepare 的加载耗时），不再出现 4s+ 失败与永久卡死；
- **URL 未过期时行为完全不变**（仍走原 `seek(0)` 秒开快速路径）；
- 即使 deadline 无法解析（如清单模式），片尾 seek 失败也会被兜底捕获并重载，且 UI 不再停留在假"播放中"。

## 6. 本轮修复总结

**改动面**：`lib/pages/video/player_controller.dart` 单文件——新增 `_streamDeadlineSafetyMarginMs` 常量、`_streamDeadlineMs` 字段、`_parseStreamDeadlineMs()` 解析；`_openWithQuality` 记录/重置 deadline；`replay()` 过期前置检测；`_processSeekQueue` 片尾失败兜底分支。

**改动面外**：新增本复盘文档。

**遗留项（本轮不做，待证据）**：

1. **暂停态（非片尾）长静置**的同源风险：URL 过期后恢复播放/拖动进度条，首次读取失败仍会进入既有卡死自愈路径（`_recoverStalledStream` 使用加载时 CDN 候选——候选 URL 同样已过期），3 次失败后放弃；本轮未改该路径（避免影响弱网自愈的既有行为）。
2. `replay()` 的过期判定依赖 URL 携带 `deadline`；清单模式（localhost HLS）无该参数，仅靠第 3 项兜底。
3. mdk seek 返回值 -8 的语义未在 fvp 0.38.1 Dart 层定义（native 返回值；Dart 层自身仅产生 -2/-10），本轮按"seek 失败"处理，不影响修复逻辑。
