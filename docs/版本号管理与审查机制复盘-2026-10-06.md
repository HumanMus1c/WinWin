## 一、分析根因（需求与现状取证）

### 1.1 需求来源

Windows 端可无视版本号与签名随意覆盖安装；但 Android / iOS / Linux 对版本号极其敏感（`versionCode` / `CFBundleVersion` 必须单调递增才能覆盖安装，deb/rpm 降级安装被默认拒绝）。真实诉求：**回滚 / 热修 / 重发时用旧版本代码构建，版本名可以持平甚至降级，但版本代码必须大于历史最高值**，否则安卓端无法覆盖安装（`INSTALL_FAILED_VERSION_DOWNGRADE`）。

### 1.2 现状缺陷（取证）

| 项 | 取证 | 结论 |
| --- | --- | --- |
| pubspec 版本从未变更 | `git log -p -- pubspec.yaml` 全历史仅初始提交 `version: 1.0.0+1` | 无版本管理可言 |
| 关于页版本脱节 | `about_page.dart` 硬编码 `版本 0.1.0` vs pubspec `1.0.0+1` | 不一致长期无人发现 |
| 无版本纪律校验 | Release 工作流仅 `Split('+')[0]` 取 name 用于产物命名 | 版本代码回退 / 重复无人拦截 |
| 无发布 tag 历史 | `git tag` 仅内部 snapshot 类 | 发布谱系空白 |

### 1.3 参考实现评估与硬约束核实（为什么自研）

| 来源 | 做法 | 结论 |
| --- | --- | --- |
| PiliPlus（上游） | `lib/scripts/build.ps1`：code = `git rev-list --count HEAD` | 旧提交 / hotfix 分支构建时**计数回退**，不满足回滚覆盖 |
| BiliPai（参考库） | 手工维护 versionCode 每次 +1 | 纪律正确但无工具保障（无单调性 / 上限校验） |
| pub 社区工具（app_version_manager 等） | 通用 bump；`revert` 连 code 一起回退 | 不满足"name 降/持平 + code 单增"语义；无 git 历史审查 |

**硬约束核实（源码级 / 实测）**：

- pub_semver 2.2.1 语法正则：`MAJOR.MINOR.PATCH(-预发布)?(+构建号)?` → **四段数字与 `[ ] : ( ) < >` 等连接符均不可行**；
- flutter_tools `flutter_manifest.dart` 硬编码 `split('+')` 提取 buildName / buildNumber；`cmake.dart` 拼写 `'$buildName+$buildNumber'` → **存储层 `+` 不可更换**；
- `rc.exe` 对 > 65535 的 FILEVERSION 段值**静默截断为 u16**（不报错），字符串版本完整——决定了大位数字日期码对 Windows 构建安全。

## 二、设计修复计划（方案与关键决策）

- **双号模型**：`version: <name>+<code>`；name 可持平 / 降级，code 只增不减；历史权威 = git 全 refs（HEAD / 分支 / tag / 远端），不维护账本文件。
- **日期编码**：`YYMMDDnn` —— 当次编译日 + 当日序号；分配算法 = `max(当日候选, 全局历史 max + 1, 当前值 + 1)`（防倒退兜底）；上限 2,100,000,000。
- **工具**：`tools/version_tool.dart`（Dart 单文件、零依赖）：`show` / `set` / `check` / `history`。
- **CI 门禁**：Release 工作流构建前执行 `check`（code 单调性硬校验），失败即中止；产物命名携带 code。
- **关键取舍**：
  1. code 锚定"**当次编译日**"而非"版本发布日"——回滚构建天然大于历史（核心优势）；
  2. 分配公式对"未提交的手改大值"保守取 max——宁可跳号不冒降级风险；
  3. 不做账本文件——git 历史即审计轨迹，hotfix 分支可见全局水位线；
  4. 工具用 Dart——跨平台（未来 Linux / macOS CI 同用）、零依赖、随 Flutter SDK 自带。
