# 消息中心会话列表「滚到底不出新会话」复盘 — 2026-11-01

## 一、现象

消息中心默认分类「全部」的会话列表，滚动到底后继续下滚**不再出现任何新会话**，也没有加载更多指示；下拉刷新同样不改变列表条数。分类切到「关注 / 未关注 / 私信」等时，滚动补批正常。

与 2026-11-01 首页推荐流「下滚不出新内容」（`531a52e`）表象相同，但**根因完全不同**。

## 二、定因

### 2.1 先排接口（实测，非推测）

用本机已登录账号对 `GET https://api.vc.bilibili.com/session_svr/v1/session_svr/get_sessions` 做了三组探针（凭据仅本机解密读取，输出脱敏，探针文件用后即删）：

| 请求 | 返回 |
|---|---|
| `session_type=4`、`size=22`、无游标 | 22 条，`has_more=1`，末条 `session_ts=1793437508924485`（16 位微秒） |
| 同上 + `end_ts=末条微秒 -1` | 11 条，**11/11 全部是第一批重复**，首条恒为最新 |
| 同上 + `end_ts` 传微秒原值 / 秒 / 毫秒 | 同上，全部重复 |
| 同上 + `pn=2`（带/不带游标） | 同上，全部重复 |
| `size=100/200/300/500` | **一律只返回 100 条**，`has_more` 恒为 1 |
| `session_type=1`（私信）/`2`（未关注）/`9`（关注）带游标 | 第二批 **overlap=0**，全新会话，分页正常 |
| `session_type=3/5/7/8` | 无会话或 `has_more=0`，正常 |

结论：**`session_type=4`（全部）不支持游标翻页**，`end_ts` 与 `pn` 被服务端忽略，单批上限恒为 100；其余分类的游标分页正常。

### 2.2 再落代码

`SessionListSection._load()`（`lib/pages/whisper/session/session_list_section.dart`）原有链路：

1. 首批按 `ViewportLoadBudget` 只请求「约 2 屏」≈ 22 条（服务端其实一次能给 100 条）；
2. 滚到底触发 `_load()`，带 `end_ts` → 服务端从最新开始重发同一段；
3. `SessionPaginationPolicy.mergePage` 判定「整页重复」→ `shouldRetry`；
4. `resolveNextEndTs` 的重试游标只往前推 **1 微秒**，永远越不过重复段；
5. 3 次重试后 `hasMore=false`，此后滚动不再发任何请求 → 列表永久停在首批。

### 2.3 同期发现的两个同类缺陷

1. `_load` 的 `_isLoadingMore` 没有 `try/finally`：请求抛异常时永久卡 `true`，此后刷新与补批全部失效，只能退出页面重进。
2. 下拉刷新被在途补批「吃掉」：`refresh` 分支先重置游标，但紧接着 `if (!_hasMore || _isLoadingMore) return;`，正在加载更多时下拉刷新静默无效。

## 三、方案（方案 A）

1. `SessionPaginationPolicy` 新增单一来源：
   - `allSessionType = 4`、`allSessionFetchSize = 100`；
   - `supportsCursorPaging(specialMode:, sessionType:)`：全部 / 特别关注（都走 `session_type=4`）返回 false，其余分类 true。
2. `SessionListSection._load`：
   - `_serverSupportsCursor` 为 false 时**一次取满 100 条**，并按「没有更多」处理（`responseHasMore: false`），不再走无效的整页重复重试；
   - 支持游标的分类维持原视口预算 + 游标分页。
3. 健壮性同批修：
   - `_isLoadingMore` 改由 `try/finally` 复位；
   - 新增请求世代号 `_requestId`：下拉刷新可抢占在途补批，旧请求结果按世代号丢弃。
4. 新增 `test/pages/whisper_session_paging_test.dart` 4 项回归，锁定：
   - 全部 / 特别关注判定为不支持游标分页；
   - 全部模式整页重复 + 服务端 `has_more=1` 时按「没有更多」处理；
   - 全部模式首批 100 条完整合并且判定没有更多；
   - 支持游标的分类仍保留「更早游标重试」能力。

不改的部分：`SessionPaginationPolicy` 的排序/去重/游标推进算法本身正确（BiliPai 移植已验证），本轮只是把「服务端能力」如实传给它。

## 六、遗留与踩坑

1. **服务端能力上限**：「全部」分类一次最多 100 条会话，更早的会话拿不到；特别关注由「全部」的 100 条内本地过滤，超过 100 之外的特别关注会话不显示。若后续仍需要真正全量，需转 gRPC `SessionMain`（PiliPlus 方案，带 offsets 真分页）——CVO 已定：**此类问题再次出现时提示走方案 B 彻底根治**。
2. 踩坑：`abstract final class` 里不能写实例 `const` 字段，策略常量必须是 `static const`。
3. 踩坑（同类第二次）：首页那次是跨泛型 `addAll` 抛 `TypeError`（日志有实锤），本轮服务端语义错配**日志干净、请求全成功**——「滚到底不出新内容」必须先实测接口再落代码，不能凭表象套用上一轮结论。
4. 未改：`session_type=1/2/9` 的服务端批量（如私信分类无视 `size=11` 仍回 26 条）会略超视口预算，属服务端固定批量，不额外处理。

## 七、总结

消息中心「全部」不能滚动出新会话，是「服务端不支持游标翻页 + 前端按分页接口使用 + 首批被视口预算压到 22 条」三者叠加：滚到底拿到的永远是重复页，三次微秒级重试后自锁。方案 A 让该分类一次取满服务端上限 100 条并显式判定「没有更多」，同时补掉加载态卡死与刷新被吞两颗雷；其余分类分页行为不变。
