# 版本号展示与云端 Release 发布根因复盘 — 2026-10-23

> 五要素结构。范围：① 云端 `Release（Windows x64）` 拉依赖失败（`39822929500`）的根因定位与修复；②「关于」页版本号硬编码导致显示停滞的修复。
> 前置：2026-10-23 01:26 用户指令「版本号升到 0.1.1，提交云端并触发 release + 打 tag」；01:28 云端 Release 失败；12:13 用户要求先做换源（方案 A）+ 依赖升级本地实测；12:39 用户实测发现「关于」页仍显示 0.1.0。

## 一、现象

1. **云端**：tag `v0.1.1+26102301` 触发 `Release（Windows x64）` 运行 `39822929500` → **failure**，耗时 2 分 25 秒。失败步骤 = 第 4 步「拉取依赖（严格遵循 pubspec.lock，防云端重解析）」，第 5~15 步（版本审查 / 打包 / 上传产物 / 草稿发布）**全部 skipped**。日志：
   ```
   Unable to satisfy `pubspec.yaml` using `pubspec.lock`.
   Would change 126 dependencies.
   Failed to update packages.   → exit code 1
   ```
2. **本机**：用户实测「关于」页版本号**仍显示 `版本 0.1.0`**，与已升位的 `pubspec.yaml`（`0.1.1+26102301`）不符。
3. **附带**：定时工作流「CI（依赖更新探测）」自 2026-10-20 起连续失败，失败步骤**同为**「拉取依赖（严格遵循 pubspec.lock）」。

## 二、根因（两条独立根因）

### 根因 A：锁文件包源漂移（云端发布失败）
- `pubspec.lock` 126 处 hosted 包源 = `https://pub.dev`；而 Release 工作流 job 级固定 `PUB_HOSTED_URL: https://pub.flutter-io.cn` 且启用 `--enforce-lockfile`。
- 包源不一致 → pub 判定锁失效 → **整体重解析 126 个包** → `--enforce-lockfile` 拒绝（设计即"明确失败而非静默重解析"）。
- **引入点**：`git log -S'url: "https://pub.dev"' -- pubspec.lock` → `84c040f`（B7 封板，2026-10-18）。该次本地 `flutter pub get` 在**未继承 User 级 `PUB_HOSTED_URL`（=镜像源）的环境**下执行，回落 `pub.dev` 默认并整文件改写；因 10-06 之后未再跑过 release，故障潜伏至今日 tag 推送才暴露。
- 对照取证：打 tag `v0.1.0`（`7511df4`，10-06）时锁文件 127 处均为 `pub.flutter-io.cn`，该次 Release 成功。

### 根因 B：「关于」页版本号硬编码（显示停滞）
- `lib/pages/setting/about_page.dart` 中 `Text('版本 0.1.0')` 是**写死的字面量**（自 `2eb0014`"建立设置页面"起），与 `pubspec.yaml` 无任何联动 → 违反「每个概念只在一处定义」。
- 全仓排查：仅此一处硬编码；`windows/runner/Runner.rc`（`FLUTTER_VERSION`）与 `windows/packaging/exe/inno_setup.iss`（`AppVersion={{APP_VERSION}}`）均为动态注入，无同类问题。

## 三、方案与实现

**根因 A（锁文件包源）**：
- 采用**方案 A（最小）**：把 `pubspec.lock` 126 处 `url: "https://pub.dev"` 改回 `https://pub.flutter-io.cn`。
- 并按要求升级：`sentry 10.1.0→10.2.0`、`video_player_avfoundation 2.12.1→2.12.2`、`sdks.flutter >=3.44.0→>=3.47.0`。
- 未采用：改工作流改用 pub.dev（与 2026-10-04 既定决策相悖，且本地环境为镜像源会导致本地重解析漂移）。

**根因 B（关于页版本）**：
- 采用**方案 A（package_info_plus）**：`pubspec.yaml` 声明 `package_info_plus: ^10.2.2`（与参考库 BiliPai 同栈，主流做法）；关于页以 `PackageInfo.fromPlatform()` 读取真实构建版本，按《版本号管理规范》§4 的 UI 形态显示 `name (code)`。
- 机制取证：`package_info_plus-10.2.2/lib/src/package_info_plus_windows.dart` 中 `versions = info.productVersion.split('+')` → `version=versions[0]`、`buildNumber=versions[1]`；本机产物 exe 版本资源为 `0.1.1+26102301` ⇒ 显示 `版本 0.1.1 (26102301)`。
- 未采用：扩展 version_tool 生成 Dart 常量（B）、构建期 `--dart-define`（C）、直接改字符串（D，不治根）。

## 六、遗留与踩坑

1. **`PUB_HOSTED_URL` 沙箱缺失坑（根因级，务必记住）**：本机 User 级确有 `PUB_HOSTED_URL=https://pub.flutter-io.cn`，但 OfficeAce 注入的 shell **不继承**该变量。任何未显式注入该变量的 `flutter pub get` / `flutter build`（build 内部会隐式 `pub get`）都会回落 `pub.dev`，**静默把 `pubspec.lock` 的包源整体改写** —— 这正是根因 A 的引入机制，本次修复过程中再次被触发（`flutter build windows --debug` 输出 `Changed 126 dependencies!` 并顺带把 `web 1.1.1→1.1.2`）。**纪律：本项目任何 flutter 命令都必须前缀 `PUB_HOSTED_URL=https://pub.flutter-io.cn`。**
2. **镜像源与 pub.dev 版本面不同**：`pub.flutter-io.cn` 为新版镜像，部分包版本滞后于 `pub.dev`（如 `web`）；跨源重解析会引入非预期升级。回归镜像源后已把 `web` 还原为 `1.1.1`，保证改动范围精确。
3. **未做**：Release 重触发（需强推 tag 或 workflow_dispatch，属破坏性/外部动作，待用户授权）；「关于」页显示形态是否补 code（默认按规范 §4 已补 `(26102301)`）；定时「依赖更新探测」工作流未单独验证（预期随锁文件修复自动恢复）。

## 七、总结

云端 Release 失败与「关于」页版本停滞是**两条彼此独立的根因**：前者是 `pubspec.lock` 包源被改写为 `pub.dev`（与工作流固定的镜像源冲突，`--enforce-lockfile` 明确失败），后者是「关于」页把版本号写死、从未接入单一事实源。两条均已按最小方案修复并本地五关验证全绿（镜像源门禁 / analyze / debug / release），锁文件改动范围经逐行核对精确等于既定范围。最大的系统性教训是 **`PUB_HOSTED_URL` 在沙箱 shell 中缺失会导致锁文件被静默改写** —— 该坑既是本次故障的成因，也是后续必须长期遵守的操作纪律。
