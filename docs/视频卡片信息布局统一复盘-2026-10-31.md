# 视频卡片信息布局统一复盘 — 2026-10-31

> 范围：历史记录、用户空间（投稿 / 最近点赞）、收藏夹详情、稍后再看、消息中心对话视频卡。
> 目标：五处视频卡片共用同一套信息层级，并按场景补齐播放进度、播放时间、发布时间。

## 一、现象

- 五处视频卡片是五套互不相干的私有实现，同一张稿件在不同页面呈现的字号、图标尺寸、信息行顺序、统计角标位置都不一致。
- 历史记录：有播放进度条与 `viewAt` 相对日期，但未标明该时间是「播放时间」，也没有「已看 / 总时长」文本。
- 稍后再看：接口已有 `pubdate`，卡片未渲染发布时间；进度条贴在封面内，与历史卡片「进度条置卡片下缘」的既有规范相反。
- 收藏夹详情：接口 `/x/v3/fav/resource/list` 的 `medias` 已返回 `pubtime`，但 `FavDetailItem` 未解析，卡片无发布时间。
- 用户空间：发布时间挤在播放/弹幕统计行右侧，封面缺播放/弹幕角标，与首页竖卡不同构。
- 消息中心对话：视频卡只有封面 + 标题，`content.times`（时长）未使用，没有首页竖卡的时长角标与信息层级。

## 二、定因

1. **无共享信息层**：历史 / 稍后再看 / 收藏夹 / 用户空间各自在页面内手写标题、UP 行、统计行，口径无法复用。
2. **数据模型缺字段**：`VideoCardData` 只有归一化进度 `progress`，没有原始已看秒数、发布时间、播放时间。
3. **收藏夹模型漏字段**：`FavDetailItem` 未解析接口已下发的 `pubtime`。
4. **消息卡未解析时长**：`msg_type=11` 的 `content` 含 `times`，原实现只取 `bvid/title/cover`。
5. **历史进度条位置的历史决策**：B7 反馈轮#2 已将历史进度条移到卡片下缘；稍后再看仍保留旧的封面内实现，造成同类信息两种位置。

## 三、方案

1. **新增共享信息层** [video_card_info.dart](file:///d:/Documents/GitHub/WinWin/lib/common/widgets/video_card/video_card_info.dart)：
   - `VideoCardInfoText`：时间 / 进度文案唯一口径。
     - 历史：`观看于 今天 21:30`（`chatFormat(isHistory: true)`，保留时分）。
     - 稍后再看 / 收藏夹 / 用户空间：`发布于 3天前`（`dateFormat`）。
     - 进度：`已看 12:34 / 29:00`；`progress == -1` → `已看完`。
   - `VideoCardInfoColumn`：统一三级信息列——标题（2 行）→ UP 行（右侧时间）→ 进度行（右侧动作）。历史 / 稍后再看 / 收藏夹 / `VideoCardH` 共用。
2. **数据层补字段**：`VideoCardData` 新增 `progressSeconds / publishedAt / playedAt`，并在历史、稍后再看、收藏夹、Map 回退、动态反射分支统一映射。
3. **收藏夹模型**：`FavDetailItem` 新增并解析 `pubtime`。
4. **历史卡片**：右列改共享信息列；显示「观看于 …」与「已看 x / y」；保留 B7 轮#2 的「进度条置卡片下缘」与封面左上业务角标。
5. **稍后再看卡片**：右列改共享信息列；新增发布时间；播放 / 弹幕统计移到封面左下角标；进度条从封面移出，统一放卡片下缘。
6. **收藏夹详情卡片**：右列改共享信息列；新增发布时间；播放 / 弹幕统计移到封面左下角标；失效稿件标题保持置灰。
7. **用户空间卡片**：投稿与最近点赞改用共享 `VideoCardV`；封面补播放 / 弹幕角标；底栏用日历图标 + 「发布于 …」胶囊替换 UP 胶囊；关闭空间内重复的更多菜单与右键菜单，保持原行为。
8. **消息中心视频卡**：按首页竖卡结构重做——16:10 封面 + 右下时长角标（`content.times`）+ 标题 2 行。消息协议不含 UP / 播放统计字段，因此不伪造底栏信息。
9. **演示与骨架**：`DemoVideoCardH` 补时间 / 进度骨架行并统一 140 封面宽；`VideoCardHSkeleton` 新增 `showProgressSlot`（历史 / 稍后再看为 true）；消息演示卡改 16:10 + 时长角标占位。

## 八、反馈轮修正（2026-10-31）

### 8.1 现象

1. 历史卡片一行标题与两行标题时，UP / 时间 / 进度行纵向位置不同，同一网格行内的信息行不对齐。
2. 历史记录里的「仅作者自己可见 / 被下架 / 已删除」稿件标题为空，卡片只剩封面、UP 与时间，没有状态说明；用户希望借鉴失效收藏档案恢复项目，恢复封面、标题、简介。
3. 消息中心对话内的视频卡在 Release 下变成超高纯灰色长条，一张卡接近占满聊天视口；标题不可见。

### 8.2 定因

1. **标题行对齐**：卡片外层 `Column(mainAxisSize: min)` 给非 Flex 子节点传入**无界高度**，Row 中的 `VideoCardInfoColumn` 因此按内容高度收缩（实测单行 58 / 两行 77），`spaceBetween` 无剩余空间可分配；UP / 进度行跟随标题高度整体下移。不是网格高度问题（两张卡外壳均为 110）。
2. **失效历史**：历史接口对不可见稿件不下发 `title`（部分场景下 `badge` 含「失效」），原卡片无占位与状态识别；点击会进入必然失败的详情页。
   - 可借鉴项目：`Mr-Po/bilibili-favorites-fix`（油猴脚本，Greasyfork 383143）。其恢复链路：`https://www.biliplus.com/api/view?id=<aid>` 取 `title / pic / description`，失败再降级到 `all/video` 页面抓 `api/view_all`。
   - 状态区分使用 B 站 `/x/web-interface/view` 的错误码：`62012` 仅作者自己可见、`62002` 稿件不可见（下架）、`62004` 审核中、`-404` 已删除、`-403` 无权访问。
3. **消息卡灰条**：`Container(color: ..., clipBehavior: Clip.antiAlias)` 违反 Flutter 断言
   `decoration != null || clipBehavior == Clip.none`（Container 有裁剪行为时必须提供 decoration）。
   Debug 直接断言失败；Release 断言被剥离后裁剪路径异常，卡片被裁成约 320 宽、接近视口高度的灰色长条。
   同时标题使用 `const TextStyle(height: 1.38)` 继承了聊天容器外的默认文本色，深色主题下不可见，只剩灰块。

### 8.3 方案

1. `VideoCardInfoColumn`：标题槽改为**固定预留两行高度**（`textScaler.scale(fontSize × 1.35) × 2`）+ `Align(topLeft)`；单行标题不再让信息行整体上移。
2. 历史失效稿件：
   - 新增 `lib/services/history_recovery.dart`：`HistoryRecoveryService.lookup()` 按 aid 串行限流（最多 2 并发）、缓存、独立 Dio 请求 BiliPlus（**不带任何 B 站 Cookie**，5s 超时，`-503` 降级）。
   - 先查 `/x/web-interface/view` 判断状态；若已恢复可访问（code 0）则直接用其标题/封面/简介并允许打开。
   - 卡片（`_HistoryCard` 改 StatefulWidget）：失效条目显示「恢复中… → 仅作者可见 / 已下架 / 已删除 / 审核中 / 已失效」封面角标；恢复出的标题置灰 + 删除线；封面优先用恢复图。
   - 点击失效卡不再进详情页，改弹详情弹窗：状态、UP、播放时间、恢复简介，支持「复制 AV 号」。
   - `HistoryItem` 新增 `isUnavailable`（无标题或 badge 含「失效」）。
3. 消息卡：`Container` 改用 `decoration: BoxDecoration(color: ...)` + `clipBehavior`；标题显式 `tokens.text.bodyMedium` 颜色。

## 十、反馈轮修正 3：发布日期 / 热门胶囊 / 已关注 / 在线人数（2026-11-01）

### 10.1 现状与约束

- 首页竖卡宽约 240px、封面 16:10（约 150px）、信息区 90px；当前「标题 + 一行底栏」已接近占满。

- 若把 UP、发布时间、在线人数、播放胶囊、点赞胶囊、已关注、更多全部塞进一行，240px 下必然溢出。

### 10.2 定稿方案（方案 A：分层不加高）

```
封面 16:10
  左上：123人正在看（设置开启且有数据时）
  左下：播放 2.6万 / 弹幕 129   右下：15:39
标题（2 行）
UP 行：UP 名 [已关注]              3天前
热门行：[热门] [1.2万点赞]            ⋯
```

- 发布时间放 UP 行右侧，日历图标 + 相对日期（3天前 / 10-28 / 2025-03-12），不占独立行。
- 在线人数做封面左上角胶囊，**沿用「显示在线人数」设置（默认关）**；开启后按可见卡片懒加载，60s 缓存、最多 2 并发、512 条上限。

- `已关注` 紧跟 UP 名，仅首页显示（使用 rcmd 的 `is_followed`）；聊天卡按用户决定**不额外查关系**。
- 网格信息区仍为 90px：标题 38 + UP 行 16 + 热门行 18 + 间距 2 ≈ 74 < 80，实测无溢出。

5. `VideoCardV` 重构信息区：标题 → UP 行（UP + 已关注 + 发布时间）→ 热门行（rcmd 理由 + 点赞胶囊 + 更多）；`showPublishTime` 默认改为 true，`showOnlineCount` 支持外部覆盖（测试用）。

## 十二、反馈轮修正 5：标题仍被裁切 / 点赞逐卡请求（2026-11-01）

### 12.1 现象

1. 首页两行标题的第二行仍被截断（截断线是水平方向的，故直观上像「水平裁切」）。
2. 所有卡片的点赞数逐个出现，用户质疑「点赞量是逐个请求的吗」。

### 12.2 定因

1. **上一轮的格子高度没落到首页**：§11 改的是 `Grid.videoCardVDelegate` 默认值与 `RcmdController._gridRowExtent`（视口预算用），而首页实际用的是 `rcmd/view.dart` 里内联的 `SliverGridDelegateWithExtentAndRatio(mainAxisExtent: scale(90))` → 信息区仍是 90。
2. **实测尺寸**（1200 宽窗口，0 号卡片 228.8 × 233.0，封面 143）：信息区 90 = 上下内边距 10 + 标题槽 + UP 行 19.6 + 间距 2 + 热门行 26（「更多」按钮 26 撑高），标题槽只剩 32；两行标题需 14 × 1.38 × 2 ≈ 38.7 → `RenderParagraph` 默认 clip 把第二行下半截掉（不是 `maxLines` 越界，所以没有省略号）。
3. **点赞逐个出现**：首页走 App 推荐流（`/x/v2/feed/index`），该接口不下发 `pubdate` 与 `stat.like`，于是 `_RcmdVideoCard` 对每张可见卡各发一次 `/x/web-interface/view`（2 并发 + 缓存）；一屏十几张卡就是十几次请求，点赞只能一张张回填。

### 12.3 方案

1. 新增 `Grid.videoCardVInfoExtent = 100.0`（实需 96.3，留约 4px 余量），推荐 / 关注 / 热门三页统一取该值（动态页的 `_DynVideoCard` 是另一套自绘卡片，不动）。
2. 回归测试断言从「信息区不溢出」升级为「标题槽 ≥ 38（容得下完整两行）」，旧值 32 会直接失败。
3. 首页数据源切到 Web 推荐流 `/x/web-interface/wbi/index/top/feed/rcmd`：单次列表请求即下发 `pubdate`、`stat.view/danmaku/like`、`rcmd_reason`、`is_followed`，卡片不再需要逐卡补全（点赞不会再一张张蹦出来）。
4. 数据源在首屏决定后固定（Web / App 模型是不同运行时类型，混装会在追加时抛类型错误）；Web 流失败才回退 App 流，此时保留 §11 的逐卡补全兜底。批大小按数据源取 20（Web ps）/ 8（App 保守估计）。

## 十三、反馈轮修正 6：点赞量在封面与底部两处重复（2026-11-01）

### 13.1 现象

同一批卡片里，封面左上角出现「3万点赞」徽章（左卡），底部作者行下方又出现「8782点赞」胶囊（右卡）；点赞量在卡片上出现两个展示位置，用户质疑为何两处都在报点赞。

### 13.2 定因

1. 封面左上角显示的是接口下发的 `rcmd_reason`（Web 流取 `rcmd_reason.content`，App 流取 `rcmd_reason` 字符串），平台有时直接下发「3万点赞」这类**数值型推荐理由**。
2. 底部「X点赞」胶囊是我们自己用 `stat.like` 拼的，与推荐理由是两套来源。
3. 上一轮只在底部加了「推荐理由含『赞』就不显示底部胶囊」的抑制，封面照常显示该理由 → 结果同一信息被拆到两处：有赞理由的卡只剩封面、无理由的卡只剩底部，看起来既重复又位置不统一。

### 13.3 方案

1. `VideoCardV` 新增 `_showReasonOnCover`：封面只放**定性**理由（热门 / 高播放 / 宝藏新作…）；含「赞」的理由不上封面，`已关注 / 新关注` 也不上封面（关注态已由 UP 行的徽章承担）。
2. 点赞统一由底部胶囊展示，取 `stat.like` 精确值；移除原来「含赞理由抑制底部胶囊」的分支。
3. App 流（无 `stat.like`）回退路径：`RcmdVideoItemAppModel.fromJson` 把「3万点赞」解析成点赞数写入 `stat.like`（`_parseCount`），保证回退时仍有点赞且只出现在底部（与上游 PiliPlus 同口径）。
