# 首页推荐流重复加载已有推荐修复复盘（2026-10-26）

## 一、现象

- CVO 反馈：首页推荐信息流「一直在重复加载已有的推荐」，并怀疑与之前「楼中楼查看更多回复重复加载」同类。
- 实机确认两种表现形式（CVO 勾选）：
  1. **下拉刷新后继续下滚，又看到大量刚看过的旧推荐**；
  2. **同一张视频卡片在列表里出现两次以上**。

## 二、定因

先做接口侧排除，再落到客户端代码。证据：

- 用与 App 相同的请求参数（`column=4`、`device=pad`、`build=2001100`、`flush=5`）连续请求 `app.bilibili.com/x/v2/feed/index`，`idx=0..9` 顺序拉取：
  - 每批次 8 条；
  - 跨批次重复仅 1 条（约 1%），**接口本身不重复投喂**；
  - 重启会话（`pull=true, idx=0`）后，新旧会话同 idx 批次重合为 **0/8**。
- 用 Debug 产物实跑启动流程，并读 `D:\Documents\logs\blackbox_api.log`：启动自动补屏共 4 次请求，`idx=0/1/2/3` 严格递增，**请求序列正常，没有同 idx 重放**。

于是重复来自客户端自身，共三处：

1. **刷新合并无去重**（`lib/pages/rcmd/controller.dart` 原 `handleListResponse`）：
   `page == 0` 时把旧列表整体 `addAll` 到新批次后面。新批次里已存在的卡片会被旧列表再追加一次 ⇒ 同一卡片出现两次；
   同时旧列表（最多 300 条）整段保留 ⇒ 下拉刷新后下滚又把刚看过的旧推荐重看一遍。
2. **下滚加载更多无去重**（`lib/pages/common/common_list_controller.dart` 原 `response!.addAll(dataList)`）：
   接口一旦跨批次重叠（实测约 1%），重复条目直接进列表。
3. **刷新与在途请求竞态会回退游标**（`RcmdController.onRefresh` + 基类 `queryData` 的 `isLoading` 守卫）：
   `onRefresh` 先把 `page` 置 0 再调 `queryData`；若此时下滚请求在途，`queryData` 被 `isLoading` 直接吞掉（下拉刷新看起来"没反应"），而在途请求结束后照旧 `page++`，把刚重置的 0 写成 1 ⇒ 此后 `idx` 从 1 重播，**整段已加载批次被重复请求**。

另：`lastRefreshAt` 早就在刷新时被记录，但视图侧从未渲染「上次看到这里」分隔（上游 PiliPlus 有），旧内容与眼前新内容无法区分，加重"在重复加载已有推荐"的观感。

## 三、方案

1. `lib/pages/rcmd/controller.dart`
   - 新增条目唯一键 `_keyOf`：优先 `bvid`（App 接口的 av 卡由 aid 反推），其余卡片用 `goto:param` 区分；
   - 新增 `_addUnique`：按键去重追加，合并后总量上限 `_maxItems = 300`（与原裁剪口径一致）；
   - 刷新路径：新批次在前、旧数据在后，**全局去重**；`lastRefreshAt = 去重后新批次条数`；
   - 下滚路径：先 `removeWhere` 丢掉本批次中已在列表内的卡片，再按原口径裁头；裁头后同步前移 `lastRefreshAt`；
   - `onRefresh` 先等 `isLoading` 收尾再重置 `page`，避免"下拉被吞 + 游标回写"。
2. `lib/pages/common/common_list_controller.dart`
   - 请求发起时记录 `startPage`，成功收尾只在 `page == startPage` 时 `page++`；刷新把游标重置后，旧响应不再能写回游标。
3. `lib/pages/rcmd/view.dart`
   - 恢复上游的「上次看到这里 / 点击刷新」分隔卡：`lastRefreshAt` 处插入一格，点击即刷新；
   - 网格索引做偏移映射（分隔卡之后 `itemIndex = index - 1`），滚到底触发加载更多、移除卡片、`lastRefreshAt` 左移均按真实条目索引处理。

## 六、遗留与踩坑

- 遗留：
  1. 「上次看到这里」分隔卡为首版自绘（`surfaceContainerHigh` + 12px 文案），实机观感待 CVO 复看；
  2. 有限 feed 的固有取舍未变：常驻 300 条后新批次进来会裁掉头部，回滚到顶部看到的是较新批次；
  3. 完全被过滤的空批次（整批广告 / 整批黑名单 UP）在「永不结束」语义下仍不推进 `page`，理论上会以同一 idx 重试；本轮未触发（实测接口每批均有有效卡），如需彻底兜底可单开一轮。
- 踩坑：
  1. 一开始把「重复」归因于接口重复投喂，实测 10 页仅 1 条重合，推翻该假设；
  2. 匿名态接口 `args.bvid` 为空，但模型已用 `IdUtils.av2bv(aid)` 反推，故 `bvid` 可安全作为去重键（勿被空 `args.bvid` 误导）；
  3. 去重键不能只用 `param`：直播/番剧卡的 `param` 含义不同，需带 `goto` 前缀。

## 七、补充（同日第二轮反馈：下滚加载变慢，「几乎一张一张」）

- 现象：去重生效后重复消失，但下滚加载显著变慢，卡片近乎逐张出现；下拉刷新同样变慢。
- 定因：
  1. **下拉刷新被轮询等待拖慢**：第一版 `onRefresh` 用 `while (isLoading) await 40ms` 等在对途请求收尾，指示器在整个等待期（最长一次请求时长）持续旋转；
  2. **每批净新增过少**：服务端在同一游标区间会回送部分已看过的卡片，去重后单批只剩少量新卡；而网格只在「最后一张卡进入视口/缓存区」时触发加载，于是一次滚动只补一行甚至更少，观感即「一张一张」；
  3. 空批次（整批重复或整批被过滤）在原逻辑下 `isEnd=true` 早退且不推进 `page`，无限 feed 会以同一 `idx` 重试。
- 方案：
  - `CommonListController` 改「登记补发」：新增 `deferRefresh()`（`Completer`），`queryData` 收尾（含空批次/异常分支）调用 `_flushPendingRefresh()`，刷新请求不丢、指示器不再被轮询占住；
  - 基类空批次分支推进 `page`（仅 `page == startPage` 时），杜绝同 `idx` 重试；
  - `RcmdController.onLoadMore` 增加**追平补拉**：去重后净新增 `< 6` 时立刻追下一批，单次下滚最多追 3 批（`_minNewPerLoad = 6`、`_maxCatchUp = 3`），保证一次滚动至少补半行以上。
- 验证：`dart analyze` **No issues found!** / `windows --debug` **√ Built**（28.3s）/ `--release` **√ Built**（64.5s）。
- 提交：`6f7662b`；回滚：`git reset --hard 6985694`。
- 取舍：追平补拉多消耗 1~2 次请求换观感；若实测服务端重复率很低，可把 `_minNewPerLoad` 降到 4 或去掉追平。

## 八、补充（同日第三轮反馈：新内容仍「一个一个蹦出来」）

### 8.1 现象

- CVO：追平补拉上线后，「新内容仍然是一个一个蹦出来」。

### 8.2 定因（本轮用登录态接口实测，不再靠推测）

前两轮只有「匿名态探测」结论，本轮改用登录态 `access_key` 复算 App 签名（`AppSign`：参数按 key 排序 → `Uri.encodeComponent` 拼接 → 追加 `Constants.appSec` → MD5，已用日志中的历史请求逐字节校验通过），连续探测 `idx=0..30`：

- 每批 8 条；`idx=0/1` 去重后新增 8/6 条；
- `idx=2~4` 只剩 1/0/3 条；
- `idx=8~20`、`25~30` 长期只剩 **0~3 条**（八条里七条是刚发过的）；
- 偶尔（`idx=5~7`、`21~23`）一次返回 20 条且全为新卡。
- 单批耗时 **736~959ms**（均值约 820ms）。

即**服务端在同一会话内大量回送已看过的卡片**，客户端去重是必要的，但去重后单批有效产出只有 0~3 条，而串行追平每批要 0.8s ⇒ 有效吞吐约 1~3 卡/秒，观感就是「一张一张往外蹦」。这也是前两轮加大追平阈值却不见效的原因：瓶颈是**每批产出太少 + 请求串行**，不是批次数量。

补充实测（并发可行性）：

- 同一 `idx=40` 连续两次请求，返回内容重合 0 条 ⇒ `idx` 并非严格游标，服务端按会话给出「下一批」；
- 并行 6 批（`idx=42..47`）耗时 **1219ms**，原始 60 条、去重后 **53 条** ⇒ 并发能把有效吞吐提高约 4~8 倍。

另发现上一版的两处结构性隐患：

1. **裁头（`removeRange(0, overflow)`）会让 `maxScrollExtent` 回缩而滚动偏移不变** ⇒ 用户「瞬间又到底」→ 立刻再次触发加载 → fetch/裁头/重建/再触发的小循环，每次只落很少的卡；常驻 300 条后该循环会自我维持。
2. 追平循环里每批都 `loadingState.refresh()` ⇒ 每批单独重建网格，视觉上是分批抽搐，而不是一次性成块。

### 8.3 方案

1. `lib/pages/rcmd/controller.dart`
   - `onLoadMore` 改为**并发补货**：一次 `Future.wait` 拉 `_prefetchBatches = 4` 批（`idx = page .. page+3`），汇总后按 `_keyOf` 全局去重，**一次性 `list.addAll` + 单次 `loadingState.refresh()`**，整轮只重建一次 UI；`page` 推进 4。
   - 新增 `_fetchBatch(idx)`：单批失败返回空列表，不打断当前列表（下次滚动重试），不再走「子类改基类状态」的追平循环。
   - **取消下滚路径的头部裁剪**，`_maxItems = 300` 仅用于刷新合并时旧内容保留上限（与上游一致）；移除 `_minNewPerLoad`/`_maxCatchUp`/`_lastAppended`。
   - `handleListResponse` 只保留刷新（`page == 0`）合并分支。
2. `lib/pages/common/common_list_controller.dart`
   - `_flushPendingRefresh` 提升为 `flushPendingRefresh`（public）：`RcmdController.onLoadMore` 自管 `isLoading` 后仍需在收尾补发被挡下的下拉刷新，否则刷新指示器会永久等待。
3. `lib/pages/rcmd/view.dart`
   - 新增滚动监听 `_onFeedScroll`：距底不足 **1.5 屏**就发起补货（`onLoadMore` 内部有 `isLoading` 互斥，不会形成请求风暴）；`itemBuilder` 里的末卡触发保留，用于首屏内容不足一屏、无法滚动时的自动填充。
