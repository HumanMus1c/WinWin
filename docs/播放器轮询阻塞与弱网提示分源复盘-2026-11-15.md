### 2.2 阻塞点：100ms 轮询内的同步 FFI

`pollTrace` 正常 tick 约 8ms，卡顿窗口内：

| tick | 总耗时 | 分段（累计 dt） |
|---|---:|---|
| #17334 | 459ms | after-position 52ms、after-buffered 219ms、after-drift 327ms |
| #17335 | 1716ms | after-position 289ms、after-buffered 445ms、after-drift 1534ms |

- #17335 在 `51.748` 记录 `AUDIO-ALIGN seek`，`52.657` 才到 `after-drift`
  → 音频硬归位 seek 的同步段约 **909ms**；
- 音频 seek 状态事件持续到 `54.07`，UI 心跳在 `52.948` 才恢复；
- `22:53:48.836 → 22:53:52.948` UiTick 中断 **4112ms**。

结论：阻塞来自 `player.position` / `bufferedTimeRanges()` / 音频
`position`、`mediaStatus` 与音频 `seek` 这些**同步 FFI 调用**，不是 CPU、内存或网络。

### 2.3 「网络较慢」来自 HTTP 分支

- `22:53:54.175` `pos=404283`、`buffered=419699` → 缓冲领先约 **15.4 秒**；
- `_bufferLowForWeakNetwork`（门槛 5 秒）为 false，播放路径不会上报；
- `22:53:54.763` 的提示只能来自共享 `WeakNetworkDetector` 的 HTTP 分支
  （任意请求 ≥3 秒即提示），与播放缓冲无关。

### 2.4 音频硬归位放大

- `DRIFT hard drift=-1540` 越过旧阈值 `driftHardMs=1500` → 硬 seek；
- seek 期间视频继续前进，落地后又差 3.16 秒 → 第二次硬 seek；
- `_alignAudioInstance` 用 `pos=0` 直接 resume，进一步促成二次判定。

## 三、修复方案

1. **`bufferedTimeRanges()` 500ms 节流**：其余 tick 用单次 `player.buffered()`
   相对估算，降低最贵的缓冲区间查询频率（`player_controller.dart`）。
2. **音频 drift 采样 4Hz**：`_lastAudioDriftSampleAt` 节流，避免 100ms 轮询每次都读
   音频 `position` / `mediaStatus`。
3. **硬归位阈值 1500→2500ms**：1.5~2.5s 漂移走速率修正，避免用一次 UI 阻塞
   换一次音频瞬跳（`seek_probe.dart`）。
4. **硬归位预测 + 落地保持**：`_alignAudioInstance(hard: true)` 按
   `_audioSeekAvgMs` 预测视频在 seek 期间的推进量；完成后 500ms 内跳过 drift 判定；
   resume 日志改用有效基准，避免二次硬定位。
5. **弱网提示分源**：`WeakNetworkDetector` 记录来源与 path；HTTP 仅 playurl 等
   播放关键请求或**连续两次**慢请求触发；超时仍直接触发；单次 3s 成功响应不再弹。
6. **关闭 `pollTrace`**：本轮取证完成，避免 50 行/秒同步 flush 放大停摆。

## 五、遗留与踩坑

1. **同步 FFI 的根因仍在**：mdk 内部锁被占用时 `position` / `buffered` 仍可能达数百 ms；
   本轮只是降低调用频率与成本，未把读取移出 UI isolate。
2. **硬归位 seek 仍是同步 FFI**：仅对 >2.5s 漂移触发，并做了预测，但单次仍可能阻塞
   约 0.9s；彻底解决需独立 isolate / mdk 回调或上游修复。
3. **fvp 0.38.1 → 0.40.0** 的更新日志未在本地缓存，升级前需核对上游改动与回归面。
4. **无播放器时的 UI 停摆**（11-15 00:57~02:40 多次 2.5~22s，无轮询记录）仍为另案，
   与本轮播放路径无关。
5. `pollTrace` 已关闭；若后续仍需取证，只建议短期开启并及时取日志（trace.log 5MB 轮转）。
