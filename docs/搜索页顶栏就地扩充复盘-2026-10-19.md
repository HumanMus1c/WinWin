# 搜索页顶栏就地扩充复盘 —— 让「搜索」不再跳页，而在原地长出来

- 日期：2026-10-19
- 快照基准：改动前 HEAD = `662ebad`（设计文档 v3；worktree clean，回滚见第五节）
- 触发：CVO 指令「开始设计改造搜索页，将其从二级页面改为首页顶栏的变形高度扩充（非搜索框高度撑开），隐藏分类 TAB 栏，将扩充的区域用于展示搜索历史和热搜……搜索历史中的直接从历史搜索访问的用户胶囊需要和搜索历史词要完整继承和保留」（设计见 `docs/搜索页顶栏就地扩充-设计文档-2026-10-19.md`；批准后「开始改造」）

## 一、现象

设计定案前没有可复现的「缺陷」，要复现的是**目标形态**：

| 观测 | 改造前 | 目标 |
|---|---|---|
| 点首页搜索框 | `Navigator.push(SearchPage())` 跳二级页 | **原地**在顶栏长高一块，不跳页 |
| 长高的是谁 | — | **整块顶栏容器**（搜索框行恒 38 不变） |
| 分类 TAB | 常驻 | 搜索态**收起**，退出**原样恢复**（位置 + 选中项） |
| 扩充区内容 | — | 自上而下：搜索历史（词）→ 用户胶囊 → 大家都在搜（两列网格） |
| 提交搜索 | 停在搜索页 | 保存历史 → **收起搜索态 → 进搜索结果页** |
| 背景 | 无 | 顶栏后方内容**压暗（含首页「首页」标题行）**，点遮罩收起 |
| 扩充区高度 | — | **设上限、绝不顶出屏幕**；超出时**末尾省略**（不溢出、不硬塞滚动条） |
| 热搜排版 | 带 1/2/3 序号的竖列（`MiuixBasicComponent`） | **照搬上游 PiliPlus 新排版**：两列网格、无序号 |
| 数据 | 历史词 + 用户胶囊（存档于二级页） | **只换展示位置**，读写/去重/上限/顺序/字段全照旧 |

## 二、定因

不是"坏在哪"，而是"为什么必须这样拆"。三条结构性原因，决定了本次改动面：

1. **压暗压不到「首页」标题行**。该行是 `AppScaffold` 的顶部安全行（`topStripHeight = 50`），在骨架里位于 `Column[strip, Expanded(body)]` 的**第一段**；页面 `body` 再怎么 `Stack` 也覆盖不到它。⇒ 只能在骨架里开一个**浮层槽位**（`overlayBuilder`），让页面把自己的浮层画在「安全行 + 内容」之上。
2. **内容一分为二（首页 + 独立搜索页）会立刻漂移**（违 P4）。「历史 + 用户胶囊 + 热搜 + 联想」若各写一份，必然两边口径不同。⇒ 抽成**唯一实现** `SearchContentPanel`（默认参数下即有内边距），两个宿主共用：首页顶栏（传 `maxHeight` 限高）/ 独立搜索页（外层可滚动）。
3. **数据口径唯一来源已是现成的**（`lib/pages/search/services/search_history_service.dart`：`SearchKeywordHistory` 键 `searchHistory`、上限 20、去重前置；`SearchHistoryService` 键 `searchHistoryUsers`、上限 20、四字段 `mid/name/face/timestamp`）。⇒ 契约即"**不动它**"，宿主只调用，`search_panel.dart` 的写入点也保留。

热搜还差两件事：模型缺字段（`show_name` / `show_live_icon`）、上游排版是 Material 写的（`InkWell` + `Material(transparency)` + `livingRect` 位图资源），搬到本项目必须自绘。

# 第二轮（实机反馈修复）—— 扩充区高度冗余 + 失焦/Esc 退出失效

- 日期：2026-10-19
- 快照基准：改动前 HEAD = `856185a`（worktree clean；回滚见 §十）
- 触发：CVO 实机反馈（截图 `1792423636694-ff096869.png` 宽屏 / `1792423636697-fd145923.png` 窄屏）：「① 点击搜索框进入搜索态后，扩充的区域有些冗余了，宽屏和窄屏形态下，扩充区域都超出了『大家都在搜』最后一行好几行的空余；② 搜索态的搜索框失去焦点后没有退出搜索态，导致点击到导航栏时即便搜索框丢失了焦点但搜索态没有退出，导致按键 `Esc` 无法退出搜索态，降低了操作效率。」

## 六、现象

| # | 观测 | 量化 |
|---|---|---|
| 1 | 扩充区下方**恒有多余空白**，宽屏 / 窄屏都有 | 空白 = 上限高度 − 内容高度，**与内容多少无关**（内容越少空白越多） |
| 2 | 搜索框失焦后搜索态**不退出**；此后 `Esc` 也**无法**退出 | 两条症状同源：退出路径缺"失焦"这条，且 `Esc` 被绑死在焦点链上 |

## 七、定因

1. **高度冗余 = 布局原语默认值**（不是数值写错）。限高链 `ClipRect > ConstrainedBox(maxHeight) > OverflowBox(topCenter)` 里的 `OverflowBox` **默认 `fit: OverflowBoxFit.max`**；Flutter 源码 `rendering/shifted_box.dart`（`RenderConstrainedOverflowBox`）实证：
   ```dart
   bool get sizedByParent => switch (fit) {
     OverflowBoxFit.max => true,          // ← 默认走这支
     OverflowBoxFit.deferToChild => false,
   };
   Size computeDryLayout(constraints) => switch (fit) {
     OverflowBoxFit.max => constraints.biggest,   // ← 取"最大"而非"内容"
     OverflowBoxFit.deferToChild => child?.getDryLayout(constraints) ?? constraints.smallest,
   };
   ```
   ⇒ 该框**永远占满上限高度**，与内容无关。原实现的"限高"只保证了"不超出屏幕"，没保证"不冗余"。
2. **`Esc` 失效 = 键事件只沿当前主焦点节点的祖先链派发**。原实现把 `Esc` 挂在搜索态子树的 `CallbackShortcuts` 上：焦点在输入框 / 面板内时生效；焦点一旦被抢走，搜索态子树不在链上，事件继续上抛给**既有全局路由器** `AppEscapeScope`（`lib/core/input/app_escape_scope.dart`，挂在 `MaterialApp.builder`，四层：①栈顶弹层 → ②`EscapeLayerRegistry` 二级浮层 → ③输入框失焦 → ④`maybePop`）。此刻 ①无弹层、②搜索态**未登记**、③`isTextInputFocused()` 为假、④无可返回路由 → 落到 `Esc unhandled (root)`，搜索态纹丝不动。**违背 P4：同一个"Esc 关闭"概念被定义了两处。**
3. **失焦不退出**：退出路径原本只有 `Esc` / 点遮罩 / 提交三条，缺"失焦"。而导航栏与底栏在 `MainLayout` 里位于页面 body **之外**（宽屏 `AppNavRail(80)`、窄屏 `Positioned` 底栏），压暗遮罩盖不到 ⇒ 点它们既走不到任何退出路径，又抢走焦点。

## 八、方案

**改动面 2 文件**（+ 本文档 + 进度表）：

| # | 文件 | 动作 | 要点 |

## 遗留与踩坑（第二轮）

- **"失焦即退出"是本轮新增的产品口径**（原设计文档只写了 `Esc` / 遮罩 / 返回三个出口）。两重护栏及依据：① Windows 上点击普通区域**不会**抢焦点（`EditableText` 的默认 `onTapOutside` 在桌面端是空实现）⇒ 不会因点面板内「刷新 / 清空 / 历史 ✕」而误收起（`MiuixPressable` 内部的 `FocusableActionDetector` 也不请求焦点，已查依赖源码）；② 窗口失活时 `FocusManager` 会**挂起主焦点**（`_suspendedNode`，源码实证）⇒ 加 `lifecycleState != resumed` 时忽略，避免"切到别的应用再回来，搜索态没了"。
- **点设置齿轮**（若其内部请求焦点）会顺带收起搜索态 —— 属可接受的"离开搜索上下文"语义；若 CVO 认为不妥，下一轮把它纳入"面板内部"白名单。
- **`lifecycleState` 护栏依赖时序**：`WidgetsBinding` 先落状态再广播监听（`FocusManager` 作为 `AppLifecycleListener` 后收到），故失焦回调里读到的已是新状态。若后续 Flutter 调整该顺序，本护栏需复核。
- **仍未做「改动后截图 vs 原截图」逐像素回归**（本会话无 VQA / OCR 工具：`read_file` 读 png 直接报错、连接器无可用 OCR）⇒ 高度是否"贴底"只能由 CVO 实机复看。
- **未跑 `flutter test`**（本机测试宿主历史性崩溃，沿用静态分析 + 双编译替代）。

## 总结（第二轮）

两个问题，根因完全不同。一个是**布局原语默认值**的坑：`OverflowBox` 默认"撑满父级"（`fit: max`），我们把它当"限高容器"用，语义正好相反 —— **"限高"于是退化成"恒为上限高"**；这种退化在任何分辨率下都表现为"多出空白"，且与内容无关，所以宽屏窄屏一起中招。修法不是调数值，而是把 `fit` 显式钉成 `deferToChild`，让它回到"按内容、上限截断"。另一个是**重复造了一条 Escape 旁路**：项目早有全局 `Esc` 分层路由器（`AppEscapeScope` + `EscapeLayerRegistry`），搜索态本就属于"无路由承载的 Stack 伪浮层"，该登记进第 2 层；原实现自挂 `CallbackShortcuts`，等于把 `Esc` 绑死在焦点链上，焦点一被导航栏抢走就失效，正违 P4。两处修完：`dart analyze` 0/0、Debug 31.2s / Release 80.4s 双 √，可一键回到 `856185a`。

**一句话教训**：先读源码确认"看起来对"的默认值，再决定要不要自己动手 —— 本轮两个问题，一个吃默认值、一个吃重复实现。

# 第三轮（实机反馈修复）—— 点击面板条目即失焦并误收起（点击被吞）

- 日期：2026-10-20
- 快照基准：改动前 HEAD = `c0d198b`（worktree clean；回滚见 §十五）
- 触发：CVO 指令「调查搜索框的搜索态，点击搜索弹层的历史搜索词，以及用户胶囊，以及大家都在搜的条目，会导致丢失焦点并退出搜索态这个问题。」；调查后 CVO 拍板 **A 方案（F1 + F2）**

## 十一、现象

| # | 观测 | 说明 |
|---|------|------|
| 1 | 搜索态下点**历史词 / 热搜条目** | 不进结果页，只见搜索态收起 |
| 2 | 搜索态下点**用户胶囊** | 不进用户空间，只见搜索态收起 |
| 3 | 三者公共表现 | **「焦点丢失 + 搜索态退出」，且点击本身无任何动作** |

## 十二、定因（一条链，四个环节）

1. **输入框的 TapRegion 只圈住输入框本体**：`MiuixTextField` 内部是 SDK `TextField` → `EditableText`，其 `TextFieldTapRegion(groupId: EditableText, onTapOutside: _hasFocus ? … : null)`（`editable_text.dart:5849`）只覆盖输入框；面板里的历史词 / 用户胶囊 / 热搜条目全在**组外**。
2. **桌面端"点外侧"默认就是失焦——不是空实现**：`_EditableTextTapOutsideAction.invoke`（`editable_text.dart:6876`）对 `windows/linux/macOS` 就是 `intent.focusNode.unfocus()`；**真正空实现的是 `onTapUpOutside`**。第二轮复盘把二者混为一谈（"桌面端什么都不做"），是本 bug 得以潜伏的直接原因。
3. **「失焦即退出」同步收起并重建 Row2**：`home_page.dart:_onSearchFocusChanged` → `_exitSearch()`（`_searchMode=false` + `setState`）；`_HomeHeader` 的 Row2（`AnimatedSize`）由 `SearchContentPanel` 换回分类标签，被按下的条目**当场卸载**。
4. **按压动作在 tap-up 才触发，此时控件已不存在**：`MiuixPressable`（`miuix_pressable.dart:361 onTapUp`）与 `AppInputChip._handleTap` 都在 `onTapUp` 才调 `onPressed` ⇒ 识别器随元素销毁 ⇒ `onSubmit` / `push(MemberSpacePage)` 永不执行。

**净效果**：焦点丢失 + 搜索态退出 + 点击被吞。

## 十三、方案（A｜F1 + F2，单文件）

| # | 点 | 要点 |
|---|----|------|
| F1 | **顶栏并入输入框 TapRegion 组** | `_HomeHeader.build` 外层包 `TextFieldTapRegion`（默认 `groupId == EditableText`，与输入框同组）；面板内按下即"内侧"，不再触发 `onTapOutside → unfocus`；组外（遮罩 / 导航栏 / 底栏）仍走默认失焦 ⇒ 第二轮"点导航栏即收起"语义**不变**。零新依赖（`TextFieldTapRegion` 由 `package:flutter/widgets.dart` 导出）。 |
| F2 | **路由 / 对话框压顶不算"离开"** | `_onSearchFocusChanged` 增判 `ModalRoute.of(context).isCurrent`：本页已非最上层（`push` 用户空间 / 清空确认框 / 设置页抢走焦点）→ **保留**搜索态，返回后原样还在；只有**原地**失焦（点导航栏 / 底栏）才收起。 |

**不动**：数据口径（`search_history_service.dart`）、`search_content_panel.dart`、`search_page.dart`、既有全局 Esc 机制——均为唯一来源 / 共用件。

## 十七、定因（两个状态由不同 widget 渲染，几何不同源）

3. **焦点环叠加**：`_borderController` 驱动 `MiuixSquircleBorder` 的 `side`（`borderWidth = progress × 2`），且 squircle 描边**沿路径居中绘制**（`miuix_squircle.dart`）⇒ 有 ~1px 溢出布局矩形，视觉上"高/宽各 +2px"。

- **同一视觉元素被两种 widget 渲染，是这次偏移的根**：常态自绘、聚焦用组件；组件又有"有前导图标≠加内距"的隐式默认。教训：**同一处外观若有两套渲染路径，必须把几何写成显式共享常量**，不能各写各的 padding。
- **AGENTS.md 规则 5 落地**：Release 首跑因残留 `winwin.exe` 锁 DLL 失败 ⇒ 已按 **PID 精确结束**（非按镜像名批量杀），复跑即过。
- **仍未做逐像素回归**（无 VQA/OCR）；`flutter test` 未跑（测试宿主历史性崩溃）。

## 总结（第四轮）

CVO 看到的"尺寸和位置偏移"，真身是**两套渲染路径的几何不同源**：常驻的"假搜索框"是我们自绘的 `Container`，一聚焦就换成 `MiuixTextField` 包装的输入条；而后者在**有前导图标时不给图标加水平内距**（`insideMargin.left` 只作用于无图标时的文本区），于是图标左缘 12→0、占位 40→20，肉眼就是"整体左跳一下"。修法不是调某个 padding 的数值，而是**把框内左边距与图标—文字间距抽成唯一常量**，两条渲染路径都引用它：`prefix` 自带 `left=_kSearchRowInset / right=_kSearchIconTextGap`，与常态框逐像素对齐。顺带把 `38` / `radiusFull` 等魔法数一并收敛。

**一句话教训**：同一处外观允许有两条渲染路径，但几何**只有一个来源** —— 否则"看起来一样"的两块，换手就错位。

## 补充（同日第二轮反馈）：输入光标高过输入框 + 占位文本下偏

- 触发：CVO 在第四轮产物上复看后报两点 —— ① 「搜索框的文本光标高度明显大于搜索框高度，应该对齐占位文本和输入文本大小」；② 「占位文本在聚焦搜索态时会下偏移」。
- 起点 HEAD `c189ece`（worktree clean）。

### 廿一、定因（一个根因，两个症状：字号不同源）

聚焦态 `AppCapsuleTextField` **没有传 `textStyle`** ⇒ `MiuixTextField` 回退到 `MiuixTheme.textStyles.main` = **`TextStyle(fontSize: 17)`**（`miuix_text_styles.dart:156`；`miuixBridgeTextStyles` 只注入 `fontFamily`，不改字号）。而占位文本是 **13px**。于是：

| # | 症状 | 机制 |
|---|------|------|
| ① | 光标比输入框还高 | 光标高度随文本行高走；17px 行高（CJK 字体约 24px）塞进 `38 − 8×2 = 22px` 的文字区 ⇒ 光标溢出框体上下缘 |
| ② | 占位文本下偏 | 输入文本 17px 与占位 13px **行盒不同高** ⇒ 二者在文字区内的视觉基线错位，"占位"相对"输入文本应有的位置"看起来下移 |

即：**同一处文字有两个字号**（占位 13 / 输入 17），与第四轮的"几何不同源"同源同病。

### 廿二、方案（同文件，字号收敛到唯一来源）

- 新增常量 `_kSearchTextSize = 13`，常态占位、搜索态占位、搜索态输入文本**三者共用**；
- 聚焦分支补 `textStyle: const TextStyle(fontSize: _kSearchTextSize)`（光标随之收到 13px 行高，不再高过框）；
- 聚焦分支补 `hintStyle: TextStyle(fontSize: _kSearchTextSize, color: searchFg.withValues(alpha: 0.7))`，使搜索态占位与常态占位**字号 + 颜色逐项一致**（此前搜索态占位走 `onSurfaceVariant`，也是一处不同源）。

### 廿三、验证

- `dart analyze lib` → **No issues found!**（0 错 0 警告）
- `windows --debug` → **√ Built**（28.4s）
- `windows --release` → **√ Built**（17.1s）（首跑被残留 `winwin.exe` PID 30152 锁 `WebView2Loader.dll` 失败，按 **PID 精确结束**后复跑成功）
- 实机验证（用户操作）：聚焦搜索框 → 光标高度应≈一行文字、不再溢出框体；占位文本与输入文本同大小、同一基线；退出再进入无位移。

## 遗留与踩坑（第四轮·补充）

- **"字号不同源"是几何不同源的孪生兄弟**：一处外观的**字号/颜色**同样必须在两条渲染路径间共享，否则切换瞬间"文字忽大忽小、占位忽高忽低"。
- 残留：`AppCapsuleTextField` 默认仍以 `textStyles.main`(17px) 作为输入文本（登录页/搜索页等**有意**用 17px，故不改全局默认，只在首页搜索框显式收窄到 13px）；占位自绘叠加层与输入文本的对齐由此显式字号保证。
- 仍未做逐像素回归（无 VQA/OCR）；`flutter test` 未跑（测试宿主历史性崩溃）。

**一句话教训（补充）**：几何要同源，**字号与颜色也要同源** —— 视觉"跳一下"往往不是布局错，而是同一元素两套样式各写各的。

## 补充二（同日第三轮反馈）：常态/搜索态往返切换，占位文本仍位移

- 触发：CVO 在 `43903b0` 产物上复看后报「常态/搜索态往返切换时占位文本仍然位移」。
- 起点 HEAD `43903b0`（worktree clean）。

### 廿四、定因（外层 `Stack` 顶对齐 vs 占位层居中）

现象仍在，说明前两轮修的"左右位移 / 字号"都不是它的根。真身在 `AppCapsuleTextField` 的外层 `Stack`：

1. **输入框被顶对齐**：`Stack` 用的是**默认 `alignment: topStart` + `fit: loose`**；盒子被上层 `SizedBox(height:38)` 夹成 38，而输入框**固有高 ≈ 36**（`insideMargin` 8×2 + 行/图标 20）⇒ 输入框被钉在盒子**顶部**，内容比盒心高约 `(38−36)/2 = 1~2px`。
2. **占位层居中于整盒**：自绘占位是 `Positioned.fill` + 上下对称 padding(8,8) + `Align(center)` ⇒ 居中于**整个 38**。
3. **两者不同轴心** ⇒ 占位相对输入文本/图标**下偏** `(盒高−固有高)/2`；常态框（`Container` 的 `Row` 默认 `crossAxisAlignment.center`，内容居中于 38）没有这个问题 ⇒ 往返切换即见"占位跳一下"。

### 廿五、方案（共享组件，一行对齐修正）

`lib/ui/components/app_components.dart`：把 `AppCapsuleTextField` 外层 `Stack` 显式设为 **`alignment: Alignment.center`**，使"固有高 < 盒高"的输入框与占位叠加层**同轴心**（都居中于盒）。不改尺寸逻辑（`fit` 仍为 `loose`），故**无无界高度风险**；仅当"盒高于内容"时生效，语义上本就是胶囊输入条应有的居中行为。

### 廿六、验证

- `dart analyze lib` → **No issues found!**（0 错 0 警告）
- `windows --debug` → **√ Built**（31.2s）
- `windows --release` → **√ Built**（67.8s）（构建前按 **PID 48516** 结束残留 `winwin.exe`）
- 实机验证（用户操作）：常态点搜索框、聚焦、`Esc`/点遮罩退出，反复往返 → **占位文本应纹丝不动**（与图标、输入文本同轴心）。

## 遗留与踩坑（补充二）

- **同一 bug 现象连报三轮，才挖到"轴心"这一层**：前两轮分别只看到"左右位移"与"字号不同源"，都是真的，但都不是"上下跳"的根。教训：**同一处有叠加层（overlay）时，先核对"叠加层与本体是否同轴心"**，而不是逐个改 padding 数值。
- 影响面复核：`AppCapsuleTextField` 的其它调用点（登录页 ×4 / 搜索页 / 结果页）——该改动**只在"传入的盒高 > 内容固有高"时**把内容由"顶对齐"改为"居中"，其余情况（含无界高度）逐像素不变。
- 仍未做逐像素回归（无 VQA/OCR）；`flutter test` 未跑（测试宿主历史性崩溃）。

**一句话教训（补充二）**：叠加层与本体必须**同轴心** —— 一个居中、一个顶对齐，差的就是那 1~2px 的"永远在跳"。
