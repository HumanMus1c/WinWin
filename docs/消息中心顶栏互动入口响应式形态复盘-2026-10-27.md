# 消息中心顶栏互动入口响应式形态复盘 — 2026-10-27

## 一、现象（需求）

消息中心（`WhisperPage`）顶栏合并栏的「四个互动入口」（回复我的 / 艾特我的 / 点赞我的 / 系统消息）在宽屏桌面窗口下仍按 `MainAxisAlignment.spaceAround` 铺满整行：图标被均匀拉开到整窗宽，入口之间出现大片空白，与下方左对齐收缩的 TAB 胶囊、首页合并栏的紧凑观感不一致。

CVO 要求：

1. 窄屏移动端默认形态 = 「四个互动入口全宽均布」+「TAB 栏全宽形态（TAB 栏改进之前的形态）」；
2. 当前是宽屏桌面端 → 四个互动入口改为**紧凑的非全宽形态**。

## 二、定因

- 互动入口行沿用了 PiliPlus `WhisperPage` 的移动端写法（`spaceAround` 铺满整行），没有按窗口宽度分形态；该写法在手机上能最大化手指命中面积，但在 ≥700 逻辑宽度的桌面窗口下会把 4 个入口拉到整行两端，观感松散。
- 下方 TAB 栏（`SessionFilterBar` → `AppTabStrip`）已按 `kAppTabBreakpoint = 700` 分形态：宽屏为收缩胶囊、窄屏为宽体页签；但互动行没有接入同一断点，导致同一顶栏内「入口全宽 / TAB 收缩」两种宽度策略并存。

## 三、方案

只改 [view.dart](file:///D:/Documents/GitHub/WinWin/lib/pages/whisper/view.dart#L227-L292) 的 `_buildEntries`：

- 形态判定复用全局 TAB 体系的同一断点与同一口径——`resolveAppTabForm(context) == AppTabForm.rail` 即宽屏（`MediaQuery.sizeOf` 整窗宽 ≥ `kAppTabBreakpoint` = 700），不再另写阈值；
- **宽屏（rail）**：四项改为固定间距（`Style.xxl` = 32）× 左对齐的紧凑组，不再被父级宽度拉开；
- **窄屏（wide，<700）**：保持原 `spaceAround` 全宽均布（移动端默认形态），零改动。

TAB 栏侧**无需改代码**，现状即满足要求：`SessionFilterBar` 未强制 `form`，窄屏走 `AppTabForm.wide`（`MiuixTabRow`，项宽 76–98），8 个分类的合计宽度（≥ 76×8 + 8×7 = 664）恒大于 <700 窗口下的可用宽（≤ 约 635），`AppTabStrip._resolveRowWidth` 取 `min(total, maxWidth)` 后被钳到可用宽 ⇒ 容器在窄屏**始终是改进之前的全宽形态**；宽屏则走 rail 收缩胶囊（即当前截图形态）。因此本轮只切互动入口，TAB 栏不动。

> `_headerReserve` 不受影响：互动行只改水平分布，行高（头像 52 + 间距 6 + 标签行 ≈ 20）与 TAB 行高（42）均未变。

## 六、遗留与踩坑

遗留：

1. 窄屏形态在本机只能把窗口拖到最小 640 触发（`main.dart` 的 `minimumSize`），实机窄屏观感待 CVO 复看；
2. 紧凑组的间距取 `Style.xxl`(32) 为当前观感值，若后续觉得偏疏/偏密，只改该常量即可；
3. 紧凑组按合并栏内容区左边缘落位（外层 `Padding` 12），与 TAB 胶囊容器左边缘（8）相差 4px；因入口自身带 8px 内距，视觉上不构成明显错位，暂不做二次对齐。

踩坑：

1. **不要给互动行另写断点**：项目内宽/窄切换的唯一来源是 `kAppTabBreakpoint` / `resolveAppTabForm`（`home_chrome_metrics.dart` 也是同一口径），另写 600/840 会让同一窗口下首页、消息中心的切换时机不一致；
2. `resolveAppTabForm` 读的是 `MediaQuery.sizeOf`（整窗宽），不能用 `LayoutBuilder` 的控件约束——合并栏有左右内距，按控件宽判定会提前切换。

## 七、总结

互动入口从「全端 spaceAround 铺满」改为按窗口宽度分形态：窄屏保持全宽均布（移动端默认），宽屏改为固定间距左对齐的紧凑组；断点复用全局 TAB 体系（700），TAB 栏本身在窄屏已天然是改进之前的全宽形态、宽屏是收缩胶囊，故本轮零改动。静态分析 0 错 0 警告，Windows debug / release 双编译通过。
