# 弱网缓冲态保持与音画缓冲同步复盘（2026-09-26）

> 触发场景：弱网（火绒 NetFlow 对 WinWin 进程限速）下播放视频时，
> ① 转圈消失并出现中央大播放按钮；② 音频脱离视频缓冲态继续播放；
> ③ 恢复网络后音画「一卡一卡」，且额外出现一条鬼影音频（流畅播放到视频尾端又从头继续）。
> 修复文件：`lib/pages/video/player_controller.dart`（全部改动集中于此）

### 1.3 根因链

1. 弱网下视频位置「缓慢步进」（远低于可流畅播放速率），但旧判定只看「有无推进」⇒ 缓冲态反复进入/解除（转圈闪、播放按钮现）；
2. 音频同步块被 `player.state == playing` 门控：mdk 状态一变就整块失效，且恢复条件过松 ⇒ 音频脱缰、恢复后 resume/pause 抖动（一卡一卡）；
3. 四个鬼影音频来源叠加：主实例被误挂外挂音轨（①）、音频自愈失败误播（②）、播放态直接 seek 残留旧材料（③）、播完/换源不停止音频实例（④）。

## 2. 设计修复计划

### 2.1 方案（弱网判据 + 音频主控 + 鬼影根除）

1. **流速滑窗（新基础设施）**：以「media 推进速率 vs 墙钟」量化弱网——窗口 2000ms / 最小跨度 1500ms；期望速率 = 倍速基速。
   - 健康：rate ≥ 0.75×期望，连续累计 ≥1.2s 才允许**解除**缓冲态；
   - 不健康：rate < 0.5×期望，连续累计 ≥0.8s **进入**缓冲态；
   - 灰色地带（可勉强播）：维持现状（不清健康累计，减少卡死在缓冲态的概率）；
   - 窗口未知（起播/seek/暂停后）：乐观放行，不影响正常加载解除。
2. **缓冲态保持与挂起抑制**：
   - 4 个解除点（轮询×2、`stalled→正常`、`buffered 就绪`）统一加 `_flowAllowsBufferingClear` 门控；
   - `onStateChanged` 增「缓冲挂起抑制」：`缓冲态 || 流速不健康 || 位置停滞` 且用户意图播放时，不广播 mdk 的暂停态（转圈保持、无大播放按钮）；
   - 「防死锁推动」：缓冲态下 mdk 停 paused ≥3s 时幂等推动 `playing`（节流 3s）；10s 看门狗条件放宽为 `buffered()<=0 || state==paused`。
3. **音频以视频缓冲态为主控**：暂停条件 = `buffering || 视频停滞 ≥400ms`（去掉 `player.state==playing` 硬门控、新增 `!_audioRemountInFlight` 守卫）；恢复条件 = 缓冲解除且流速连续健康，位置容差 ≤1.5s 内直接恢复，超差先**暂停态归位**（2s 节流/3 次上限，超限交重挂）。
4. **鬼影根除**：`_recoverStalledStream` 双轨模式不污染 `_currentAudioUrl`（改专属 `_audioPlayerUrl`）且绝不向主实例挂外挂音轨；`_recoverAudioStalled` 改用专属 URL、**失败不误播**（prepare/seek 失败保持静默）；`_alignAudioInstance` 改暂停态 seek、成功后再恢复；`_handlePlaybackEnded` 兜底暂停音频实例；三分支（单源/双轨/外挂音轨）换源时先 stopped 音频实例并维护专属 URL 槽。
5. **配套语义修正**：`_userIntentPlaying = autoplay`（杜绝「不自动播放」被弱网逻辑误推动起播）；`switchQuality`/HDR 传递播放意图；倍速改变/换源/seek 落地/页面分离时重置流速窗口。

### 2.2 参数表（集中定义，便于实机调优）

| 参数 | 值 | 语义 |
|---|---|---|
| `_flowWindowMs` | 2000 | 采样窗口保留时长 |
| `_flowMinSpanMs` | 1500 | 窗口跨度下限（不足=未知） |
| `_flowHealthyFactor` | 0.75 | rate ≥ 0.75×期望 ⇒ 健康 |
| `_flowUnhealthyFactor` | 0.5 | rate < 0.5×期望 ⇒ 弱网 |
| `_bufferingClearHealthyMs` | 1200 | 解除缓冲态所需连续健康时长 |
| `_bufferingEnterUnhealthyMs` | 800 | 进入缓冲态所需连续不健康时长 |
| `_bufferSuspendPushMs` | 3000 | 挂起后防死锁推动的启动时长 |

### 2.3 关键决策与取舍

| 决策 | 理由 / 取舍 |
|---|---|
| 用「流速」而非「有无推进」判弱网 | 用户报告的本质是「慢速步进时不该被当作在播」；速率窗口天然平滑 mdk 阶梯式位置更新与偶发小停顿 |
| 灰色地带不清零健康累计 | 避免网络在 0.5~0.75 倍率徘徊时永久卡在缓冲态；进入/解除双阈值天然滞回 |
| 挂起抑制复用 seek 冻结思路 | 与项目既有「冻结窗口不广播」语义同源，且片尾/用户暂停路径不受影响 |
| 防死锁推动（3s 节流） | mdk paused 后位置不推进会让流速永远不健康——必须主动推动，否则死锁；幂等、低频，无效由 10s 看门狗重挂兜底 |
| 音频归位改暂停态 | 严格遵守 M1 定因；与用户 seek 的音频归位（已在冻结/暂停态执行、项目称「验证安全」）完全同源 |
| `_recoverAudioStalled` 失败不播放 | 宁可静默等待（冷却重试），也不允许「从 0 起播」的鬼影——这是用户实测「从头播放」的直接来源 |
| 不动 `isPosAdvancing` 定义 | 看门狗/漂移控制仍依赖其语义，本次只为缓冲判定引入流速窗口，缩小改动面 |

## 6. 第二轮修正（实机反馈后 · 2026-09-26）

### 6.1 实机反馈（第一轮后，用户实测）

1. 弱网态：转圈出现 ✔，但视频**无声地继续前进**与停下缓冲交替（转圈下画面仍在走、没有声音）；
2. 恢复网速后：视频先无声播放，声音随后"追赶"同步（滞后对齐、非加速），有小时间维度滞后；
3. 用户判断："声音和视频没有同步缓冲与缓冲长度，导致声音有小时间维度的滞后"。

### 6.2 根因（第一轮引入/遗留）

| # | 根因 | 位置（第一轮产物） |
|---|------|------|
| S1 | **无条件「防死锁推动」**：缓冲态内 mdk 停 paused ≥3s 即推回 playing ⇒ 弱网下推翻 mdk 的缓冲等待，视频消耗已缓冲数据边播边停（音频已同步暂停 ⇒ **无声**）——「前进-停下」交替的根源 | 轮询「缓冲挂起防死锁」块 |
| S2 | **视频无冻结手段**：流速不健康但仍在缓慢推进时不冻结 ⇒ 抖动着播（无声前进） | 同上 |
| S3 | **音频恢复滞后于视频**：缓冲解除需连续健康 1.2s，期间视频已恢复（无声）而音频在等 | `_bufferingClearHealthyMs=1200` |
| S4 | **音频恢复容差过宽**：1.5s 内直接以滞后位置恢复 ⇒「声音小时间维度滞后」 | 缓冲同步恢复分支、AUDIO-UNMUTE |

### 6.3 修正方案（第二轮）

1. **缓冲态视频冻结**（S2）：缓冲态内出现弱网迹象（流速不健康 / 停滞 ≥1s / 底层 stalled）时主动 `paused`（画面停在缓冲点；日志 `BUFFER-HOLD-PAUSE`）。暂停态下 mdk 照常下载缓冲（既有实证）。
2. **流量门控恢复**（S1）：新增**水位窗口**（冻结期间采样 `buffered()`，2s 窗口）——增长率 ≥0.75×期望（下载已能支撑流畅播放）或 水位 ≥20s（网络充裕只是缓冲已满）才推回 playing（2s 节流；日志 `BUFFER-HOLD-RESUME-PUSH`）；半恢复网络下保持冻结等待，不再反复试探。
3. **音画同刻续播**（S3）：推动恢复的同一刻同步恢复音频（容差 ≤0.5s 直连，日志 `AUDIO-SYNC-RESUME-PUSH`；超差先暂停态归位）——消除「视频先无声播放、声音再追赶」。
4. **参数收紧**（S4）：`_bufferingClearHealthyMs` 1200→800；音频恢复容差 1500→500（缓冲同步分支 + `AUDIO-UNMUTE`）。
5. **配套修正**：10s 看门狗回调为「`buffered()<=0`」单一判据（paused 现为缓冲冻结的常态）；`playOrPause` 在缓冲冻结期按用户意图判定方向（否则用户点暂停会被误处理成恢复播放）。

### 6.4 参数表（第二轮新增/调整）
