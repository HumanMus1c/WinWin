## 一、现象（背景与起点）

Phase 0-4 + Phase 7 已完成；MD3 库级退役（L0 / B1~B7）已于本批前收官（闸门 0）。
`docs/移植开发计划.md`「待推进工作」#1 = **Phase 5 下载系统（0%）**。

WinWin 侧已有 HTTP 前置 `lib/http/download.dart`（`DownloadHttp` +
`DownloadMediaInfo` / `DownloadVideoStream` / `DownloadAudioStream`），其类文档
明确标注"Phase 5 下载系统实施时补齐"。即：**接口已能拿到播放地址，但任务模型、
队列 / 续传 / 分片策略、持久化、下载引擎、UI 全部缺失**。

## 二、根因（为什么先做这一层）

下载是跨 5 层的功能（模型 → 策略 → 存储 → 引擎 → UI）。一次性推进风险面过大、
难以验证。依据「大型一致性批量改造逐部件小步交付」，拆为三批次；本批只做
**纯逻辑核心层**：无 IO、无网络、无 UI ⇒ 可用 `flutter test` 完整验证，
并为后续批次提供稳定基座。

同时有一个硬约束决定架构：`pubspec.yaml` 无 ffmpeg、`assets/` 目录不存在、
`windows/runner/` 未捆绑二进制 ⇒ **DASH 音视频分离流无 muxer 可合并**。
规避路径已由 `lib/http/video.dart` L216-219 注释确认：离线下载可另发
`fnval=1` 请求取 **DURL 单文件 MP4**。因此策略层保留 `merging` 状态位
（DASH 路径前向兼容），但本批不引入合并逻辑。

## 三、实现方法

### 3.1 新增 `lib/models/download/download_task.dart`
- `DownloadStatus`：queued / pending / downloading / merging / completed /
  failed / paused（对齐 BiliPai `DownloadStatus`；`fromName` 未知值回退 pending）
- `DownloadTask`：稳定唯一键 `id`（`{bvid}_{cid}_{quality}`，仅音频为
  `{bvid}_{cid}_audio`）；派生状态 `isComplete` / `isDownloading` / `canResume`
  / `isFailed`；进度 `progress` 由 `downloadedSize / fileSize` 派生（单一事实源，
  避免双写漂移）；`copyWith`；`toJson` / `fromJson` 容错（int / num / 字符串
  互转、缺失字段取默认、未知状态名回退）
- `DownloadOptions`（includeDanmaku）/ `QualityOption`

### 3.2 新增 `lib/core/download/download_policy.dart`（移植自 BiliPai）
风格对标 `lib/core/policy/video_load_policy.dart`：头部标注 Kotlin 源路径，
`abstract final class` 容器 + 全 `static` 纯函数。
- `DownloadQueuePolicy`：并发上限 2、活跃态判定、下一个排队任务
  （createdAt → id 排序）、陈旧地址刷新（30 min 阈值）
- `DownloadResumePolicy`：续传计划（已完成 / 支持 Range 追加 / 从头）
- `DownloadRangePolicy`：`Content-Range` 解析（含 `*` 未知总长）、并行分片阈值
  8 MiB、分片区间切分（余数前置分配，无重叠无空洞）
- `DownloadNamingPolicy`：文件名非法字符清洗与折叠、导出文件名、扩展名推断
- `DownloadRequestHeaders`：User-Agent / Referer / Cookie 构造

### 3.3 单测 36 例
- `test/models/download/download_task_test.dart`（13 例）
- `test/core/download/download_policy_test.dart`（23 例）

覆盖边界：阈值 ±1ms、负数归零、除零、分片余数、`*` 总长、非法文件名清洗等。
