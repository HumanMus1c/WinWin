# 播放卡顿与弱网误报误判复盘（2026-11-14）

## 一、现象

- 2026-11-14 21:45 / 21:49 播放 4K 视频期间多次卡顿、音频断点/跳音；界面弹出
  「网络较慢，请检查网络或更换网络环境」。
- 用户怀疑是内存或 CPU 吃满导致，而不是网络问题。

## 二、取证与定因

### 2.1 不是内存 / CPU 吃满

- **CPU**：`winwin` 21:08:09–22:05:25 累计 **1017.5 CPU 秒 / 3420 秒 ≈ 0.30 核**；
  4K HEVC 若走软解会高一个数量级 ⇒ 硬解在工作，CPU 未吃满。
- **内存**：系统 16GB、空闲 3.2GB、提交 76%、页面文件 2.1GB；`winwin` 私有 1.07GB
  （其中 GPU local 约 627MB），24 秒采样完全不变；峰值工作集 356MB。无内存耗尽，
  也无可观测的持续增长。
- **卡顿签名**：Dart 定时器停、播放器 PTS 继续推进 ⇒ UI 线程阻塞，不是资源饥饿
  （资源吃满会让播放器和定时器一起变慢）。

### 2.2 核心事实：UI isolate 阻塞

| 时间 | 证据 |
|---|---|
| 21:45:28.368 → 21:45:38.142 | `trace.log` UiTick 心跳中断 **9.774s** |
| 同窗口 | 视频 PTS 65.2s → 75.8s（推进 10.5s）；`buffered()` 80.6s → 90.9s |
| 20:28:26 → 20:28:35 | UiTick 中断 8.85s；`POLL#3338 SLOW dt=7423ms` |
| 21:49:16 → 21:49:20 | UiTick 中断 3.77s |

播放器与下载在 21:45 窗口内均正常前进，停的是 UI 线程。

### 2.3 看门狗误判并放大卡顿

- 21:45:38.170 `StallWatchdog: RENDER STALL: no completed frame for 9s`；
- 21:45:39.608 `PlayerController: device-loss soft recovery: no-frame 9s`
  → `setMedia` + seek 76.7s；
- 21:45:50.914 重载后的 seek 窗口出现流速 0.159 → 21:45:53.422 弹「网络较慢」；
  此时 `buffered()` 仍约 **101 秒**。

结论：看门狗把 UI 线程阻塞误判为「渲染停死/设备丢失」，重载媒体反而制造了真正
的播放中断与再缓冲，并触发后续弱网提示。

### 2.4 弱网判据不看缓冲水位

- 21:49:00.541 流速 0.414，`buffered()` **79 秒** → 暂停音频；21:49:02 弹弱网提示。
- 20:28:36 的提示同样发生在缓冲充足时。

旧判据只看「位置推进速率」，把本地解码/渲染抖动误判为网络不足。

### 2.5 音频假 0 触发假硬定位

- 21:46:21 `DRIFT hard drift=-98800 v=98800 a=0`；
- 21:49:05 `DRIFT hard drift=-69900 v=69900 a=0`。

`_sanitizeAudioPos` 仅在音频 `paused` 时防护；`playing + position=0` 被放过，
产生数十秒的假漂移与硬定位/归位，形成可闻跳音。

### 2.6 `d3d11.sync.cpu` 被设回 1

- `lib/main.dart` 按 2026-10-21 设备丢失复盘设为 `0`；
- `lib/pages/video/player_controller.dart` 每次创建播放器又设回 `1`，覆盖规避措施。

该栅栏正是 10-21 复盘认定的「GPU 重置后永远等不到」的同步路径，列为 UI 阻塞的
强嫌疑（本轮按 A/B 改为 0，待实机确认撕裂/闪烁）。

### 2.7 系统背景

- 近两周无 Display 4101 TDR；但存在 11-06 / 11-09 / 11-13 的
  LiveKernelEvent 141/124（GPU watchdog / WHEA）转储，11-13 18:36 与 Display 4107
  对齐 ⇒ 本机 AMD GPU 有卡死史。今天 21:45 无对应 TDR，更像短时 GPU/同步阻塞。

## 三、修复方案

1. **看门狗防误判**（`lib/core/diagnostics/stall_watchdog.dart`）：记录 2s 检查
   定时器的实际间隔；迟到 >2500ms 判为 `UI STALL`，跳过设备丢失重载，只落 W 日志
   并重置停摆回合。
2. **弱网门控**（`lib/pages/video/player_controller.dart`）：新增
   `_bufferedAheadMs` / `_bufferLowForWeakNetwork`；缓冲存量 ≥5s 时不再判弱网、
   不弹提示；音频同步暂停需「存量不足且视频停滞 ≥400ms」或「视频停滞 ≥3000ms」。
3. **音频假 0 防护**：`_sanitizeAudioPos` 改为「起播窗口（换源 5s / 起播对齐）+
   回退幅度 >5s」判定，不再依赖音频 state；`_audioSyncPaused` 期间跳过漂移；
   seek / 重挂 / 归位成功后重置有效基准。
4. **GPU 同步栅栏**：`d3d11.sync.cpu` 改回 `0`，与 `main.dart` 及 10-21 结论一致。
5. **取证**：`Documents/logs/seek_probe.json` 的 `pollTrace` 改为 `true`，下次复现
   可定位具体阻塞阶段；注意 `trace.log` 5MB 轮转，复现后尽快取日志。

## 五、遗留与踩坑

1. **UI 线程 9.8s 阻塞的确切调用尚未定位**：可能为 mdk 同步 FFI、平台通道、同步
   文件写入或弹幕排版；`pollTrace` 只覆盖轮询阶段，若下次仍是「tick 之间」阻塞，
   需要另加 UI 任务埋点或 ETW 取证。
2. **`d3d11.sync.cpu=0` 的代价**：可能重现纹理时序撕裂/闪烁；若实机出现，不能简单
   改回 1，需要走「轮询读取移出 UI 线程」的异步方案。
3. **内存另案**：退出播放后私有提交约 1.07GB、GPU local 约 627MB，显著高于
   2026-09-28 基线（约 300MB）；本轮未将其作为卡顿根因，建议另开内存审计。
4. **无播放器时的 UI 冻结**：20:16/20:17（3.1~3.6s）、20:45（5.1s/12.0s）未定位，
   可能与系统调度、平台通道或同步日志有关；本轮改动不覆盖。
5. **pollTrace 开销**：约 50 行/秒同步写日志，`trace.log` 会快速轮转；取证完成后
   应把 `pollTrace` 改回 `false`。

## 六、总结

本次「网络较慢」是误报。实际链路是：UI 线程阻塞 → 看门狗误判并重载 → 弱网判据
不看缓冲而误报/暂停音频 → 音频假 0 触发假硬定位。内存/CPU 数据不支持「吃满」
判断。已修误报链并关闭 GPU 同步栅栏，待实机复验。
