# 播放器「重播后立即快进 → 瞬间回到播放完毕/重播态」复盘（2026-09-24）

## 1. 现象

用户口述：播放完一个视频（画面中央显示重播按钮）→ 点击中央重播按钮，视频开始重播 → **立即**再做一次「seek 快进」→ 视频**瞬间回到播放完毕/重播态**。

现象特征：
- 完成态是「瞬间」出现的，与真实播完无关；
- 出现后画面不再前进（播放器被暂停），且此后任何点击/快进都**没有反应**。

## 2. 定因（取证）

- `D:\Documents\logs\runtime.log`（AppLogger，Release 仅 W/E）
- Windows 应用事件日志（Application Error / WER）

事件会话为 `2026-09-24T23:09`：35 秒短视频，双播放器模式（主实例 video-only + 第二实例 audio-only），3 条 CDN 候选。

### 2.3 根因一：完成态误判（「瞬间回到重播态」的直接来源）

`_handlePlaybackEnded()` 有 4 个触发源，但**只有 `MediaStatus.end` 由 0→1 翻转这一支能在位置仅 ~3.4s/34.6s 时触发**（其余三支都要求位置 ≥ 片尾-1.5s）：

```
案件位置 3.4s ≪ 片尾-1.5s
   pollNearEnd    → 要求 isNearEnd（≥ dur-200ms）           ✗ 不可能
   statePaused    → 要求 pos ≥ dur-1500ms                   ✗ 不可能
   mediaStatus.end→ 无任何位置门控                           ← 唯一可能
```

而 `onMediaStatus` 里该分支**没有任何位置校验**（修复前）：

```dart
if (!oldValue.test(mdk.MediaStatus.end) && newValue.test(mdk.MediaStatus.end)) {
  if (!_isSeeking && !_nativeSeekInFlight && _queuedSeekTargetMs == null) {
    _handlePlaybackEnded();   // ← 位置不校验，直接判完成
  }
}
```

`_handlePlaybackEnded()` 的动作是「进度归一到片尾 + `completed=true` + `playing=false` + **暂停播放器**」——正是用户看到的「瞬间回到播放完毕态」，且之后画面停住。

**旁证（本会话日志直接实证 `end` 会假置位）**：

```
23:09:06.087  mediastatus/MediaStatus(+loaded+prepared+buffered) -> ...(+seeking)
23:09:06.093  mediastatus/MediaStatus(+loaded+prepared+buffered+seeking) -> ...(+buffered+end)   ← 普通前进 seek 中 end 被置位
```

一次**普通的前进 seek**（target=9850ms，位置 2.0s，视频总长 34.6s）执行过程中 `end` 位就被置起来了；该位随后一直保留到下一次 seek 才被清除。机制推测：主实例为 **video-only + 预读 30s**（`SeekProbe.bufferMaxMs=30000`），35 秒短视频在 seek(0) 后预读很快触达文件 EOF，mdk 即置 `end`；一旦该翻转发生在 seek 冻结窗口之外，就会误判为播放完毕。

冻结窗口判定（`_isSeeking || _nativeSeekInFlight || _queuedSeekTargetMs != null`）只能覆盖 seek 期间，覆盖不到「seek 落地后 1~5 秒预读触达 EOF」这类**窗口外瞬态**。

### 2.4 根因二：随后 isolate 整体冻结（「快进没反应 + 日志全静默」）

- 本项目所有 seek 入口（进度条 / 双击 / 拖拽 / 方向键 / 番剧页）最终都走 `WinWinPlayerController.seek()`，而 `seek()` 内的 `SeekProbe.begin()` 一旦被调用就必落 `SEEK#N REQ`（该行不受探针窗口限制）。**日志中不存在 23:09:33 之后的任何 REQ** ⇒ 用户那次「快进」根本没有派发到控制器 ⇒ **输入未被处理**。
- 同时整段 0 条日志、0 条 dispose、0 条状态事件，直到 21 分钟后以 `amdxx64.dll 0xc0000409` 崩溃 —— 与项目既有档案「同步 FFI 读取死锁」（2026-09-20 00:11 实证：瞬态窗口同步读 position 令 isolate 永久阻塞）同类。
- 冻结发生在轮询回调里的 5 处同步 FFI 读取之一（`position` / `bufferedTimeRanges` / `buffered` / `mediaStatus` / `state`），**本次因缺少现场埋点无法定位**（见 2.5）。

### 2.5 取证缺口（导致本次无法一步定因）

1. **常态监控 MON 心跳永不落盘（代码缺陷）**：`SeekProbe.nowMs` 用的是探针秒表 `_clock`（仅 `begin()`→`close()` 期间运行，窗口外恒停在 ≤4000ms），而报告阈值是 5000ms ⇒ 判据永假。整个 trace.log（5629 行、跨 6 周）**0 条 MON 行**。
2. `MediaStatus` / 播放状态变迁只在探针窗口内记录（`_active` 门控），本事件的 `end` 翻转恰好落在窗口外。
3. `seek()` 入口无埋点 ⇒ 无法区分「没派发」与「派发后卡死」。
4. `_handlePlaybackEnded` 不记录触发源与原始读数（pos/dur/status/state）。
5. 第二实例（音频）全程零埋点。
6. 轮询回调无 tick 心跳、无阶段埋点 ⇒ 卡死点无法定位。

## 3. 修复方案（本轮）

### A. 完成态判定加固（消除误判）

1. `_handlePlaybackEnded({required String source})` 增加**片尾位置门控**：`durMs <= 0 || rawPosMs < durMs - 1500` 时直接返回，只落 `FAKE-END` 证据行，**不改任何 UI 状态、不归一进度、不暂停播放器**；
2. `onMediaStatus` 的 `end` 翻转分支改调 `source: 'mediaStatus.end'`（其余三个调用点分别为 `statePaused` / `pollNearEnd` / `stallRecovery`）；
3. 冻结窗口内出现的 `end` 翻转记 `END-FLIP-IN-SEEKWINDOW (ignored)`，被门控拒绝的暂停事件记 `STATE-STOP-NOTEND`，供回溯统计。

### B. 取证补齐（下次必然可定因）

1. **修复 MON 时钟**：新增独立单调时钟 `_monClock`，并把「5s 报告」从 `monitorTick` 拆到新函数 `beat()`；`monitorTick` 退化为纯采样器；
2. **零 FFI 存活心跳 `BEAT`**：放在轮询回调**最前端**（任何早退分支都拦不住），只读 ValueNotifier 缓存与控制器标志 ⇒ 心跳一断即证明 isolate 被阻塞；行内含 `phase=`（最后完成的轮询阶段）；
3. **RAW 常态原始读数（5s 节流）**：含底层真实 `state` / `status` / 缓冲水位 / `adv` / `playing` / `completed` / 第二实例 `state@pos`，且放在「完成态冻结」早退分支**之前**——本次事件中该行会直接落在冻结分支内，一眼看出 `end` 假置位；
4. **`seek()` 全链路埋点**：`SEEK-REQ`（入口，零 FFI）→ `SEEK-QUEUE` / `SEEK-QUEUE-DRAIN` → `SEEK-DISPATCH` → `PROC ... enter`（首次 FFI 读取之前）→ `AUDIO seek`/`AUDIO seek ret` → `MAIN seek`/`MAIN seek ret` → `UNFREEZE`；
5. **状态变迁全量落盘**：`STATE old -> new`、`STATUS old -> new`（含 `end` 位）、`AUDIO state/status`（第二实例首次创建时挂常驻监听）；漂移硬定位记 `DRIFT-HARD`；
6. **`pollTrace` 逐 tick 阶段埋点（配置开关，默认关）**：每 tick 写 `enter / after-position / after-buffered / after-drift / done`，行内带 `dt=`（自 tick 起点耗时）⇒ 卡死点可直接锁定到具体同步 FFI 读取，且能看到阻塞前的耗时恶化趋势；`pollEnd()` 在无 pollTrace 时兜底记录 `SLOW`（≥300ms）tick。

### C. 冻结防御（待证据）

本轮**不改**轮询的同步 FFI 读取结构（避免盲改引入新风险）；等实机复现拿到 `POLL#N` 卡死点后再定向处理。

## 6. 复测新增发现（2026-09-25 01:19–01:22 会话）

### 6.1 双实例漂移校正基本失效 ⇒ A/V 不同步 0.9~1.5s（最严重）

证据（RAW 行同时采样主实例与第二实例原始 position）：

| 时刻 | 视频 pos | 音频 pos | 偏差 |
| --- | --- | --- | --- |
| 01:21:13 | 15233 | 15144 | -89ms |
| 01:21:18 | 47533 | 48812 | **+1279ms** |
| 01:21:23 | 52533 | 53850 | +1317ms |
| 01:21:28 | 57633 | 58989 | +1356ms |
| 01:21:33 | 62633 | 64030 | +1397ms |
| 01:21:38 | 67633 | 69071 | +1438ms |
| 01:21:43 | 72633 | 74110 | +1477ms |
| 01:21:48 | 77633 | paused@79103 | 音频轨道**已播完并暂停**（比视频早约 1.4s） |

- 稳定播放期偏差以 **~0.78%/s 单向增长**（+39ms/5s），说明 ±3% 速率修正**没有真正生效**；偏差一路涨到 >1.5s 后触发 `DRIFT hard` 硬定位（音频瞬跳，可闻）：`01:21:54.80 DRIFT hard drift=3484`、`01:22:00.80 DRIFT hard drift=1523`。
- **代码根因**：`SeekProbe.driftDecision` 在**节流期**（seek 后 250ms / 稳定期 5s）返回 0，与「偏差在死区内返回 0」不可区分；而调用处对 `decision == 0` 的处理是 `apd.playbackRate = 1.0`（复位）⇒ 每次 nudge 只生效约一个 tick（~100ms）就被复位，占空比 ~2%（稳定期），等效修正量 ≈0.06%。
- **次因（每次 seek 后必现一次音频瞬跳）**：主实例 seek 走 `keyFrame`，落点是**关键帧**（与目标差 -3.6s ~ +3.1s），而第二实例按**请求目标**落点 ⇒ 每次 seek 后天然产生 1.5~3.5s 固定偏差，随即被 `DRIFT hard` 硬拉：
  `01:20:19.93 DRIFT hard drift=-3115 v=200966 a=197851`、`01:20:28.03 DRIFT hard drift=3451`、`01:21:54.80 DRIFT hard drift=3484`。

### 6.2 主实例 seek 落点不准（keyFrame 快照）

## 8. 第三轮修复（2026-09-25 17:27–17:51 会话复测）

**复测结论（第二轮验收通过）**：音画偏差全程 50~120ms（旧 900~1500ms）、`DRIFT-HARD` **0 次**、22 次 seek 全部 `AUDIO seek seq=N -> <res> (main landed res=<res>)` 齐步、探针判定全部 `settled=1 / aheadMax=0 / driftBack=0`、`SLOW=0`、多次正常 dispose 退出；比例控速按偏差下发（`DRIFT-APPLY rate=0.9870/1.0262/1.0198/reset`）。

**新现象定因（用户报告「偶发 seek 回调，从 seek 时间点回退至原播放时间点」）**：

- 本会话 22 次 seek 的落点**全部落在 5s 关键帧网格上**（0/5000/10000/…），其中 **18 次落在目标之前**（-0.3s ~ **-4.8s**：如 49808→45000、29624→25000、14176→10000、163804→160000），4 次落在目标之后（+0.6s ~ +4.3s：如 150684→155000、55799→60000）。
- 呈现为两段式：seek 期间进度条/时间胶囊显示**目标点**（`seek()` 写入 `position.value` + mdk 立即回报请求位），落地后 `_processSeekQueue` 写回**真实落点** ⇒ 观感「到点后又回退一段」= 用户所述「偶发 seek 回调」；小幅度 seek 时落点可落到原播放点附近/之前 ⇒「回退至原播放时间点」。
- 「偶发」成因：误差大小取决于目标与最近关键帧的距离（0~4.8s 随机），并非每次都能察觉。
- **已排除旧故障类**：22 个窗口 `aheadMax=0`（无"时钟被拖回 seek 前位置"）、`DRIFT-HARD=0`、`noProgress=0`、`SLOW=0` ⇒ 2026-09-19/20 的「demuxer 不归位 / 被音频时钟拖回」未复现。

**改动**：

1. `accurateSeek`（配置开关，默认 `false`＝保持现状）：前向与快退均可改「精确落点」（去 KeyFrame），用于 A/B 判定双实例（主实例纯视频 DASH、主媒体 seek）配置下 Accurate 是否可靠——历史「Accurate 快退间歇不生效」实证来自**外挂音轨 / 单源 HLS 清单**配置，需在新配置下重新判定；
2. 埋点修正：`AUDIO unfreeze` 的陈旧 `pos=0`（实测该瞬间读值恒为 0）改为延迟 300ms 的 `AUDIO settled pos=…` 行；
3. 监控统计去瞬态：seek 落地后 3s 内不采样 + 解冻时重置采样窗口（此前实测落地后 1.6s 的样本仍被算成 2.8s 停顿）。
