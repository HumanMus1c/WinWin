# 播放器缓冲冻结死锁修复复盘（2026-09-29）

**范围**：复测日志审计发现的 P0 遗留问题——弱网"缓冲保持"逻辑在特定时序下的**冻结死锁**。

## 一、分析根因（现象 + 取证 + 根因链）

- **现象（取证）**：Release 版（PID 36844，12:28 启动）。同一视频第三次打开（历史续播 seek→140s），12:32:44.507 触发 `BUFFER-HOLD-PAUSE pos=140000 buf=0`；此后 **50 分钟**（至 13:22:40 用户手动关闭）`pos=140006` 恒定不变、`intent=1`（用户想播）、`buffering=1`、缓冲恒定 `155020`（≈16s 缓存上限−1s）、`avgRate=0.00`、`stalls=1`，**无任何自动恢复**；runtime.log 无任何告警（冻结仅写 trace）。
- **根因链（四环叠加，均已在代码中钉死）**：
  1. **误冻结**：seek 落地瞬态 `player.buffered()==0` + 停顿计数 `_bufferingStallMs≥1000` 命中冻结条件（`player_controller.dart:1772-1784` 原版）；
  2. **恢复判据全灭**：`_waterReadyForResume`（`:1018-1022` 原版）要求水位增长≥0.75×期望 **或** 缓冲≥`_waterFullMs=20000ms`；实际缓存上限=cache-secs=`Pref.bufferSec`(16s)，缓冲 ~15s 封顶、水位 0 增长 ⇒ **两个分支都不可达**（阈值按旧 30s 上限校准，与现配置脱节）；
  3. **停滞看门狗被门控挡住**：真卡死恢复要求 `player.buffered() <= 0`（`:1854`），此处有 15s 存量 ⇒ 不触发；
  4. **诊断缺口**：冻结事件无运行日志，用户侧"看得见的卡死、日志里看不见"。

## 二、设计修复计划与实现

1. **① 上限阈值动态化**：`_waterFullMs` 由常量改为按 `Pref.bufferSec × 倍速`（与 initBuffer 的 cache-secs 同口径）的 85% 推导、下限 5s —— "缓存已满"分支恢复可达（16s 配置下阈值 13.6s，实测死锁时存量 15.0s 即可续播）；
2. **② 冻结超时兜底**：冻结 ≥3s 且存量 ≥5s ⇒ 无条件推回播放（trace 标注 `via=timeout`）——水位/上限判据全部失效时仍可自愈；与第三轮"存量 ≥5s 连续播"理念一致，不会引入"推一下播一点"抖动；
3. **③ 卡死告警**：冻结持续 ≥10s 记一条 `[W] 'Buffer hold stuck …ms … — keep waiting'`（每次冻结仅一条，不刷屏）；
4. 冻结计时统一在"进入暂停等待"处挂表（含引擎自发暂停），恢复 / 脱离暂停即清零。

## 三、修复效果验证

- `dart analyze`：exit=0，**6 issues（0 error / 0 warning）**，均为预存 lint，无新增；
- 双编译：**Debug ✅ 20.9s**；**Release ✅ 18.9s**——首发因运行中的 App 锁 `WebView2Loader.dll`（MSB3021，环境类失败），关闭应用实例后重跑通过；**0 警告**；
- 实机验证清单（待用户执行，复现路径：同一视频连续打开 ≥3 次、均从历史深位续播）：
  - [ ] 若仍触发冻结：**≤3s 后自动续播**，trace 出现 `BUFFER-HOLD-RESUME-PUSH … via=timeout frozenMs=…`；
  - [ ] 真弱网（存量 <5s 推不动）时：**10s 后 runtime.log 出现一条** `[W] Buffer hold stuck … — keep waiting`；
  - [ ] 正常网络下不再出现 >10s 的无动作冻结。
