# GPU 设备丢失后 UI 冻结：取证与分级自愈落地复盘（2026-10-21）

## 一、现象

- 2026-10-21 11:35–11:40 系统正在安装 **AMD 显卡驱动套件**（Adrenalin `26.10.1`）期间，
  **整机显示黑屏掉线再自动恢复**，随后 WinWin 界面冻结、无法操作。
- 现场客观证据（进程级，非猜测）：
  - `winwin.exe` PID 48684 **仍在运行**、窗口 **Responding=True**、MainWindowHandle 有效；
  - **3 秒内 CPU 增量 = 0 ms** → 全进程处于**阻塞等待**（非空转）；
  - 50 个线程几乎全部 `Wait`（多个 `UserRequest`）→ 硬阻塞；
  - `D:\Documents\logs\runtime.log` 最后一条停在 **11:07:27**（应用启动的玻璃预载）后**完全静默**；
  - **无 WER 崩溃记录、无 TDR（无 Display 4101）** → 属「挂死」而非崩溃。

## 二、定因

- 触发源（系统日志闭环）：`11:35:43` SCM 7045 装入内核模式驱动 `amdkmdag.sys`（AMD 显卡驱动）；
  `11:36:23-24` Configuration-Change-Monitor ×8；`11:38:20` Display 4107
  （`SetDisplayConfig(SDC_FORCE_MODE_ENUMERATION)`）；`11:39:48-53` MsiInstaller 安装 `AMD WVR64` / `RyzenMasterSDK`。
  → **这是一次设备级重置事件**，会拆除并重建所有 D3D 设备。
- 机制：GPU 驱动重置 → **D3D 设备丢失**；进程内有线程正阻塞在一次**永远等不到**的 GPU 同步调用上。
  本项目 `lib/main.dart` 中的 `mdk.setGlobalOption('d3d11.sync.cpu', 1)`（D3D11 CPU-GPU 同步栅栏）
  即属此类"等 GPU 回应"的阻塞调用；设备丢失后该栅栏不会再被满足 → 线程硬阻塞。
- 症状一致：UI isolate 事件循环停摆（Dart 定时器停、日志静默）+ 全进程 CPU≈0 + 平台线程仍活着
  （Responding=True、不退出、无异常）——正是"**渲染/UI 死、消息泵活**"的设备丢失签名。
- 与 2026-10-20 修复的关系：昨日 `RunOnSeparateThread` 解决的是"切屏/改分辨率时窗口消息 ↔ Dart 互阻"
  （窗口路径）；本次是 **D3D 设备丢失路径**，两者机制不同，昨日修复未推翻、也覆盖不到本次。

## 三、方案

### 一轮：规避 + 冷路径兜底（提交 fde9cc1）

- **试验 A**：`lib/main.dart` 将 `d3d11.sync.cpu` 由 `1` 改为 `0`——去掉可能"永远等不到"的
  CPU-GPU 同步栅栏（一行、可逆）。代价：原作者注释表明该栅栏用于消除纹理时序撕裂/新旧画面闪烁，
  若实机出现撕裂则回退为 1（或将开关升级为设置项）。
- **冷路径看门狗**：`lib/core/diagnostics/stall_watchdog.dart` —— 主 isolate 每秒心跳 → 独立
  **后台 isolate**（有自己的事件循环，不受 UI isolate 阻塞影响）；无心跳超阈值即落盘
  `Documents/logs/render_stall.log`；超阈值执行**整进程重启**。
- **诊断埋点**：`WidgetsBindingObserver.didChangeMetrics` 把 DPR / physicalSize 变化记入 `runtime.log`，
  便于与 `render_stall.log`、Windows Display 事件按时间线对齐。

### 二轮：**分级恢复**（本轮，依 CVO 意见「先做 2」）

把"一超时即整进程重启"升级为**分级**，尽量保住页面/进度：

1. **暖路径（UI isolate 存活、仅渲染停摆）**——主 isolate 用 `SchedulerBinding.addTimingsCallback`
   跟踪"最近一次完成渲染"；**仅在"期望出帧"状态下判定**（视频播放中由播放器声明，避免把静止页面
   无重绘误判为卡死）。无帧 **≥5s** →
   - **进程内轻量恢复**：调用 `PlayerController.recoverFromDeviceLoss()`，在本共享 `mdk.Player`
     上 `load()` 重挂媒体（**重建 Flutter 纹理**），保留页面与进度；
   - 若仍无帧 **≥15s** → 升级为**整进程重启**（延时重启 + `exit(0)`）。
2. **冷路径（UI isolate 整体停摆）**——心跳停止（主 isolate 事件循环被同步 FFI 阻塞时，
   定时器随之中止）→ 后台 isolate **≥30s** → 落盘取证 + 整进程重启（此时进程内恢复**不可能**，
   因为没有任何 Dart 代码可运行）。

**播放器接入**（`lib/pages/video/player_controller.dart`）：
- 构造时 `StallWatchdog.registerSoftRecovery(recoverFromDeviceLoss)`；
- `playing` 变更 → `StallWatchdog.setRenderExpected(playing.value)`（期望出帧状态跟随播放态）；
- 引用计数归零时 `setRenderExpected(false)` + `unregisterSoftRecovery(...)`。

## 五、遗留与踩坑

1. **轻量恢复的边界**：`recoverFromDeviceLoss()` 走 `load()` 重挂媒体——只有 **fvp/纹理路径** 的停摆
   能靠它恢复；若停摆发生在**引擎光栅/整设备**层，进程内无法恢复，只能升级为整进程重启（暖路径 15s
   升级 / 冷路径 30s）。
2. **"期望出帧"依赖播放态**：只有"正在播放"才判定停摆，静止页面不判——因此**静止页面下的冻结不会
   被暖路径捕获**（该情形也无客观判据，且影响较小）。
3. **真·设备级感知未做**（务实取舍）：D3D11 无"设备丢失事件"可订，且设备句柄在 `flutter_windows.dll`
   与 `libmdk` 内，应用层拿不到；当前用"帧停止"作等价近似。后续可 fork/上游 `fvp` 加
   `GetDeviceRemovedReason()` 回调，或在 runner 建 `IDXGIFactory7` + `RegisterAdaptersChangedEvent`。
4. **A 的副作用**（撕裂/闪烁）仍需实机确认；这是本轮主要待验证取舍。
5. 本机另有 **GameViewer Virtual Display Adapter**（虚拟显示适配器），会参与显示器枚举，后续若仍有
   切屏类问题需一并评估。

## 六、总结

本次冻结的根因由"进程级 + 系统事件"双证据定位为：**GPU 驱动重置导致 D3D 设备丢失，线程阻塞在
`d3d11.sync.cpu=1` 这个永远等不到的 CPU-GPU 同步栅栏上**。据此分两轮落地：**A** 关闭栅栏规避阻塞；
**B/C 分级自愈**——暖路径（UI 存活）先做**进程内轻量重建**（重挂媒体/重建纹理，保留页面进度），
15s 无效才升级整进程重启；冷路径（UI 整体停摆）30s 整进程重启；全程由独立后台 isolate 落盘取证。
均已通过 analyze 与 debug/release 双编译；实机效果待 CVO 复验。
