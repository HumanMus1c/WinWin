# GPU 设备丢失后 UI 冻结：取证与自愈落地复盘（2026-10-21）

## 一、现象

- 2026-10-21 11:35–11:40 系统正在安装 **AMD 显卡驱动套件**（Adrenalin `26.10.1`）期间，
  **整机显示黑屏掉线再自动恢复**，随后 WinWin 界面冻结、无法操作。
- 现场客观证据（进程级，非猜测）：
  - `winwin.exe` PID 48684 **仍在运行**、窗口 **Responding=True**、MainWindowHandle 有效；
  - **3 秒内 CPU 增量 = 0 ms** → 全进程处于**阻塞等待**（非空转）；
  - 50 个线程几乎全部 `Wait`（多个 `UserRequest`）→ 硬阻塞；
  - `D:\Documents\logs\runtime.log` 最后一条停在 **11:07:27**（应用启动的玻璃预载）后**完全静默**；
  - **无 WER 崩溃记录、无 TDR（无 Display 4101）** → 属「挂死」而非崩溃。

## 二、定因

- 触发源（系统日志闭环）：`11:35:43` SCM 7045 装入内核模式驱动 `amdkmdag.sys`（AMD 显卡驱动）；
  `11:36:23-24` Configuration-Change-Monitor ×8；`11:38:20` Display 4107
  （`SetDisplayConfig(SDC_FORCE_MODE_ENUMERATION)`）；`11:39:48-53` MsiInstaller 安装 `AMD WVR64` / `RyzenMasterSDK`。
  → **这是一次设备级重置事件**，会拆除并重建所有 D3D 设备。
- 机制：GPU 驱动重置 → **D3D 设备丢失**；进程内有线程正阻塞在一次**永远等不到**的 GPU 同步调用上。
  本项目 `lib/main.dart` 中的 `mdk.setGlobalOption('d3d11.sync.cpu', 1)`（D3D11 CPU-GPU 同步栅栏）
  即属此类"等 GPU 回应"的阻塞调用；设备丢失后该栅栏不会再被满足 → 线程硬阻塞。
- 症状一致：UI isolate 事件循环停摆（Dart 定时器停、日志静默）+ 全进程 CPU≈0 + 平台线程仍活着
  （Responding=True、不退出、无异常）——正是"**渲染/UI 死、消息泵活**"的设备丢失签名。
- 与 2026-10-20 修复的关系：昨日 `RunOnSeparateThread` 解决的是"切屏/改分辨率时窗口消息 ↔ Dart 互阻"
  （窗口路径）；本次是 **D3D 设备丢失路径**，两者机制不同，昨日修复未推翻、也覆盖不到本次。
  且当前运行的正是含昨日修复的构建（`Release\winwin.exe` 时间 10-20 19:48）→ 证明**这是独立触发源**。

## 三、方案（试验 A + 诊断埋点 B + 自愈 C）

- **试验 A**：`lib/main.dart` 将 `d3d11.sync.cpu` 由 `1` 改为 `0`——去掉可能"永远等不到"的
  CPU-GPU 同步栅栏（一行、可逆）。代价：原作者注释表明该栅栏用于消除纹理时序撕裂/新旧画面闪烁，
  若实机出现撕裂则回退为 1（或将开关升级为设置项）。
- **诊断埋点 B**：新增 `lib/core/diagnostics/stall_watchdog.dart`：
  - 主 isolate 每秒心跳 → 独立**后台 isolate** 监测（后台 isolate 有自己的事件循环，
    不受 UI isolate 阻塞影响）；
  - 无心跳 ≥ 8s 判定停摆，落盘到 `D:\Documents\logs\render_stall.log`
    （记录 START / ongoing 时长 / END 总时长）；
  - 另经 `WidgetsBindingObserver.didChangeMetrics` 把 DPR / physicalSize 变化记入 `runtime.log`，
    便于与 `render_stall.log`、Windows Display 事件按时间线对齐。
- **自愈 C**：同看门狗内，停摆 ≥ 30s 时执行「**延时重启 + 强制退出**」：
  `cmd /c ping -n 4 … & start "" "<exe>"` 延时 ~3s 启动新进程（确保本进程先退出、释放单实例互斥锁
  `Local\winwin-single-instance-v1`），随后 `exit(0)`。把"静默硬冻结、需手动强杀"变为"自动恢复"。

## 五、遗留与踩坑

1. **自愈默认开启**（阈值 30s）：若某次超长同步操作（非真停摆）误触，可将
   `StallWatchdog.init(autoRecover: false)` 仅保留取证；后续再评估接入 `Pref` 开关 + 设置行。
2. **看门狗检测的是「UI isolate 事件循环停摆」**：与本机此次"同步调用阻塞"完全吻合；
   若未来出现"仅光栅停摆而 UI isolate 存活"，需补原生侧帧进度心跳（本轮为控制构建风险未动原生）。
3. **显示变更的客观依据**暂用 Windows `Display 4107` 事件 + 应用侧 `didChangeMetrics` 日志；
   如需更强关联，可后续在 runner 补 `WM_DISPLAYCHANGE` 原生落盘。
4. 本机另有 **GameViewer Virtual Display Adapter**（虚拟显示适配器），会参与显示器枚举，后续若仍有
   切屏类问题需一并评估。
5. **A 的副作用**（撕裂/闪烁）需实机观察确认；这是本次方案的主要待验证取舍。

## 六、总结

本次冻结的根因已由"进程级 + 系统事件"双证据定位为：**GPU 驱动重置导致 D3D 设备丢失，线程阻塞在
永远等不到的 CPU-GPU 同步栅栏上**（`d3d11.sync.cpu=1`），表现为"UI/渲染死、消息泵活"的静默硬冻结。
据此落地三件事：**A** 关闭该栅栏规避阻塞、**B** 独立后台 isolate 看门狗落盘取证、
**C** 停摆 30s 自动延时重启恢复。三者均已通过 analyze 与 debug/release 双编译，实机效果待 CVO 复验；
若 A 引发撕裂则以 B/C 的取证与自愈兜底、并按需回退 A。
