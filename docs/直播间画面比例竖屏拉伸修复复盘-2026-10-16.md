# 直播间「画面比例」竖屏被压扁拉宽 修复复盘（2026-10-16）

## 一、现象描述
- 直播间视频源为**竖屏**画面时，画面被压缩高度、拉伸宽度（明显变形）。
- 将「画面比例」切到「原始比例」仍变形；其余档位（16:9 / 4:3 / 铺满拉伸）切换后
  肉眼几乎无变化，疑似「完全没生效」。

## 二、问题根因（定因）
源码级定位 `lib/pages/live/live_room_page.dart`：

1. 外层播放器盒 `_buildPlayerBox()`（约 L1036）恒为 `AspectRatio(16 / 9)`，
   与视频源比例无关。
2. 内层 `_buildVideoSurface()`（约 L1194）直接用 Flutter `Texture` 渲染。
   关键事实：Flutter `Texture` 会**把解码帧拉伸铺满其布局盒子**，是否保真
   完全取决于外层是否按源尺寸设 `AspectRatio`。
3. 旧实现中：`原始比例` 与 `铺满拉伸` 两档都包了**写死的** `SizedBox(1920, 1080)`
   （即 16:9），`16:9` 档也用 `AspectRatio(16/9)` —— 四档里至少三档最终盒子
   都是 16:9。竖屏源（如 1080×1920，9:16）被塞进 16:9 盒子 → **高度被压缩、
   宽度被拉伸**，且档位切换无视觉差异。

权威依据：fvp `Player.textureSize`（`Future<ui.Size?>`）是官方获取视频显示尺寸
的途径，且**已按 rotation 旋正**（`lib/src/player.dart` 处理 `rotation % 180 == 90`），
竖屏流会返回「高 > 宽」的真实尺寸 —— 旧代码**从未读取它**，这是根因闭环。

## 三、修复方法（方案 A，用户 2026-10-16 拍板）〔已作废 · 见文末 §2〕

> ⚠️ **本节及 §四/§六的结论已于 2026-10-16 第二轮作废**：实测「方案 A」仍不正确
> （`16:9` 呈「原始比例」效果、`4:3` 与 `原始比例` 被**逐级等比放大**）。已改为
> **直接移植上游 PiliPlus 实现**，见文末「§2 返工」。以下内容保留作历史记录，勿再据此维护。

语义：除「铺满拉伸」外一律**等比缩放、不拉伸**（contain）；档位只决定**容器比例**
（即黑边方向）；「原始比例」按视频源真实比例显示。

改动文件：`lib/pages/live/live_room_page.dart`（保持 diff 最小）：

1. 新增字段 `Size? _videoSize`；`_initLive()` 进入时清零；`_startPlayer()` 建纹理后
   `unawaited(player.textureSize.then(...))` 写入源尺寸（仅当 `mounted && _player == player`）。
2. 新增 getter `_playerBoxAspectRatio`：16:9 / 铺满拉伸 → 16:9；4:3 → 4:3；
   原始比例 → 源比例（源未知回退 16:9）。外层 `_buildPlayerBox()` 由恒 `16 / 9`
   改为读该 getter。
3. 重写 `_buildVideoSurface()`：
   - `_aspectRatioMode == 3`（铺满拉伸）→ `SizedBox.expand(FittedBox(fit: fill,
     SizedBox(srcW × srcH, Texture)))` —— **唯一拉伸档**；
   - 其余档（0/1/2）→ `Center(AspectRatio(srcW / srcH, Texture))`，按源比例等比、
     绝不拉伸。
4. 全屏路径复用同一 `_buildVideoSurface()`，因此全屏也由「拉伸铺满」变为
   「等比 contain」，**顺带修复全屏变形**。

## 五、遗留与踩坑
- 「16:9」与「原始比例」在**源本身即为 16:9** 时视觉一致（容器同比例），属预期，非 bug。

## 六、总结
根因是「软件把视频盒写死 16:9 + `Texture` 铺满拉伸 + 从未读取源尺寸」，
而非某个档位「点击无效」。修复引入 fvp `textureSize` 源尺寸，并按「方案 A」
重写渲染与容器比例：竖屏源不再变形、四档语义清晰可辨，并顺带修复全屏变形。

## §2 返工：移植上游 PiliPlus「画面比例」实现（2026-10-16 第二轮）

> 本节为**最新有效结论**；上方 §三/§四/§六 的方案 A 已作废。

### 一、现象（用户第二轮实测反馈）
切换到**非 16:9** 的视频后，四档表现为：
- `16:9` → 呈现「原始比例」效果；
- `4:3` → 把视频画面**等比放大**；
- `原始比例` → 在此基础上**再次等比放大**分辨率；
- `铺满拉伸` → 正常。

即第一轮实现产生**逐级放大、档位互相串位** → 判定为**方向性错误，整段作废**。

### 二、定因（第一轮实现为何错）
1. 同时改动**外层容器 `AspectRatio`**（`_playerBoxAspectRatio`）与**内层
   `AspectRatio(源比例)`**，两层比例叠加、缩放基准不一致 → 出现「越切越大」的累积放缩；
2. 内层用手写 `AspectRatio` 而非上游「**按源尺寸建盒子 + `FittedBox(boxFit)`**」
   的组合，与 `Texture` 拉伸铺满的机制错配。

### 三、修复：直接移植上游实现（本机 PiliPlus commit `65d5bf8`）
- **新增** `lib/pages/video/video_fit_type.dart`：逐值移植上游
  `lib/plugin/pl_player/models/video_fit_type.dart` —— `fill/contain/cover/fitWidth/
  fitHeight/none/scaleDown/ratio_4x3/ratio_16x9`，各带 `boxFit` 与可选 `aspectRatio`。
- **改动** `lib/pages/live/live_room_page.dart`：
  - 字段 `int _aspectRatioMode` → `VideoFitType _videoFit`（默认 `contain`＝自动）；
  - **撤销**第一轮的 `_playerBoxAspectRatio`，外层容器恢复**固定 `AspectRatio(16/9)`**；
  - `_buildVideoSurface()` 改为上游组合：
    `ClipRect → FittedBox(fit: boxFit) → SizedBox(width: ar==null?源宽:源高*ar,
    height: 源高) → Texture`；
  - 菜单四项重挂上游语义：`16:9→ratio_16x9`、`4:3→ratio_4x3`、
    `原始比例→contain(自动)`、`铺满拉伸→fill`（标签不变）。

上游渲染依据（`media_kit_video/src/video/simple_video_texture.dart`，该项目 resolved-ref
`fd8421d`；`view.dart` 外层为 `FittedBox(fit: videoFit.boxFit)`）：
```dart
SizedBox(
  width: aspectRatio == null ? rect.width / dpr : rect.height / dpr * aspectRatio!,
  height: rect.height / dpr,
  child: Texture(textureId: id),
)
```

### 五、遗留与踩坑
- 「4:3」与「原始比例」在**源本身即 4:3** 时视觉一致（强制比例 == 源比例），属上游固
  有语义，非 bug。
- 默认档由「16:9」改为 `contain`（自动）：16:9 直播源观感不变，竖屏源默认不再变形。
- 构建降级坑同上（`ProgramFiles(x86)` 缺失，需先 `set`）。

### 六、小结（§2）
放弃自研「档位叠加容器比例」，直接移植上游 `VideoFitType` + `FittedBox` 组合：外层
容器固定 16:9，渲染全部交给 `FittedBox(fit: boxFit)` 与「按源尺寸/强制比例建盒子」，
四档互不等价且竖屏默认不变形。
