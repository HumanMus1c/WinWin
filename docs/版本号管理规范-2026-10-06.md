# 版本号管理规范（双号模型：版本名可持平/降级 · 版本代码只增不减）

> 日期：2026-10-06 ｜ 工具：`tools/version_tool.dart` ｜ CI 门禁：`.github/workflows/windows-x64-release.yml`
> 首版落地：`pubspec.yaml` 版本切换为 `0.1.0+26100601`（首个日期编码版本代码）

## 1. 背景与目标

Windows 端可无视版本号与签名随意覆盖安装；但 Android / iOS / Linux 对版本号极其敏感：

- **Android**：`versionCode` 必须单调递增才能覆盖安装（降级安装被系统拒绝 `INSTALL_FAILED_VERSION_DOWNGRADE`；Play 商店同样强制递增）；上限 `2100000000`（int32）。
- **iOS**：`CFBundleVersion`（= Flutter 的 build number）重复 / 回退会被拒收；用户只能装到最新。
- **Linux**：deb/rpm 降级安装需特殊参数（`--allow-downgrades` / `--oldpackage`）。

**核心诉求**：回滚 / 热修 / 重发时，用**旧版本代码**重新构建发布——版本名可以是旧值（持平甚至降级），但**版本代码必须大于历史最高值**，安卓端才能覆盖安装。因此建立本项目级纪律：

> **name 可持平、可降级；code 只增不减（唯一硬纪律）。**

## 2. 双号模型（单一事实源）

**事实源**：`pubspec.yaml` → `version: <name>+<code>`。Flutter 工具链自动完成各平台映射：

| 平台 | `name` 映射为 | `code` 映射为 |
| --- | --- | --- |
| Android | `versionName` | `versionCode`（int32，≤ 2100000000） |
| iOS | `CFBundleShortVersionString` | `CFBundleVersion` |
| Windows | `FILEVERSION` 前三段 + 字符串版本 | `FILEVERSION` 第 4 段（见 §5.3 截断说明） |
| Linux（未来立项） | 包版本主体 | 立项时决定是否附加 |

- **name**：人类沟通版本名。可持平、可降级；不参与单调性约束。规范形态：`MAJOR.MINOR.PATCH` 三段数字（当前采用语义化风格；未来如切换"日期对齐"风格 `YYYY.MM.DD` 亦合规，但需全项目统一）。
- **code**：整数，**单调递增**，由工具自动分配（编码见 §3）。
- **历史权威 = git 全 refs**（HEAD / 分支 / tag / 远端）上的 pubspec 版本变更记录：不维护账本文件，审计轨迹天然存于 git；hotfix 分支上同样能看到"全局已用到哪"。

## 3. 版本代码编码（YYMMDDnn）

**格式：`YYMMDDnn`（8 位定宽整数）** —— 当次编译日 + 当日构建序号：

| 场景 | code | 解码 |
| --- | --- | --- |
| 2026-10-06 首次构建 | `26100601` | 2026-10-06 第 1 次 |
| 同日重发 / 热修 | `26100602` | 2026-10-06 第 2 次 |
| 次日 | `26100701` | 2026-10-07 第 1 次 |

**分配算法**（`set` 命令自动执行，禁止手工编造）：

1. `todayBase = YYMMDD × 100`（如 `26100600`）；
2. `candidate = todayBase + 当日已用最大序号 + 1`（当日无记录则 `01`；序号容量 99 次/日）；
3. **防倒退兜底**：`final = max(candidate, 全局历史最大值 + 1, 当前工作区值 + 1)`
   —— 防时钟回拨 / 跨时区 / 手工跳号；兜底触发时工具会提示（形态脱离日期编码属正常保护，`check` 会标记提示）；
4. 上限校验：`≤ 2,100,000,000`（本方案全周期峰值 `99123199` ≈ 0.99 亿，余量极大）。

**跨天回滚友好性（本设计的核心优势）**：无论构建的是哪个旧版本的代码，code 一律取"**本次编译日**"编码——永远大于任何历史值，天然满足"回滚构建仍可覆盖安装"。

## 4. 分隔符与展示形态（四层约束）

| 层 | 形态 | 约束 |
| --- | --- | --- |
| pubspec 存储 | `version: 0.1.0+26100601` | **`+` 为语法规定，唯一合法**（SemVer 构建段；flutter_tools 硬编码 `split('+')` 提取） |
| UI / 文档展示 | `0.1.0 (26100601)` | 自由约定；规避 `+` 在 URL / 搜索中被编码为空格的问题 |
| git tag | `v0.1.0+26100601` | git ref 禁 `:` `[` `?` `*` `~` `^` `\` 等字符；`+` `-` `.` `( )` 合法 |
| 产物文件名 | `WinWin_windows_0.1.0+26100601_x64_setup.exe` | Windows 文件名禁 `< > : " / \ | ? *`；`+` `( )` `[ ]` 合法 |

**为什么不能换 `+`（常见疑问）**：

- `-`：语义变为**预发布**（`0.1.0-26100601` 排序低于 `0.1.0`），且工具链取不到 build number → **版本代码映射整体失效**；
- `[ ]` `:` `( )` `< >` 等：不在 pub_semver 语法内 → 工具链判定版本无效（警告 + 缺省回退），产物版本信息不可用。

## 5. 各平台语义

### 5.1 Android
`versionCode = code`（纯整数，直接参与覆盖安装判定）；`versionName = name`（任意字符串）。Play 商店要求 versionCode 严格递增。

### 5.2 iOS
`CFBundleVersion = code`（数字字符串）；`CFBundleShortVersionString = name`（须为数字点分，语义化 / 日期对齐两种 name 风格均合规）。

### 5.3 Windows（FILEVERSION 截断说明）
Flutter 将 build number 注入 `Runner.rc` 的 `FILEVERSION` 第 4 段；`rc.exe` 对超过 65535 的段值**静默截断为 u16（mod 65536）**——不报错、不影响构建；**字符串版本（Properties 面板 FileVersion / ProductVersion 文本）为完整原值**。Windows 本就不做版本管控，无实际影响。

### 5.4 Linux（未来立项时）
deb/rpm 包版本以 name 为主体；如回滚发布需覆盖安装，届时评估是否将 code 附加进包版本（注意 deb 版本比较规则）——单独立项，见后续文档。

## 6. 工具用法（`tools/version_tool.dart`，零依赖 Dart CLI）

```bash
# 显示当前版本 + 全局历史对照
dart run tools/version_tool.dart show

# 设置版本名并自动分配日期码（唯一的版本分配入口）
dart run tools/version_tool.dart set 0.2.0

# 保持版本名不变，仅重新分配 code（name 持平重发场景）
dart run tools/version_tool.dart set --code 26100602

# 版本纪律审查（退出码 0 通过 / 1 失败；CI 门禁同款）
dart run tools/version_tool.dart check

# 版本谱系审计（全 refs、按 code 升序）
dart run tools/version_tool.dart history
```

`check` 审查项：① name / code 格式与上限（硬）；② **code ≥ 全局历史最大值**（硬，降级覆盖风险门禁）；③ 日期编码形态提示（软）；④ 浅克隆检测；⑤ HEAD 上 `v*` tag 与版本一致性；⑥ 输出审计摘要。

## 7. 发布流程与场景规程（纪律）

**标准发布**：

1. `dart run tools/version_tool.dart set <name>`（自动分配日期码）；
2. `dart run tools/version_tool.dart check`（发布预检）；
3. 提交版本变更 → 打 tag **`v<name>+<code>`** → push（触发 Release 工作流；CI 内置同一审查门禁，失败即中止发布）。
4. **人工转正（发布纪律）**：工作流只产出**草稿（draft）Release**——产物与 Release 必须由**仓库所有者人工核对后手动转正**；工作流与工具永不自动转正。
5. 版本名升位的判定（大版本 / 小修复）参考《版本升位判定指南》（`docs/版本升位判定指南-2026-10-06.md`）——**指导性、非硬性**，最终由仓库所有者裁定。

**回滚 / 重发 / 热修**：一律经 `set` 重新分配（code 自动取全局更大值）；**禁止手写重复 code**。基于旧提交 / hotfix 分支构建同理——工具扫描全 refs，自动保证递增。

**发布路径与 tag 创建时机（2026-10-06 实证）**：

- **推荐路径（tag 由本地创建，固定指向发版提交）**：`git tag v<name>+<code>` → `git push origin v<name>+<code>` → 工作流构建 → 草稿 Release → 人工核对 → 转正；tag 与发版提交一一对应，无歧义。
- **dispatch 路径注意**：GitHub **草稿 Release 关联的新 tag 在草稿期间并不创建**，转正时才创建、且（当 target 为分支时）指向**分支的当时最新提交**；若走 `workflow_dispatch`（带 tag 输入）→ 草稿 → 转正，**转正前须确认 main HEAD == 发版提交**，否则 tag 与资产将对齐到最新提交，并额外触发一次 tag push 构建。
- **探测信号语义注记**：`flutter pub outdated` 的 `resolvable`（探测信号）可能比 `flutter pub upgrade` 的实际约束内升级范围更激进——探测为"宽触发"、gate 为"保守执行（约束内升级）"，属设计预期。

## 8. FAQ

- **为什么不用 git 提交计数作 code（PiliPlus 方案）？** 基于旧提交 / hotfix 分支构建时计数会回退，不满足"回滚覆盖"需求。
- **为什么不用现成 pub 工具（app_version_manager 等）？** 均为通用 bump，`revert` 会连同 code 一起回退，且无 git 历史单调性审查能力。
- **为什么不用四段版本号（如 `2026.10.06.1`）？** pub_semver 语法只允许三段数字 + 可选预发布 / 构建段；"同一天多次"由 `+code` 承担（构建号本就是为此设计）。
- **同日超过 99 次构建？** 序号溢出后走防倒退兜底继续递增（形态脱离日期编码，仍保证单调）；实际不可能触及。
- **两位年份到 2100 年怎么处理？** 兜底公式保证不冲突（候选变小则取历史最大值 + 1）；届时另行评估扩位。
