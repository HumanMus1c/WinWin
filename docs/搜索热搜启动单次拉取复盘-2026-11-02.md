# 搜索态「大家都在搜」改为启动单次拉取复盘（2026-11-02）

轮次：搜索态数据口径收口（非退役批次，闸门 0→0）
改动文件：`lib/pages/search/services/search_trending_cache.dart`、
`lib/pages/search/widgets/search_content_panel.dart`、
`lib/ui/home/home_page.dart`

## 一、现象

搜索态的「大家都在搜」20 条热搜，**每次进入搜索态都会重新联网拉取**（间隔超过
5 分钟即触发）；面板标题行已有「刷新」按钮，进场自动重拉属于重复请求，用户要求
改为**只在首次启动时后台静默拉取一次**。

## 二、定因

`SearchTrendingCache` 是 **5 分钟 TTL 缓存**：`ttl` 到期后 `peek()` 返回 null。
两个宿主（首页顶栏搜索态、独立搜索页）每次进入都会新建 `SearchContentPanel`，
其 `initState → _loadTrending()` 先 `peek()`；TTL 过期即落到 `fetch()` 重新请求。
因此「重复进出搜索态」在 TTL 过期后必然重复拉取。

## 三、方案

| 项 | 改动 | 说明 |
|---|---|---|
| 缓存口径 | 删除 `ttl` / `_fetchedAt` 与过期判定，`peek()` 恒返回已成功拉取的数据 | 进程内长期有效；重启才重新拉取 |
| 启动预取 | 保留首页首帧 `SearchTrendingCache.prefetch()` | 即「首次启动后台静默拉取一次」，命中缓存跳过 |
| 进场补拉 | `_loadTrending()` 缓存命中直接落数据、不联网 | 只有**从未成功拉取**（启动预取失败）才补拉一次 |
| 手动刷新 | `invalidate()` 置空缓存 → 重新请求；`_inflight` 并发合并保留 | 「刷新」按钮链路不变 |

## 五、遗留与踩坑

- 启动预取失败（离线 / 接口异常）时，首次进入搜索态仍会补拉一次；之后同样遵循
  「只拉一次」。若补拉也失败，热搜整块省略（此时标题行含刷新按钮一并省略），
  重启应用后恢复。
- 缓存仅进程内内存、不落盘；每次启动必然重新拉取一次，符合「首次启动」口径。
- 手动「刷新」在请求在途时点击，会复用同一在途请求（不重复发请求），结果落到
  缓存后即等价于刷新完成。

## 六、总结

热搜数据从「5 分钟 TTL + 每次进场复核」收敛为「进程内单次 + 启动预取 + 手动
刷新」，进出搜索态不再产生额外网络请求，展开动画期的加载态跳变也随之减少。

## 七、反馈轮 1：缓存已命中仍闪骨架

### 7.1 现象

首轮改动后，重复进出搜索态时数据虽已命中缓存，但**每次进场仍会先看到白色
骨架**（约一次展开动画时长），之后才换成 20 条热搜文本。

### 7.2 定因

`SearchContentPanel` 的热搜区渲染条件为
`if (_trendingLoading || !widget.contentReady)`：`contentReady` 是宿主的
「展开动画已落定」标志（首页顶栏展开 220ms + 80ms 兜底）。即使 `initState`
已同步命中缓存、`_trendingLoading` 为 false，只要动画未落定仍走骨架分支。
该门禁原本用于避免**数据在动画途中异步到达**时"矮→高"跳变触发
`AnimatedSize` 重跑；但对「首帧前数据就已绪」的缓存命中场景是多余的一刀。

### 7.3 方案

新增 `_trendingReadyAtFirstFrame`：`_applyTrending` 在 `!_built`（即首帧 build
前同步落数据）时置 true。渲染条件改为
`if (_trendingLoading || (!widget.contentReady && !_trendingReadyAtFirstFrame))`。

- 缓存命中（启动预取已就绪）→ 展开动画期间**直接渲染真实网格**，不再闪骨架；
- 数据在动画途中异步到达（首帧无缓存）→ 仍走骨架，等落定后换真身，保留原
  防"动画重跑"能力；
- 手动刷新 `_trendingLoading = true` → 仍显示骨架反馈。
