# 消息中心「请求过于频繁」风控修复复盘（2026-11-05）

## 一、现象

首次进入消息中心，会话列表区域显示服务端文案「请求过于频繁」，一条会话都不渲染；其他页面正常。该错误文本来自会话列表接口 `get_sessions` 的 `message` 字段，被 `_error` 原样透出。

## 二、定因

服务端对 `session_svr/get_sessions` 返回了限流类业务错误（典型 -509/-412 的「请求过于频繁」），不是本地解析或 UI 异常。WinWin 侧存在三个放大因素：

1. **读接口缺少 WBI 签名**：`get_sessions`、`fetch_session_msgs` 为裸参数直连；同文件的写接口（发消息/置顶/删除/已读）都做了 `WbiSign.makSign`。对照 PiliPlus 早期 Web 实现，`sessionList`/`sessionMsg` 是带 WBI 签名的，WinWin 移植时漏掉了读接口签名。
2. **Referer/Origin 域不匹配**：账号拦截器给所有 Web 请求的默认 Referer 是 `https://www.bilibili.com`，而消息中心网页端使用 `https://message.bilibili.com/`。
3. **无退避重试**：命中限流后直接透出文案，不会延迟重试，用户只能手动下拉刷新再次触发。

证据边界：Release 构建不记录业务响应（API 黑箱日志仅 debug 且只记字段名不记 code 值），因此精确错误码未被捕获；历史 debug 日志（10-09~10-26）显示该接口当时 HTTP 200 正常，结合上游实现签名的事实，判定为风控限流。

## 三、方案

1. **WBI 签名**（`lib/http/msg.dart`）：新增 `_sessionGet` 统一入口，`sessionList` 与 `sessionMsg` 改为「每次请求先 `WbiSign.makSign` 再发送」，参数集合保持原样（含 `size/pn/end_ts/web_location`）。
2. **Referer/Origin 对齐网页端**（`lib/core/account/account_mgr.dart`）：`api.vc.bilibili.com`、`/x/msgfeed/*`、`/x/im/*` 的请求默认 Referer 改为 `https://message.bilibili.com`，并补 `Origin: https://message.bilibili.com`；其余接口行为不变。
3. **限流退避重试**（`lib/http/msg.dart`）：命中 `-509/-412` 时延迟 2 秒重新签名重试一次；仍失败返回「请求过于频繁，请稍后重试」，其余错误码保留服务端文案。

## 六、遗留与踩坑

1. **精确错误码未捕获**：Release 无业务日志；若后续仍复现，需临时用 debug 构建记录 `code/message` 再定位。本次按「签名 + 来源头 + 退避」三管齐下修复。
2. **WBI 签名依赖 `/nav` 密钥缓存**：签名失败（如未登录/网络异常）时退化为裸请求，仍可能触发风控；该分支不做静默重试以外的处理。
3. **重试延迟 2 秒**：仅对 -509/-412 重试一次，避免无限重试放大限流；重试仍失败时保留用户下拉刷新入口。
4. **单次进入仍有 3 个首屏请求**：`single_unread` + `msgfeed/unread` + `get_sessions`，其中前两个为不同接口，暂未做合并节流；若后续仍触发限流，可考虑串行化首屏请求。

## 七、总结

消息中心「请求过于频繁」判为服务端风控限流，已通过读接口补 WBI 签名、消息域 Referer/Origin 对齐网页端、命中限流延迟重试三项一并修复；静态分析零问题、285 项测试全过、Windows debug/release 双编译成功。实际是否根治需进入消息中心实机确认会话列表能正常渲染。
