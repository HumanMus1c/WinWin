# 启动期高内存占用根因与修复复盘（2026-09-27）

> 触发场景：用户报告「程序运行时内存占用始终处于 1000MB 之上」。
> 调查方式：外部黑箱测量（进程内存/GPU 计数器/虚拟内存区域扫描/VM Service/Dart 探针应用对照），
> 最终通过临时环境变量诊断开关逐层二分定位到具体页面与具体组件。
> 修复文件：`lib/pages/whisper/msg_feed/msg_feed_page.dart`（全部改动集中于此，+6 行）

---

## 1. 分析根因

### 1.1 现象描述

| # | 现象（实测复现） | 期望 |
|---|---|---|
| 1 | Release 冷启动 10 秒 WorkingSet 即达 **988MB**，2 分钟曲线稳定在 980~1003MB | 与功能复杂度相称的内存（同机空白应用 102MB） |
| 2 | 进程 Commit 内存 2020MB；**GPU 专用显存 987MB + 共享显存 722MB** | GPU 资源与渲染内容相称 |
| 3 | 私有内存存在 **1707MB PAGE_NOCACHE 区域**（GPU 资源的 CPU 映射）：1×727MB（与窗口渲染尺寸联动）+ 20×32MB（恒定） | — |
| 4 | 全部大额分配在**启动后第 2~3 秒一次性完成**（窗口显示/首帧渲染阶段），之后完全稳定不增长 | — |

结论：**不是内存泄漏**（2 分钟无增长），而是「启动即建立的 1.6GB 常驻内存」。

#### 1.2.4 关键机制（Flutter 3.47 源码确认）

- `IndexedStack`（`lib/ui/app.dart` 根页面容器）为保持各页 State，会**构建全部 5 个根页面**；非当前页通过 `_RenderVisibility.paint: if (!visible) return;` **不绘制**（`flutter/lib/src/widgets/indexed_stack.dart`）；
- 但**图片解码与 live image 驻留与"是否绘制"无关**：`MsgFeedAvatar`（45px 显示）使用 `CachedNetworkImage` 时**未设置 `memCacheWidth/memCacheHeight`**，头像原图（B 站用户头像原图可达 1000+px）按**原分辨率**解码；
- 会话列表按 `size: 100/页` 游标分页加载（用户会话量大时多页），每行一个头像 ⇒ 数百张大尺寸解码位图；
- 这些图片被 offstage 页面的 widget 持续引用，构成 **live image**——**`main.dart` 中 `imageCache.maximumSizeBytes = 256MB` 只约束非活跃缓存，live images 不受该上限约束**；
- 叠加 GPU 侧资源（WDDM 记账的专用/共享显存与对应 NOCACHE 映射）后，形成 **1.6GB CPU+GPU 双份常驻**。

### 1.3 根因链

1. 根容器 `IndexedStack` 保活构建全部根页面 → 消息页启动即 `initState → SessionListSection._load()`；
2. 会话列表加载（100/页 × 多页）→ 每行 `MsgFeedAvatar` 发起头像加载；
3. 头像 `CachedNetworkImage` **无解码尺寸限制** → 按原图分辨率解码（每张可达数 MB）；
4. live image 不受 imageCache 上限管控 → 数百张大位图 + GPU 侧资源永久驻留；
5. 结果：进程 WorkingSet 988MB（用户感知「始终 1000MB 之上」）。

## 2. 设计修复计划

### 2.1 方案

给 `MsgFeedAvatar` 的 `CachedNetworkImage` 增加解码尺寸限制（**对齐项目既有 `NetworkImgLayer` 的 memCache* 策略**）：

```dart
// 解码尺寸限制（对齐 NetworkImgLayer 策略）：头像原图可能高达 1000+px，
// 不限制解码尺寸会让每张头像按原图解码（CPU 位图 + GPU 纹理双份占用）。
final dpr = MediaQuery.devicePixelRatioOf(context);
final decodeTarget = (size * dpr).round().clamp(64, 256);
...
memCacheWidth: decodeTarget,
memCacheHeight: decodeTarget,
```

### 2.2 关键决策与取舍

| 决策 | 理由 / 取舍 |
|---|---|
| 限制解码尺寸而非跳过加载 | 保留头像显示功能（W1 实验证明禁用图片可修复，但会丢功能） |
| 复用 `NetworkImgLayer` 既有策略 | 与项目统一策略一致（该组件早已用 memCache* + 缩略图后缀），本次是"绕过统一组件处的补漏" |
| `(size × dpr).clamp(64, 256)` | 头像显示 45 逻辑像素：1080p@1.0 DPR 需 45px、200% 缩放需 90px；上限 256 留足高 DPI 余量且杜绝原图解码 |
| 只改消息页头像（最小改动面） | 其余 14 处裸 `CachedNetworkImage` 不在启动路径/数量级小（见 §4.3 遗留项） |

### 4.1 改动面
