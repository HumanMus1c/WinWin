# 版本升位判定指南（大版本更新 vs 小修复）

> 日期：2026-10-06 ｜ 性质：**指导性文档（非硬性要求）**——版本号控制权完全归仓库所有者，最终升位由其裁定
> 关联：`docs/版本号管理规范-2026-10-06.md`（双号模型与工具）、`tools/version_tool.dart`
> 上游调研：PiliPlus / BiliPai 本地仓库实测（tag 历史与版本提交）

## 1. 目的

回答发布前的一个问题：**下一次发布，name（`MAJOR.MINOR.PATCH`）应该升哪一位？**
本文基于上游同类项目的**实际发布实践**归纳建议；不设硬性门槛、工具不做强制校验，仅作为发布前决策参考。

## 2. 上游实践观察（本地仓库实测）

### 2.1 PiliPlus（2.x 世代，tag 无前缀）

| 观察项 | 实践 |
| --- | --- |
| tag 形态 | `2.1.6` / `2.1.5` / `2.1.4` ……；**四段热修**：`2.1.3.1`、`2.1.2.1`～`2.1.2.3`、`2.0.9.1`～`2.0.9.2` |
| 发布节奏 | **PATCH 位逐个递增 = 每次正式发布**；MINOR 位（2.0 → 2.1）为阶段里程碑；MAJOR 极少变动 |
| 第四段含义 | 同一 PATCH 发布后的**快速热修**（补丁中的补丁），如 2.1.3 发布后补 2.1.3.1 |
| 发布提交 | 专用 `Release 2.1.6` / `Release 2.1.5` 提交（发布动作集中落地，区间内 fix / opt / feat / 依赖升级混合） |

### 2.2 BiliPai（0.x 世代，tag 带 `v` 前缀）

| 观察项 | 实践 |
| --- | --- |
| tag 形态 | `v0.3.1` / `v0.3.0` / `v0.2.9`……；**预发布通道**：`v0.2.3-alpha.2`～`alpha.10` → `v0.2.3` 正式 |
| 发布节奏 | PATCH 位逐个递增 = 每个发布；MINOR 位（0.2 → 0.3）= 成批 feat 后的里程碑 |
| versionCode | 每次发布 +1（427 → 428 → 429…）；**非发布的构建单独 bump code、不动 name**（如 `chore: bump versionCode to 435`） |
| 发布提交 | `Release v0.2.7` / `Bump version to 0.2.6 with version code 428`（版本名与版本代码在同一提交落地） |

### 2.3 共识与差异（归纳）

- **共识**：
  1. MINOR 位承载"**功能批次 / 里程碑**"（成批新功能落地后升）；
  2. PATCH 位是**发布滚动位**——小修复与小改进都走它，逐个 +1；
  3. MAJOR 位极少使用（两者都处于 0.x / 2.x，尚未进入破坏性大版本循环）；
  4. 发布前都有一个**专用版本提交**（Release / bump），集中记录版本动作。
- **差异（热修与预发布的管理）**：上游用「**第四段**」（PiliPlus）或「**alpha 后缀通道**」（BiliPai）；**本项目均不使用**（pub_semver 不支持四段、后缀对 iOS / 商店分发不友好）——等价机制为 **name 持平 + code 递增**（见下）。

## 3. 本项目的建议判定（指导，不强制）

| 变更类型 | 举例 | 建议升位 | 备注 |
| --- | --- | --- | --- |
| 重大变革 / 不兼容 | 数据格式迁移、架构重写、首个正式版宣示（1.0.0） | **MAJOR** | 0.x 阶段克制使用 |
| 成批新功能 / 里程碑 | 新模块上线、多个页面或系统级改进集中落地 | **MINOR** | 对应上游的"阶段性 Release" |
| 小修复 / 优化 | bug 修复、样式 / 文案、性能优化、依赖小升级 | **PATCH** | 最常见的发布形态 |
| 同版本重发 / 热修 | 打包问题重发、发布后即发现的小补丁 | **name 持平、code 递增** | 替代上游「第四段 / alpha」的机制 |
| 回滚发布 | 回退到旧版本代码重新构建 | **name 可降、code 递增** | 双号模型核心场景（安卓覆盖安装保障） |

**发布前快速自检三问**：

1. 本次变更包含"用户可感知的新功能"吗？——是 → MINOR；否 → PATCH。
2. 是否存在"不兼容 / 需要用户迁移"的变化？——是 → MAJOR。
3. 只是重发 / 回滚 / 小补丁？——name 持平或降级，靠 code 递增区分（`set` 自动处理）。

## 4. 与流程、工具的关系

- `dart run tools/version_tool.dart set <name>`：**name 由人工指定**——工具不推断、不强制升位；
- `dart run tools/version_tool.dart check`：只做**硬性纪律**校验（name 格式、code 单调递增等），**不对升位做任何判定**；
- 发布流程的决策窗口：Release 以**草稿**形式产出，人工核对时若发现版本号与变更规模不匹配——删除草稿（tag 未创建前）→ `set` 修正 → 重新触发发布即可；**转正前是版本号修正的最佳窗口**。

## 5. 权属声明

- 本文为**参考指南**：不构成发布流程的硬性要求，任何建议位次均可调整或推翻；
- **版本号的最终控制权完全归仓库所有者（HumanMus1c）**——`set` 允许在任何时间指定任意合规 name（可持平、可降级）。
