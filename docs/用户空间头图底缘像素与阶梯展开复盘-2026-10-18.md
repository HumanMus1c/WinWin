# 用户空间头图底缘异常像素修复 + 阶梯展开头图 复盘（2026-10-18）

> 范围：`lib/pages/member/member_space_page.dart`（头图渲染重写 + 阶梯展开交互）。
> 关联：本文件为「非 B7 项」审计轨迹，不计入 B7 批次；闸门（`lib` 内 `import 'package:material_ui` 文件数）保持 **5**。

## 一、现象

用户反馈（附截图 `1792254783270-742d2047.png`）：

1. **用户空间头图（顶部横幅）下边缘有异常像素**；
2. 希望新增：**在用户空间滚动使背景图展开到全尺寸的「阶梯步进」，向上滚动阶梯收回初始尺寸态**。

### 取证（像素级）

对截图做程序化分析（`PIL`）：

| 项 | 结果 |
|---|---|
| 截图尺寸 | 2560 × 523（局部裁切图） |
| 异常行 | 第 **412** 行，亮像素 **2162** 个；其上/下行亮像素均为 **0** |
| 该行颜色 | (73,29,25)/(55,57,76)/(109,37,24)… **饱和红蓝**（头图原图内容） |
| 上下文 | 300~411 行 ≈ (19,19,22) 纯页面背景（遮罩已不透明）；413+ 行同色 |

→ 判定：**头图在 AppBar 底边比遮罩层多露出 1 物理像素行**，露出未被压暗的原图 = 那条亮线。

## 二、定因

- 头图高度 `_coverHeight = 330`（逻辑像素）；本机 **DPR = 1.25**，330 × 1.25 = **412.5 物理像素** —— AppBar 底边落在**半物理像素**上。
- 原实现在 `FlexibleSpaceBar.background` 内用 `Stack(fit: expand, [CachedNetworkImage(cover), Container(渐变遮罩)])` **两层**结构：头图图层与遮罩 Container 图层各自参与合成、各自取整，半像素边界处两者取整方向不一致（图片向上取整到 413、遮罩向下取整到 412）⇒ 第 412 行只画了头图、没被遮罩覆盖 ⇒ 亮线。
- 参照上游 PiliPlus `member/widget/user_info_card.dart` `_buildHeader`：其头图为**单张 `CachedNetworkImage`**（显式 `width/height`、`color`/`colorBlendMode` 压暗、短淡入），**不存在第二层遮罩**，因此天然不产生该缝。

## 三、方案

### 缺陷 1：头图底缘异常像素（采用上游 PiliPlus 写法）

于 `_buildHeaderBackground` 收敛为**单层结构 + 显式收边**：

- 头图改用 `CachedNetworkImage`：显式 `width`、`fit: BoxFit.cover`、`memCacheWidth`（沿用的解码口径）、
  **短淡入/淡出（120ms）**、`placeholder`/`errorBuilder` 均回落默认渐变（对齐 PiliPlus 的 placeholder 写法）；
- 外层再包 `ClipRect` + `Stack(clipBehavior: Clip.hardEdge)`，把子层硬裁到同一框；
- 渐变遮罩由「`Stack` 内 `Container`」改为 **`Positioned.fill(DecoratedBox(...))`**，与头图**严格同框**，消除层间子像素缝；
- 保留原有 4 段渐隐观感（顶部压暗 → 中部透明 → 底部收到页面背景），仅重构绘制层级。

> 说明：`cached_network_image_ce 4.13.1` 的 `CachedNetworkImage` **无 `gaplessPlayback` 参数**（上游 PiliPlus 所用版本有），故以 `placeholder` 回落替代，其余写法对齐。

### 缺陷 2：阶梯展开头图（触发方式取「悬停/点开后才接管滚轮」，防误触）

- 新增状态：`AnimationController _expandCtrl`（220ms 补间） + `double _expandTarget`（0~1 档位进度） + `bool _headerHovered`；
- **触发**：头图外层 `MouseRegion`（`onEnter/onExit` 维护 `_headerHovered`）+ `Listener(onPointerSignal:)`；
  **仅当指针悬停于头图**时，滚轮才用于展开/收回；未悬停时**不注册**，滚轮交给 `NestedScrollView` 正常滚动（防误触）。
- **抢占**：悬停时以 `GestureBinding.instance.pointerSignalResolver.register(event, ...)` 注册滚轮信号 ——
  本 `Listener` 在命中链上比 `Scrollable` 更靠内、先注册先得，故**展开时页面内容不跟着滚动**（"不干扰页面滚动"）。
- **阶梯步进**：`_expandStepCount = 6`，每滚一格 = ±1 档（`1/6`），离散档位而非连续跟随滚动；
  `expandedHeight` 由 `AnimatedBuilder` 跟随 `_expandCtrl.value` 在 `[初始 330, 全尺寸]` 间补间 → "阶梯步进"手感。
- **全尺寸**：`_expandedCoverHeight` = 按背景图**自然宽高比**折算到当前窗口宽的高度（异步经 `ImageStreamListener`
  读 `info.image.width/height` 回填 `_bannerAspect`），兜底 4:1，夹到 `[_coverHeight+80, 视口高×0.92]`。

## §2 第二轮（2026-10-18 01:33）滚轮交互方向修正 + 头图跳变 / 数字藏品分析

> **勘误**：本篇 §一~§七「阶梯步进 / 分 6 档 / 滚轮向下展开」的**交互口径作废**，以本节为准（方向翻转 + 取消分档 + 增加"页面最顶端"闸门）。§一~§七 的**像素修复部分仍然有效**。

### 一、现象

用户反馈三条：

1. **滚轮交互方向做反了**：本意是「滚轮向下 = 页面上滚」；期望在**用户空间、页面处于最顶端、鼠标悬停在头图上**时，**滚轮向上滚动**（页面往下滚的方向）→ 头图**一次性展开**（不再分档步进）。
2. **头图进入瞬间跳变**：部分用户的背景头图会在进入页面的瞬间，**从一个非默认头图跳变为默认头图**。
3. **动态数字藏品头图无法渲染**：部分用户的空间背景头图是**动态数字藏品**对象，当前似乎无法渲染；要求**分析上游 PiliPlus 是否具备渲染这类对象的能力**。

### 二、定因

- **交互方向**：原实现 `dy > 0（滚轮向下）→ 展开`，与用户直觉相反；且 `_expandStepCount = 6` 的离散分档不符合"一次性展开"诉求。
- **头图跳变（高置信推断）**：`_buildHeaderBackground` 的取图优先级为
  `images?.topPhoto ?? images?.imgUrl ?? _extraTopPhoto?.topPhoto ?? _extraTopPhoto?.imgUrl ?? _cardInfo?.spaceLImg/SImg`。
  空间接口（`_loadSpace` → `images`）的兜底字段（`l_img`/`s_img`，多为**平台默认空间背景**）优先级**高于**专用头图接口
  `/x/space/top/photo`（`_loadTopPhoto` → `_extraTopPhoto`）的真实头图。十个加载 Future 并行执行：
  专用接口**先返回** → 先渲染真实头图；空间接口**后返回** → `images` 优先级更高，把真实头图**覆盖为兜底默认图** ⇒ 即用户看到的"非默认 → 默认"跳变。
- **数字藏品**：WinWin 的 `MemberImages.fromJson` 只解析 `imgUrl` / `nightImgurl` / `top_photo`，
  **完全没有解析 `collection_top_simple`**（B 站空间接口中承载藏品头图的对象）⇒ 藏品封面 URL 取不到 → 回落 `l_img`/`s_img`（默认）⇒ "无法渲染"。

### 三、方案

#### 已实施：滚轮交互修正（点 1）

- **方向翻转**：滚轮**向上**（`scrollDelta.dy < 0`）→ 头图**展开**；滚轮**向下**（`dy > 0`）→ **收回**。
- **取消分档**：删除 `_expandStepCount` 与 `_stepExpand`，改 `_setExpand(bool)` 直接补间到 `0` / `1`（一次性展开 / 收回，260ms `easeOutCubic`）。
- **增加闸门**：`_onHeaderPointerSignal` 仅在 `_scrollController.offset <= 0.5`（**页面最顶端**）且**悬停头图**时注册信号；其余情况**不注册**，交还页面正常滚动（进一步降低误触）。
  未展开时向下滚 → 不拦截，页面正常下滚；已展开时向下滚 → 先收回，再继续滚才翻页。

#### 待确认（点 2 / 点 3，本轮仅分析，未改代码）

- **点 2 修法**：调整取图优先级——专用头图接口（`_extraTopPhoto`）的真实头图应**优先于**空间接口的 `l_img`/`s_img` 兜底；并接入 `gaplessPlayback` 语义（该版本 `cached_network_image_ce` 无此参数，可用 `placeholder` + 短淡入替代）避免 URL 切换闪跳。
- **点 3 移植**：参照 PiliPlus 补全 `collection_top_simple` 解析与渲染（见下）。

### 四、上游 PiliPlus 数字藏品渲染能力分析（点 3 结论）

**结论：PiliPlus 具备渲染该类对象的能力**（以静态对齐图 + 轮播 + 角标形式呈现，不播放逐帧动画）。

证据链（`D:\Documents\GitHub\PiliPlus`）：

| 环节 | 位置 | 关键实现 |
|---|---|---|
| 数据模型 | `lib/models_new/space/space/images.dart` | `SpaceImages.collectionTopSimple`（读 `json['collection_top_simple']`） |
| 藏品结构 | `.../space/collection_top_simple.dart` → `.../space/top.dart` | `CollectionTopSimple.top` → `Top.imgUrls`（读 `json['result']` 列表）→ `TopImage` |
| 单图字段 | `top.dart` `TopImage.fromJson` | `_defaultImage = image.default_image`；`fullCover = json['cover']`；`header = _defaultImage ?? fullCover`；由 `image`/`item.animation` 的 `location`+`height` 折算垂直对齐 `dy = (start+end)/height - 1` |
| 渲染 | `lib/pages/member/widget/user_info_card.dart:556` `_buildV` → `_buildCollectionHeader` | 单张：`_buildHeader(..., alignment: Alignment(0.0, img.dy))`；多张：`PageView.builder` 轮播 + `HeaderIndicator` 页码 + `HeaderTitle` 标题角标 |
| 兜底 | 同文件 | `collectionTopSimple` 为空时回落 `images.imgUrl` / `nightImgurl` |

→ 即：**藏品封面 = 一张（或一列）网络图**，PiliPlus 用 `cover`/`default_image` 取图、用 `image.location` 折算 `dy` 做**垂直取景对齐**，
多张时用 `PageView` 轮播 + 页码 + 标题角标。**它并不播放动画**——`animation` 字段仅用于推导 `dy`（当 `image` 缺失时兜底）。

**WinWin 现状差距**：`MemberImages` 无 `collectionTopSimple` 字段，`_buildHeaderBackground` 只吃单张 URL，
故藏品头图取不到封面 → 回落默认。**修复路径 = 移植 PiliPlus 的 `collection_top_simple → Top → TopImage` 解析链**，
在 WinWin 头图渲染处按 `imgUrls.length`（0/1/多）分流，并对单张应用 `Alignment(0.0, dy)` 对齐。

## §3 第三轮（2026-10-18 01:46）数字藏品头图渲染移植 + 头图跳变修复（点 2 + 点 3）

> 承接 §2 的"待确认"两项，本轮经用户确认（"确认，继续做点 2 + 点 3"）后**实施**。

### 一、现象

- **点 2**：部分用户空间背景头图在进入瞬间**从非默认头图跳变为默认头图**。
- **点 3**：部分用户的背景头图是**动态数字藏品**对象，**无法渲染**（回落默认）。

### 二、定因

- **点 3（确定性）**：WinWin `MemberImages.fromJson` 只解析 `imgUrl` / `nightImgurl` / `top_photo`，**未解析 `collection_top_simple`**；
  而 B站 `/x/v2/space`（`Api.space`）响应的 `data.images.collection_top_simple` 正是藏品头图载体（PiliPlus `SpaceData.fromJson` 从**同一接口**读取）。
  取不到 ⇒ 回落 `l_img` / `s_img`（≈**平台默认**）⇒ "无法渲染"。
- **点 2（机制）**：`_buildHeaderBackground` 的 `CachedNetworkImage` **未启用 gapless 语义**。十个加载 Future 并行时，
  取图来源可能**先解析出真实头图、后又被兜底默认图覆盖**（专用 `/x/space/top/photo` 先到、空间接口 `/x/v2/space` 后到）；
  **URL 变更 → 组件重解析 → 先渲染 `placeholder`（= 默认渐变）** ⇒ 即"跳变为默认头图"。对藏品用户，因 `collection_top_simple` 未解析，
  取图直接落到兜底默认图，表现为稳定地"停在默认"。

### 三、方案

1. **模型（`lib/http/member.dart`）**：新增 `MemberCollectionTop` / `MemberCollectionImage`；`MemberImages` 增 `collectionTopSimple` 字段并解析
   `collection_top_simple`。`dy` 由 `item.image.location`（`"x-start-end"` 取后两段）+ `height` 折算（`(start+end)/height-1`），
   `headerUrl = default_image ?? cover` —— 对齐 PiliPlus `TopImage`。
2. **渲染（`member_space_page.dart`）**：`_buildHeaderBackground` 新增**最高优先级分支**——`collectionTopSimple.images` 非空即渲染：
   - 1 张 → `Alignment(0.0, dy)` **垂直取景对齐**；

## §4 第四轮（2026-10-18 02:04）高级头图取数来源修正 + 展开尺寸口径重定义

用户实机复验 §3 后给出三项反馈（第 1、2 条为同一 URL、同一描述，实为**同一问题**）：

1. `https://space.bilibili.com/8465957` 无法加载高级头图，自动降级到默认；
2. （同 1，重复描述）
3. `https://space.bilibili.com/235630215` 无法一步完全展开头图。

### 一、现象

- **现象 A（点 1/2）**：该用户空间头图总是显示为兜底的普通背景图/默认渐变，看不到他设置的「高级头图」。
- **现象 B（点 3）**：头图滚轮展开动作"有反应但看不出展开"——只涨了一点点，像是没展开。

### 二、定因

**现象 A｜取数端点已下线（硬证据）**

- 代码里"高级头图"走 `MemberHttp.topPhoto` → `/x/space/top/photo`。实测该端点**已下线**：
  `api.bilibili.com` 与 `app.bilibili.com` 两个基址均返回 **404 + HTML 错误页**（加参数仍 404）。
- 应用内日志佐证：每次进空间**成对**出现
  `Http: 响应体非 JSON Map（runtimeType=String），按接口失败处理` +
  `MemberSpace: topPhoto 加载失败 mid=… err=获取背景图失败`
  （`D:\Documents\logs\runtime.log`，01:42–01:55 反复出现）。
- ⇒ 高级头图**永远取不到**，只能回落到普通 `l_img`（该 URL 本身 200 正常，非防盗链问题）。
- **共因缺陷（顺带修掉）**：取图链原用 `??` 串联，取的是**首个非 null**。任一环节返回**空串**
  即截断后续全部兜底（`hasPhoto=false`）→ 直接落到默认渐变。这本身就能造成"降级到默认"，
  与端点下线是两个独立成因，故一并修正为**首个非空**。

**现象 B｜展开尺寸语义选错（算法问题，不是参数问题）**

- 实测两名用户头图原图均为 **1280×200（≈6.4:1）** 的超宽横幅。
- 旧口径 `_expandedCoverHeight = clamp(宽 / 6.4, 初始 330 + 80 = 410, 视口高 × 0.92)`：
  1920 宽下自然高 = 300，比初始 330 还矮 → 被下限抬到 410 → **一次展开仅 +80px**，观感"没展开"。
- 更本质：B站空间头图**天然就是 6.4:1 的超宽横幅**，"按图片自然比例折算全尺寸"这一语义
  对宽图无法产生可见展开 → **是语义选错，不是参数没调**。

### 三、方案（用户已拍板：点 3 取方案 A，点 1/2 取方案 1）

- **点 3 · 方案 A（沉浸式满屏）**：`_expandedCoverHeight` 改为与图片比例**无关**的
  **视口高 × 0.92**（下限 初始 + 80）。任何用户"一步展开"的幅度一致且显著。图片以
  `BoxFit.cover` 呈现（超宽图会左右裁切，属沉浸式满屏的预期代价）。
  - 随之删除 `_bannerAspect` / `_bannerAspectUrl` / `_resolveBannerAspect` 机制及 3 处调用
    （该机制的唯一用途就是旧口径的折算；保留会触发 `unused_element`）。
- **点 1/2 · 方案 1（换取数来源）**：`MemberHttp.topPhoto` 改打
  **`/x/space/wbi/acc/info`**（`Api.memberInfo`，`WbiSign.makSign` 签名，参数对齐上游
  PiliPlus `MemberInfoModel`），取 `data.top_photo`；**取不到 `top_photo` 时返回空
  `MemberImages` 的 Success**（该用户本就没有高级头图，属正常态），不再产生失败日志。
  回落链保持原顺序：`images.topPhoto → images.imgUrl → acc/info.topPhoto → 卡片 l_img/s_img`，
  即**用可用端点顶替失效端点所在的槽位**，对 `/x/v2/space` 正常的用户零影响。
- **诊断加固**：`_pickHeaderPhoto` 列表化 + 新增 `_logHeaderSource(source, url)`，
  记录头图**最终选用来源 + 解析后 URL**（同一结果只落一次，不刷屏），供实机复核取证。
