> 任务来源：本次对话。修复评论区无法显示评论附带的图片与 GIF、官方表情 `[xxx]` 显示为文本占位两项缺陷，

> 改动面：7 个文件（6 改 + 1 新增，+134 行）；快照基准 `7ce21f0`（stash 引用 `ddc383e`）。

## 1. 分析根因

### 1.1 现象描述

视频详情页 / 番剧播放页 / 专栏文章页 / 动态详情页 的评论区存在三个缺陷：

1. 评论附带的图片与 GIF **完全不渲染**（界面中直接消失，无占位）；
2. 官方表情（`[doge]`、`[打call]`、`[大哭]` 等）**显示为文本占位**；
3. 评论图片无任何点击放大/多图预览能力（动态页与文章正文均有，评论区没有）。

### 1.2 取证证据

**（a）接口返回确认（游客态实测 `/x/v2/reply/main`，样本 aid=117337432917883）**

```json
"content": {
  "message": "梦之队加油呀！！！[打call]",
  "emote": { "[打call]": { "url": "https://i0.hdslb.com/bfs/emote/….png",
                           "text": "[打call]", "meta": { "size": 1 } } },
  "pictures": [ { "img_src": "https://i0.hdslb.com/bfs/new_dyn/….png",
                  "img_width": 3840, "img_height": 2160, "img_size": 2413.112,
                  "top_right_icon": "https://i0.hdslb.com/bfs/activity-plat/…png",
                  "play_gif_thumbnail": true } ]
}
```

- `content.emote` 键为表情转义符（含中括号），值为表情图 URL 与尺寸档位；
- `content.pictures` 字段集与 PiliPlus `models_new/reply/picture.dart`、gRPC `Picture` proto（6 字段）完全一致；
- 请求层无需改动（字段本来就在响应中，只是被解析丢弃）。

**（b）GIF 行为实测（对 B站 CDN `new_dyn` 图片逐项探测）**

| 探测项 | 结果 |
|---|---|
| 源 `.png` 默认直连 | 静态 PNG（单帧，与 `img_size` 完全一致） |
| `@.gif` / `@240w.gif` / `@480w.gif` | GIF89a 但**单帧**（严格块解析逐帧核对） |
| `@.webp` / `@240w.webp` | 静态 WebP（无 VP8X/ANIM 动画块） |
| 同 hash `.gif`/`.webp`/`.mp4` 直连 | 404 |

- 结论：B站对"大表情"类（`play_gif_thumbnail=true` 的 png/jpg 源）在 CDN 上**只提供静态渲染 + `top_right_icon` 角标**，不存在可取的动图版本（第三方客户端 PiliPlus/BiliPai 同样按静态处理）；
- `play_gif_thumbnail` 语义为"应播放缩略图"，与官方 BiliRoamingX「UnlockGif」补丁行为一致；
- 仅 `.gif` 源图原样直连才能保留动画（BiliPai `isGif()` 同款判断）。

**（c）参考实现检索（全局规则：移植/复用优先）**

- PiliPlus `reply_item_grpc.dart::_buildMessage`：表情 → `WidgetSpan` 图片，尺寸 `size × 20px`；
- PiliPlus `ImageGridView` / BiliPai `CommentPictures`：评论图片网格与点击进画廊；
- WinWin 现成件：`showImageGallery`（动态页在用）、动态页 `_buildDrawGrid` 九宫格视觉、`BilibiliEmotes`（直播弹幕在用）、`NetworkImgLayer`。

### 1.3 根因链

```
接口返回 content.emote / content.pictures
  → lib/models/video/reply_item.dart 的 ReplyContent.fromJson 只解析 message，字段被丢弃【根因1】
  → 4 个页面共 6 处渲染点全部是纯 Text(reply.content?.message)（无 span、无网格、无预览入口）【根因2】
  → 即使有 .gif 源，ImageUtils.thumbnailUrl 的 @…webp 转码会将其转为静态首帧（动图丢失）【根因3】
```

## 2. 设计修复计划

### 2.1 方案与关键决策

| # | 决策 | 依据 |
|---|---|---|
| 1 | `ReplyContent` 补 `emote`/`pictures`/`pictureScale` 三个字段（新增 `ReplyEmote`、`ReplyPicture` 小模型，逐字段容错解析） | 对照 PiliPlus REST 模型；请求层零改动 |
| 2 | 新建**共享组件** `lib/common/widgets/comment/reply_content_view.dart`（`buildReplyEmoteSpans` + `ReplyContentView` + `ReplyPictureGrid`），统一承接 6 处渲染点 | 避免出现第 5 份复制粘贴（视频/番剧本就是复制关系，文章/动态为第三、四份） |
| 3 | 表情渲染：`[xxx]` → `WidgetSpan` 图片；URL 优先 `content.emote`，回退内置 `BilibiliEmotes.defaultEmotes`；尺寸 `20px × meta.size`（上限 40px，PiliPlus 口径）；解码受 `decodeClamp` 限制 | 参照直播弹幕 `_buildDanmakuContentSpans` + 动态 `_buildRichSpans` |
| 4 | 图片网格：单图自然比例（0.5~2.0，`picture_scale` 缩放上限），多图九宫格（4 图 2 列 / ≥3 图 3 列 / 其余 2 列，最多 9 张，单元格 50~130px）；`top_right_icon` 右上角标 | 视觉与动态页 `_buildDrawGrid` 一致（用户明确要求"动态页同款"）；比例口径取 BiliPai 评论组件 |
| 5 | 预览：点击图片 → `showImageGallery`（原图 + 首帧缩略，与动态页调用方式一致） | 复用动态页已验证的全屏画廊（缩放/滑动/保存/复制/按键） |
| 6 | GIF 修复：`ImageUtils.thumbnailUrl` 对 `.gif` 源跳过 CDN 变换原样返回 | 动图经 `@…webp` 转码会变静态首帧；其余调用方（封面/头像/表情）不受影响 |
| 7 | 明确不做：评论输入框表情选择器、`content.members`（REST 中为 @ 用户列表）、新依赖 | 防过度设计，控制改动面 |

### 2.2 取舍说明

- **"大表情"类图片动图化放弃**：实测 CDN 无动图版本可取（§1.2b），与 PiliPlus/BiliPai 行为一致；以静态图 + 官方角标呈现，不做无依据的 URL 猜测（防止把 2.4MB 静态 PNG 当作动图拉取）。
- **不改请求层**：字段本来就在响应里，改解析即可，避免触碰三级容灾逻辑。

## 4. 本轮修复总结

- **改动面**：7 文件（+134 行）——
  - `lib/models/video/reply_item.dart`：`ReplyContent` 补 3 字段 + 新增 `ReplyEmote`/`ReplyPicture` 模型；
  - `lib/common/widgets/comment/reply_content_view.dart`（新增 ~295 行）：表情 span 构建器 + 富内容视图 + 图片网格 + 角标；
  - `lib/utils/image_utils.dart`：`.gif` 源跳过 CDN 转码（+4 行）；
  - 4 个页面 6 处渲染点接入（video×2、bangumi×2、article×1、dynamics×1）。
- **行为预期**：评论图片（单图/多图）与官方表情全部正常渲染；点击图片进入动态页同款全屏预览；
  `.gif` 源图片保留动画；"大表情"类图片按官方口径静态呈现并带角标。
- **遗留项**：
  1. 评论输入框的表情选择器仍未接入（本次范围仅"渲染"侧）；
  2. 楼中楼接口（`/x/v2/reply/reply`）的 `emote`/`pictures` 字段以文档口径与主列表同构实现，实机样本覆盖后如有差异需回归；
  3. `play_gif_thumbnail=true` 且源为 png/jpg 的"大表情"动图化（B站 CDN 无动图版本，需等待官方开放或走 SVGA 体系）。
