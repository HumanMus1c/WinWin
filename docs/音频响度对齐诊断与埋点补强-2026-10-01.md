# 音频响度对齐：实机诊断结论 + 埋点盲点补强（2026-10-01）

**本轮性质**：**诊断 + 埋点补强**（非功能修复）。用户要求"分析日志，诊断音频响度均衡是否存在
问题、是否符合预期"。诊断结论为**存在问题、不符合预期**，并修复了导致无法一次确诊的**埋点盲点**。

本文档按五要素记录（根因 / 方案 / 验证 / 总结 / 提交与回滚）。

## 一、分析根因

### 1.1 诊断结论

| 项 | 结论 | 依据 |
|---|---|---|
| **B（菜单恢复）** | ✅ **符合预期** | 会话内 `Coverage: player menu audio opened` ×5（14:54:36/42/46、14:55:34 等）。该菜单的渲染条件正是 `audioCodecLabel != null`，只有读对实例才非空 |
| **D（静态增益）** | ❌ **不符合预期：增益恒为 1.0，响度对齐未生效** | 见 1.2 证据链 |

### 1.2 D 未生效的证据链

会话：`pid 30492`，2026-10-01 14:54:01 启动（Debug 构建）；`runtime.log` 该会话共 23 行。

1. **14:54:29 有 `PlayerController: setMedia`** —— 该路径会调用 `_recomputeNormalizationGain`；
2. **14:55:23 `setting.hive` 被写入** —— 正是用户在播放器音频菜单中**选中响度均衡模式**的时刻
   （`setAudioNormalize` → `Pref.audioNormalization = config` → Hive 落盘），该路径也会调用增益计算；
3. **两处均无 `Coverage: loudness gain` 日志**；
4. **直接读取 Hive 存储确认当前设置值为 `'2'`（智能响度均衡）**：

   ```
   $env:APPDATA\com.winwin\winwin\hive\setting.hive
   offset 778:  01 12 "audioNormalization" 04 01 00 00 00 32
                └ 键帧 ┘ └── 18 字节键名 ──┘ └─ 长度 1 ─┘ └ '2'
   ```

   （读取方式：该文件被运行中进程独占，需以 `FileShare.ReadWrite` 共享读打开。）

⇒ **既然不是"禁用"（`'0'`），则"无增益日志"只可能来自**：`playUrl.volume == null`、
`volume` 各字段全 0、或 `measuredI` 非负。**三者都使增益恒为 1.0 —— 响度对齐实际未生效。**

### 1.3 导致无法一步确诊的埋点盲点（本轮的"根因"）

原探针只在**成功算出增益**时才记录：

```dart
if (pref == '0' || v == null || !v.isNotEmpty) { gain = 1.0; return; }  // 静默
if (measuredI >= 0) { gain = 1.0; return; }                            // 静默
… AppLogger.w('Coverage', 'loudness gain: …');                          // 只有这条会记
```

⇒ "没有日志"**无法区分**三种早退原因。这是本轮诊断卡住（需要绕道读 Hive 才能定性）的直接原因。

### 1.4 一条被排除的错误线索（避免后人重走）

曾试图用黑箱 API 日志（`blackbox_api.log`，仅 Debug 初始化）证明"接口未返回 `volume`"：
搜索 `volume` / `loudness` 均 0 命中，**看似**支持该结论。但进一步检查发现
**该日志的响应体是被截断的**：

```
…baseUrl":"https://…/upgcxcode/97/62/... [truncated, total: 86139 chars]
```

⇒ "搜不到"是**截断造成的假象**，不能作为证据。

同时按"本地参考库优先"核对 **PiliPlus**：它使用**同一接口、同一组参数**
（`fnval=4048`、`voice_balance=0`、`fourk=1`）并从 `json['volume']` 解析 ——
**说明该接口本身会返回响度元数据**。

⇒ **"为何本次没有元数据"暂不能定论**，需靠补强后的探针复现一次来区分是
"接口真未返回"还是"本项目请求/解析路径有差异"。

## 二、设计修复计划与实现

**改动**：`lib/pages/video/player_controller.dart` 的 `_recomputeNormalizationGain` ——
**每条早退路径都写一条带原因的覆盖探针**（纯日志，零行为变更）：

| 分支 | 新增日志 |
|---|---|
| 模式为禁用 | `loudness gain: skipped (mode=0 已禁用)` |
| `playUrl.volume == null` | `loudness gain: skipped (playUrl.volume == null，接口未返回响度元数据)` |
| volume 字段全 0 | `loudness gain: skipped (volume 各字段全 0，无实测数据)` |
| `measuredI` 非负 | `loudness gain: skipped (measuredI=… 非负，不符合 LUFS 约定)` |
| **成功算出增益** | `loudness gain: measuredI=… targetI=… tp=… → N.NNNx` |

设计原则：**让"机制是否生效、以及为何不生效"完全可从日志自证**，不再需要绕道读存储文件。
