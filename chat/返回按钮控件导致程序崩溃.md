## 架构要点总结

1.  **共享单例播放器**：`WinWinPlayerController` 内部用静态 `_sharedPlayer` + `_playerCount` 引用计数（`player_controller.dart` 第 56-57 行）。每个详情页构造时 `_playerCount++`，dispose 时递减，归零才真正释放底层 mdk.Player。
    
2.  **返回按钮极简**：直接 `Navigator.pop(context)`，没有任何前置拦截，依赖 `dispose` + `RouteAware` 回调自动完成释放/上报/暂停。
    
3.  **没有 PopScope / WillPopScope**：整个 `lib/pages/video/` 目录下未发现这两类 widget，Android 系统返回键走默认 pop 行为。
    
4.  **didPushNext/didPopNext 而非 dispose** 是页面切换时（push 新视频页 / 返回）恢复播放进度的核心路径；`dispose` 只在真正销毁页面时触发。
    
5.  **弹幕重建信号**：`didPopNext` 中 `ctrl.reloadDanmaku()`（`player_controller.dart` 第 770 行）触发 `danmakuReloadSignal.value++`，因为 `PlayerPanel` 始终挂载、`WinWinDanmaku` 不随路由重建，需要显式通知弹幕层清空引擎并重新拉取 dm。

## 根因分析完成

**崩溃机制已 100% 确认**，证据链如下：

1.  **崩溃性质**：[run\_debug.log](file:///D:/Documents/GitHub/WinWin/run_debug.log) 末尾是 `Lost connection to device`——进程直接死亡，是原生层硬崩溃，不是 Dart 异常。
    
2.  **触发路径**：返回按钮 → `Navigator.pop` → 页面 `dispose()` → [player\_controller.dart](file:///D:/Documents/GitHub/WinWin/lib/pages/video/player_controller.dart#L939-L959) → `_playerCount` 归零 → `_sharedPlayer.dispose()`。**整条 pop 路径上没有任何 pause/stop 调用**（`didPushNext` 有暂停，但返回时没有）——播放器在解码循环全速运行时被直接销毁。
    
3.  **原生崩溃点**（读 fvp 0.37.3 Windows 插件源码 [fvp\_plugin.cpp](file:///C:/Users/SilverT1ger/AppData/Local/Pub/Hosted/pub.flutter-io.cn/fvp-0.37.3/windows/fvp_plugin.cpp#L74-L85) 确认）：视频播放中时，mdk 的渲染回调每帧（16-33ms）执行 `renderVideo(); MarkTextureFrameAvailable(textureId)`。而 fvp 的 `Player.dispose()` 内部顺序是**先释放纹理**（`ReleaseRT` → `UnregisterTexture` \+ 销毁 `TexturePlayer` 对象）**后停止播放**（`state = stopped`）。销毁后仍在飞行中的渲染回调访问已释放的 D3D11 资源/对象 → `EXCEPTION_ACCESS_VIOLATION`。这正是 fvp 已知 issue [#321](https://github.com/wang-bin/fvp/issues/321) （Windows 崩溃堆栈完全吻合）和 [#131](https://github.com/wang-bin/fvp/issues/131) （loading 中 dispose 崩溃）的机理。
    
4.  **修复方案**：在 `_sharedPlayer.dispose()` 之前**同步先置 `PlaybackState.stopped`**——停止解码/渲染循环（同时中止加载中的请求，覆盖 #131 场景），再走 fvp 内部的释放流程，竞态窗口关闭。这也是 PiliPlus「dispose 前先暂停」的标准做法。
