# 2026-08-10 Work Log

## 修复 onLoginMain 删除账号导致登录完全失败

**问题**: 上一轮修复后"连登录状态都不变了"。根因：`Accounts.set()` 调用
`onLoginMain()` 时不传 `fallbackMid`，当 web nav 返回"账号未登录"时，
`onLoginMain()` 执行 `Accounts.deleteAll({account})` **删除了刚创建的账号**。

**修复** (`lib/core/account/login_utils.dart`):
- `onLoginMain()` 自动从 `Accounts.main.mid` 获取 `fallbackMid`
- **绝不删除账号**——即使所有 API 都失败，也用最小模型设置登录态
- 账号删除仅在 `onLogoutMain()` 中执行
- 三级回退不变：web nav → app 端 → 最小模型

**编译结果**: Debug ✓ (20.9s) + Release ✓ (55.8s)

## QR 扫码登录"登录成功"但未登录状态修复

**问题根因**: `LoginUtils.onLoginMain()` 在 QR 登录成功后调用 `UserHttp.userInfo()`
（`/x/web-interface/nav`）拉取用户信息。TV QR 登录返回的 cookie 可能无法被 web 端
`/x/web-interface/nav` 接口接受（返回 `isLogin=false` 或 `-101 账号未登录`）——
cookie 兼容性/激活问题。此时：
- `AccountService` 不会被更新 → 个人页显示"未命名用户"、所有数据为 0
- 若错误为"账号未登录"，账号会被删除
- 但 `_setAccount` 中的 "登录成功" toast 仍然弹出 → 用户看到矛盾现象

**第一阶段修复**（最小登录态兜底）:
- `onLoginMain()` 新增 `fallbackMid` 参数（来自 QR/密码/短信登录响应的 `mid`）
- web nav 失败时，用 `fallbackMid` 构造最小 `UserInfoModel(isLogin: true, mid: ...)`
- 当 `fallbackMid` 存在时不再删除账号
- 返回 `bool`，调用方据此显示不同 toast

**第二阶段修复**（用户数据回退到 app 端）:
- 新增 `Api.userInfoApp = 'https://app.bilibili.com/x/v2/account/myinfo'`
- 新增 `UserHttp.userInfoApp()`：使用 `access_token` 鉴权，绕过 web cookie 问题
- 调用时必须传非空 queryParameters（`{'platform': 'android'}`）以触发
  `AccountManager` 的 app 端签名流程（添加 access_key + appkey + ts + sign）
- `onLoginMain()` 新逻辑：
  1. 先试 web nav（含 vip 信息）
  2. 失败回退到 app 端 userInfoApp（access_token 鉴权，TV QR 一定可用）
  3. 都失败用 fallbackMid 设最小登录态
- 关键 Dart 语法注意点：`Success` 类的字段名是 `response`（不是自定义名），
  `==` 不能用作常量模式匹配（用嵌套 if 或 `when` 子句）

**调用方更新** (`lib/pages/login/login_page.dart`):
- `_setAccount`: 传入 `tokenInfo['mid']` 作为 `fallbackMid`，根据返回值显示不同 toast
- `_CookieLoginTab._login`: 传入 `account.mid` 作为 `fallbackMid`

## PiliPai 分析 + buvid 激活修复（根本原因）

**问题**: 前面的修复（cookie 注入、app 端 API 回退、fallbackMid）都没解决问题。
分析 PiliPlus 源码后发现根本原因。

**PiliPlus 关键代码分析**:
- `lib/utils/accounts.dart` `Accounts.set()` 在设置账号后调用:
  1. `Request.buvidActive(account)` — 激活 buvid3 cookie
  2. `LoginUtils.onLoginMain()` — 拉取用户信息
- `lib/http/init.dart` `Request.buvidActive()`:
  调用 `/x/internal/gaia-gateway/ExClimbWuzhi` API 激活 buvid3
- **WinWin 完全缺少 buvid 激活步骤**！
  未激活的 buvid3 不被 web API 接受 → web nav 返回 isLogin=false

**修复**:
1. `lib/http/init.dart`: 新增 `Request.buvidActive(Account)` 方法
   （移植自 PiliPlus，调用 `Api.activateBuvidApi` = `/x/internal/gaia-gateway/ExClimbWuzhi`）
2. `lib/core/account/accounts.dart`: `Accounts.set()` 现在依次执行:
   - 保存账号到 Hive
   - `Request.buvidActive(account)` 激活 buvid3
   - `LoginUtils.onLoginMain()` 拉取用户信息（仅 main 账号）
3. `lib/pages/login/login_page.dart`:
   - `_setAccount`: 移除单独的 `onLoginMain()` 调用（由 `Accounts.set()` 处理）
   - `_CookieLoginTab._login`: 简化为 `Accounts.set()` + 检查 `AccountService().isLogin`
   - 移除未使用的 `UserHttp` import

**PiliPlus vs WinWin 流程对比**:
```
PiliPlus: setAccount → onChange → set accountMode → (switchAccountDialog → Accounts.set → buvidActive → onLoginMain)
WinWin  : _setAccount → onChange → Accounts.set → buvidActive → onLoginMain → toast
```
现在 WinWin 的流程与 PiliPlus 一致。

**问题**: 即使添加了 app 端 API 回退，web nav 仍然失败。根本原因是
`cookie_jar` 的 `loadForRequest()` 域名匹配不稳定——TV QR 登录返回的 cookie
存入 `domainCookies['bilibili.com']` 后，对 `api.bilibili.com` 的请求
可能匹配失败，导致 cookie 未被发送。

**BiliPai 方案分析** (`D:\Documents\GitHub\BiliPai`):
- `AppSessionCookieJar.loadForRequest()` 不依赖 cookie_jar 的域名匹配
- 每次请求时从 `TokenManager` 缓存直接注入 SESSDATA/bili_jct/DedeUserID/buvid3
- 先 remove 同名 cookie 再 add，确保缓存值优先

**移植到 WinWin**:
1. `LoginAccount.keyCookies` getter (`lib/core/account/account.dart`):
   直接从 `cookieJar.domainCookies['bilibili.com']['/']` 读取
   SESSDATA/bili_jct/DedeUserID/DedeUserID__ckMd5/buvid3

2. `AccountManager.onRequest` 修改 (`lib/core/account/account_mgr.dart`):
   - `loadForRequest` 结果 + `account.keyCookies` 合并
   - keyCookies 优先：先移除 jarCookies 中的同名 cookie
   - 确保关键 cookie 始终被正确注入，绕过域名匹配

这解决了 web nav 返回 `isLogin=false` 的根本原因——cookie 未被发送。

**问题**: `flutter_inappwebview_windows` 插件在 `add_custom_command(TARGET)` 中使用
`DEPENDS` 关键字，CMake 3.28+ 策略 CMP0175 产生 dev 警告。

**修复** (`windows/CMakeLists.txt`):
