# Taste
- When an attempted fix reintroduces an older regression, expects it to be rolled back immediately to the last known-good state instead of being iterated on in place; experimental changes are not kept just because they partially helped. Confidence: 0.7
- Prefers root-cause analysis grounded in recent git commit history and the project's `docs/` development documents before writing any code; asks for an explicit development plan rather than immediate edits. Confidence: 0.8
- Prefers an evidence-first workflow: add structured runtime logging/tracing and run an A/B variant matrix to get objective data before touching fragile logic — especially in code with a history of fix-then-revert cycles. Confidence: 0.75
- When trading off in a fix, prioritizes correctness (e.g. deterministic synchronization) over speed, accepting slight added latency. Confidence: 0.6
- Runs `dart analyze` expecting 0 error / 0 warning, and builds both `--debug` and `--release` Windows configs, reported separately; dislikes temporary-directory builds. Confidence: 0.7
- Surfaces raw build-output warnings back to the agent and expects each one explained and driven to a clean run: the root cause stated, a re-run in an uncontended state to obtain a 0-warning record, and environment-caused warnings (e.g. `MSB3026` copy retries because the running app locks `WebView2Loader.dll`) clearly distinguished from real code warnings rather than silently tolerated. Confidence: 0.5
- Has a standing rule that nothing is committed until both Debug and Release builds pass — a blocked/failed build (e.g. the running app holding a DLL) is a hard reason to hold off committing and retry after the build is re-run, never something to commit past. Confidence: 0.65
- Treats a pre-change snapshot (`git stash create` → `refs/snapshots/latest`) as a mandatory step for every change — a stated global rule, not optional — and calls it out when it's skipped. Confidence: 0.85
- Uses bracketed conventional commit messages: `[type](scope): 中文描述`, with a detailed Chinese bullet-point body (root cause / fix / verification numbers / doc reference) and a `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer, written to a UTF-8 (no-BOM) file and committed via `git commit -F` to avoid PowerShell encoding mangling. Confidence: 0.7
- Maintains a per-fix document under `docs/` named `{主题}复盘-YYYY-MM-DD.md`, covering five elements: root cause / fix plan / verification / summary / commit records (including the rollback snapshot SHA and the push status). Confidence: 0.7
- A fix isn't finished until it's committed to local git and pushed to `origin main`; expects the real commit hash to be backfilled into the docs afterwards, and when the push is blocked by the environment (e.g. proxy down) wants the blocker stated plainly and carried as a pending item to retry, not quietly dropped. Confidence: 0.7
- Keeps plan/scratchpad documents synced into the global plans directory (`~/.commandcode/plans/`) and has the plan reviewed before committing. Confidence: 0.5
- Expects the agent to run the whole fix pipeline to completion on a bare "继续" — snapshot, edit, analyze, debug+release builds, docs, commit, push — without pausing for step-by-step approval, reserving the user's involvement for on-device manual verification. Confidence: 0.6
- Does not weaken security settings to work around failures (e.g. never disables SSL/TLS certificate verification for a failing `git push`); prefers to keep retrying and report the blocker. Confidence: 0.6
- Communicates in Chinese and expects replies in Chinese. Confidence: 0.9
- Wants to be able to build/run the app himself: asks for exact, copy-pasteable Debug/Release compile-and-run commands (build output paths, `flutter run -d windows`) instead of relying solely on the agent to drive builds. Confidence: 0.5
- Prefers to drive end-to-end verification himself by manually interacting with the running app; asks for automated test drivers (e.g. scripted auto-seek) to be turned off while keeping the underlying logging/observability fully in place. Expects a self-run verification (e.g. an A/B comparison) to be spelled out as a concrete, numbered protocol: which config to edit, the exact repeated actions, what to watch for (回退 / latency), and when to hand the trace log back. Confidence: 0.65
- Expects the feasibility of candidate solutions to be re-evaluated against the latest releases/changelogs of the relevant libraries and dependencies before committing to an approach. Confidence: 0.7
- Has a standing, explicitly-named rule of "local reference library first" (本地参考库优先): when investigating a bug or choosing a design, consults the checked-out comparable open-source project (e.g. PiliPlus) for its concrete implementation/source evidence and aligns this project's behavior and values to it (e.g. porting its error-message mapping and timeout constants) rather than inventing its own. Confidence: 0.65
- Prefers to port/replace with a proven, mature implementation (e.g. switching the player core to mpv/media_kit, as PiliPlus does) over continuing to pile custom patches on an in-house approach once it keeps failing. Confidence: 0.6
- Once several successive fix attempts have failed, expects the agent to stop patching and instead lay out the remaining candidate solutions with their costs/risks and wait for the user to pick the direction (approval before acting, snapshot first). Confidence: 0.5
- Expects a newly added switch / code path to be confirmed as actually active from runtime logs before being told a fix is in place and asked to test again; a fix that was reported as live but never took effect (unparsed config flag) erodes trust and is called out as the "same old problem". Confidence: 0.5
- When a format/library-based approach fails, expects the actual capability of the bundled runtime to be verified empirically (e.g. scanning the shipped binary/DLL for compiled demuxer/library symbols) to pin down the true root cause, rather than assuming the format is supported. Confidence: 0.55
- Pushes back on continuous corrective machinery (e.g. a per-second drift-correction loop) as needless runtime overhead and asks why correctness isn't enforced strictly at the operation boundary instead (e.g. exactly synchronizing clocks at the seek instant); expects the residual cost of any ongoing/background work to be justified. Confidence: 0.6
- Wants an explicit, evidence-backed coverage accounting of every candidate solution he has proposed (tried / rejected / never actually run), rather than a blanket claim that options are exhausted; probes whether supposedly-tried approaches were truly exercised before accepting a new direction, and then directs the agent to actually run the specific not-yet-exercised candidate. Confidence: 0.6
- Expects the visible task/TODO list above the input box to be kept in sync with actual progress (completed items marked done, new pending items added) and to be cleared out once a piece of work is finished ("清理Todos列表"), not just summarized in prose — he checks the panel himself after a task is declared done and calls out leftover entries directly ("对话框上方的 Todos 列表没有清理掉"). Note that clearing actually requires overwriting the list with a final all-completed list (the panel ignores an empty update), and expects the agent to fix it immediately on being told. Confidence: 0.65
- Monitors the agent's intermediate reasoning/thinking as it works and follows up on anything unclear or alarming in it — asks for internal shorthand / log-derived terms the agent coined (e.g. "重挂为 0") to be explained in plain language and for an explicit yes/no on whether they indicate a real defect, expecting the raised concern to be investigated rather than waved off. Confidence: 0.55
- After manually verifying a fix on-device he reports it very tersely (e.g. just "已测试自然播放完成一条视频"), often without attaching anything, and expects the agent to locate the trace/log file on its own, confirm from the evidence whether the fix and no-regression hold, and keep mining that log for additional latent issues (ranked by severity) rather than stopping once the reported symptom is gone; log auditing is a standing per-round duty — even when he judges the state essentially complete (e.g. "似乎已经比较完善了") or the experience already "基本无感" (imperceptible), he still directs the agent to read the latest session's runtime log and analyze anomalies, without first naming a specific bug; a good perceived experience is explicitly not taken as evidence that the log is clean — e.g. after confirming "已复测，开关弹幕不再出现程序无响应" he immediately asks whether the rest of the video-playback pipeline still has other problems. Confidence: 0.8
- Prefers cloud pushes to be deferred/batched to the very end of a work session rather than pushing each commit as it lands: local commits proceed normally, and only the accumulation of pending commits gets pushed once, at the end. Confidence: 0.6
- When a new symptom appears during otherwise-normal operation, reports the observed behavior concisely (hedged with uncertainty, e.g. "历史播放进度似乎跳了2秒左右") and asks for it to be investigated/confirmed first ("请你调查是否是这样？") — cause and even existence verified from evidence — rather than asking for an immediate fix. Confidence: 0.65
- When he reports that a just-delivered fix didn't work (terse, e.g. "仍然是双重音频" / "still double audio"), expects the agent to treat the previously stated root cause as unconfirmed and go back to fresh runtime-log evidence to derive the real mechanism, rather than re-applying or defending the earlier fix. Confidence: 0.55
- When reporting a bug he usually supplies his own root-cause hypothesis (e.g. "音视频没有保持同样的缓冲尺度" / "声音和视频没有同步缓冲与缓冲长度") and expects the agent to validate it against source/runtime evidence — confirming or correcting it — then fix the verified mechanism, rather than accepting his guess at face value or ignoring it. Confidence: 0.6
- When reporting a bug he ranks the observed symptoms by severity ("最主要的是… 其次…") and explicitly labels the ones he can live with ("…但是仍然可接受"), expecting the primary problem fixed first while the tolerable ones are treated as lower-priority / optional improvements. Confidence: 0.5
- Uses simulated weak-network (弱网) conditions as a standard reproduction/verification scenario for network- and player-related fixes, and reports the resulting behavior changes as the acceptance criteria. Confidence: 0.55
- Once the reported symptom is confirmed gone, expects the remaining backlog items to be triaged by *necessity* — each justified with evidence (prior reproduction history, whether the trigger path is still reachable, cost/risk) and explicitly labeled must-do / nice-to-have / observe-only — instead of being worked off indiscriminately; unreproducible issues should not be patched blindly but kept as observation items with their instrumentation in place. Confidence: 0.6

Confidence: 0.6
- Is comfortable with temporarily instrumenting production source for diagnosis (env-var-controlled probe modes, a blank root widget, page-filter flags), provided a persistent git snapshot is taken first and every diagnostic artifact (flag file, temp widget, imports) is removed and verified gone (grep showing zero residual references) so the delivered diff contains only the real fix. Confidence: 0.55

Confidence: 0.6
