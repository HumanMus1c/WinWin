# Coding preferences

- Prefers upgrading legacy Material 2 widgets to current official Material 3 equivalents rather than leaving them in place — e.g., `MenuAnchor`/`MenuItemButton` over `PopupMenuButton`, `DropdownMenu` over `DropdownButton`, `RadioGroup` over `RadioListTile`'s deprecated `groupValue`/`onChanged`. Trend toward eliminating deprecated/legacy components fully (targets "清零", not partial). Confidence: 0.65
- When introducing a new widget, aligns with patterns already used elsewhere in the same repo (对齐项目已有范式) instead of inventing a new approach. Confidence: 0.5
- When a legacy API has no clean modern equivalent, prefers keeping it and documenting the rationale rather than forcing a hacky migration (recorded, not silently degraded). Confidence: 0.5
- Preserves existing visual/interaction semantics (colors, tooltips, selected-state highlighting) when refactoring widgets, and when migrating to a new design language he explicitly names the visual effects that must survive the migration intact — e.g. insisting the home search box / category filter keep their *whole-control* frosted-glass background blur, with the expectation that the untouched code path is how that guarantee is met. Confidence: 0.55
- During a design-language/library migration, does not want the app's own iconography degraded: when the migration swapped the navigation icons for the library's uniform monochrome icons he demanded the original colored, per-item-accent icons be restored and the library applied only to the surrounding chrome ("只将每个导航除图标外的设计替换为flutter_miuix样式", "没有替换之前的彩色图标好看"). Also treats a stroke-style mismatch inside one control (one outline icon among filled ones) as a defect — an icon set must read as coherent. Migration fidelity to the library is subordinate to keeping the app's established color/visual richness on icons. Confidence: 0.5
- When an official/built-in SDK capability can achieve the goal, prefers it over introducing a third-party dependency — e.g. chose theming Flutter's built-in SnackBar (`snackBarTheme`, floating dark card) and converged all call sites on one helper, rather than adopting toastification/motion_toast. Confidence: 0.5
- When a UI direction was picked from an earlier demo/proposal, expects the real implementation to reproduce the agreed behavior including its interaction details (e.g. tap-anywhere-to-close on the card), not a visually similar but behaviorally reduced version. Confidence: 0.45
- Treats third-party dependency currency as a standing review item: asks whether a dependency is "最新版本库" and whether the project can be updated to the latest release, not only when something breaks. Confidence: 0.5
- When he asks about an upstream library's recent update activity ("最近的更新动态"), expects every recent commit to be judged for whether it actually matters *to this project*, with the verdict grounded in primary evidence rather than a changelog summary: check from the code whether the dependency is even still used (grep `lib/` + `pubspec.yaml` versus docs/README), line the commits up against the published release dates on pub.dev, and answer commit-by-commit (relevant / irrelevant for the current codebase / reference value only if the library were adopted) — a fix in a library the project has migrated away from must be reported plainly as having no bearing on the current code, with the migration rationale cited from the docs. Confidence: 0.45
- Prefers adopting the purpose-built upstream library/port of a design language over an in-house approximation of it — e.g. asked whether the hand-rolled `UiStyle.miuix` enum + token layer could be swapped for the community `flutter_miuix` port of compose-miuix, i.e. fidelity to the real design language (HyperOS/Miuix) outranks keeping the dependency count low. Confidence: 0.45
- Once he commits to such a library adoption, wants the migration driven all the way to completion — the legacy/in-house rendering path fully replaced ("完全化替换", not a partial or token adoption), with the remaining work broken into sub-stages that each run the full pipeline until nothing is left un-migrated; a terse "继续后续阶段" is the green light to keep going to the end. The library component is the default for *everything*: when a round ships with a list of self-built components kept "保留自研" for design-rationale reasons (既有设计, no direct upstream equivalent, floating dark card, badge set, token layer), he rejects that framing and insists they be migrated too — a hand-built component may only stay when blocked by a genuine hard constraint, and he expects such exceptions to shrink to a single, named case ("除了首页头部（模糊约束），是目前为止唯一需要保留的，其余都应该使用 X"). Confidence: 0.6
- Migration completeness is subordinate to his own visual judgment: he accepts — and explicitly asks for — reverting a library-migrated component back to the app's own original implementation when the library version looks or feels worse. E.g. he rejected the newly-migrated pull-to-refresh indicator as a regression of the previously-working one ("不是本已正常的下拉视觉样式… 原已有的下拉视觉更好") and had it restored to the previous implementation, and had the navigation rail reverted to the self-drawn colored version. A previously-shipped visual that he was happy with outranks finishing the migration. Confidence: 0.55
- Icons for stateful/toggle interactions must ship as a proper dual-state pair: outlined/stroke when inactive (off) and filled/solid when active (on). An icon that renders filled at rest—e.g. because the chosen source supplied only a single filled glyph for a two-state semantic—is flagged as a recurring defect ("又碰到了老问题，部分图标常态显示为填充而不是描边") and must be fixed by pairing genuine off/on glyphs (or falling back to a source that has the outline variant) rather than reusing one shape for both states. Confidence: 0.6
- For numeric appearance/style settings he prefers a continuous slider over a dropdown/select menu: asked the subtitle "字重" (font weight) picker to be changed to "同样的 slider 滑动调节" — the same control the other style rows already use — with an explicit min/max/step (100–900, step 100). Wants settings within the same visual family to share one control idiom, numeric style values living on sliders, and does not want a control-type inconsistency among sibling rows. Confidence: 0.5
- Treats the official platform's own artwork as the fidelity target for icons/art: he directs the agent to crawl the official site's real assets (page-inline SVG, icon fonts, script-rendered DOM) and swap the project's in-house drawings and third-party approximations for the official originals ("抓取一遍官方网站的美术素材，替换本项目美术素材"), accepting the official shape even when it differs from the previously used Material equivalent. Confidence: 0.55
- Maintains a set of art/UI assets he has previously ordered "fixed" and expects any bulk art-replacement sweep to carve them out by default — he restates the exception every time he requests such a sweep ("仍然排除曾要求固定的某些美术"), so the delivered change must leave those pinned items untouched and confirm it. Confidence: 0.5
- Menu/option icons must be sized to match their adjacent label text — an icon whose size differs from the option's text is reported as a defect ("图标和选项的文本大小保持一致"). Wants the icons within one menu to read as optically uniform (driven by the row's text size) rather than each item hardcoding its own size or mixing sources that render at visibly different optical weights. Confidence: 0.5
- When a UI detail is refined in one place, expects the same change propagated to every other component/entry point that presents that same control (e.g. "同步改进其它视频卡片会触发的『更多操作』的选项的图标", not just the instance the report happened to name), so the app's instances of one control stay visually identical — consistency across duplicated UI is the acceptance bar. Confidence: 0.45
- A design-language/library swap must preserve the control's *actual runtime behavior*, not just its appearance: when the newly-migrated `MiuixPullToRefresh` left the comment section and message center completely un-pullable (not even an indicator rendering), he reported it as a defect and expected the real mechanism root-caused from the component's own source plus a minimal reproducing test — with the migration kept and fixed forward, not reverted or guessed at. Standing rule derived for scroll views: never leave a bare `AlwaysScrollableScrollPhysics()` (with no parent chain it inherits the base no-op boundary conditions, so pixels over-scroll unbounded and **no `OverscrollNotification` is emitted**, silently swallowing overscroll), because `OverscrollNotification`-driven widgets then stop working — wrap it as `ClampingScrollPhysics(parent: AlwaysScrollableScrollPhysics())` (or another bounded physics). Confidence: 0.5
- After committing to a design-language migration, expects the new design language to own framework/theme-level defaults too, not just individual controls: a legacy library's platform default still in effect (e.g. `pageTransitionsTheme` still resolving to material_ui's default `ZoomPageTransitionsBuilder`) is treated as an unfinished migration item, and he challenges it directly ("MD3 风格相关的所有控件元素都移除了吗？为什么程序还在使用 material_ui 的默认转场主题？"). The fix is to replace it with the new design language's own behavior — and when the adopted library ships no ready-made component for that surface (flutter_miuix has no page transition), implement it per that library's published spec/design tokens (e.g. `MiuixMotion` entry/exit curves) rather than keeping the legacy default, retaining the old default only as an explicit one-key fallback. Confidence: 0.5
- Does not want `dart format` run on existing files at all: a whole-tree `dart format lib` is forbidden (the project is not run under global formatting; a global run silently reflows ~237 unrelated files), and scoping the formatter to just the handful of files a change actually touched is *also* unsafe — those files carry pre-existing format drift, so a per-file run still produces hundreds of reflowed lines of unrelated diff (e.g. ~800 lines across 3 files), forcing the diff way beyond the intended change. In both cases the mistake is caught by checking `git diff --stat`, the reflowed files are reverted (`git checkout -- <files>`), and the edits are re-applied by hand to match each file's current style so the final diff contains only the intended change. Standing repo rule: formatting is a hand-done, change-local activity, never a formatter sweep. Confidence: 0.55
- Borrows a third-party/platform control for its *behavior* only, never its default visual style: after a design-language migration he reported the newly-adopted text-selection toolbar's right-click menu as 不符合 Miuix 规范 (the library's own native toolbar look) and expected it rebuilt from the app's own unified menu building blocks — same overlay panel / menu row components, same open/close animation rhythm, same Esc semantics, Chinese labels plus semantic icons — while keeping just the behavior from the third-party control. Every user-visible menu/overlay must render on the single adopted design track; a native/default-styled surface is a defect, not an acceptable byproduct of reuse. Confidence: 0.55
- During a design-language migration, deliberately drops the legacy control's incidental style overrides (`style:`, padding, `shape`, `visualDensity`, explicit colors) so the new library's own sizing/colors take over, while explicitly preserving the overrides that carry *meaning* — selected-state emphasis (bold + color on the active sort/filter row), danger/failure semantic color (danger buttons kept red via the new library's color escape hatch), and interaction affordances (long-press / secondary-tap menus moved out to an outer gesture wrapper). The resulting visual deltas are enumerated as an on-device comparison list rather than treated as regressions. Confidence: 0.45
- In mechanical replacement batches holds a strict zero-visual-change line: the substitute wrapper must render identically to what it replaces, and any artwork/vector upgrade is deliberately deferred to a separate, explicitly named later batch (e.g. "美术替换统一归 b7-d"), keeping each batch's diff behavior-preserving. Confidence: 0.5
- Replacement wrappers must be drop-in compatible with the widget they replace — mirror its named-parameter surface, adding whatever is missing (e.g. `semanticLabel`, `autofocus`, `readOnly`, `textInputAction`, `colors`) so call sites migrate without being rewritten; when a parameter genuinely has no upstream equivalent, it is compensated elsewhere (e.g. `maxLength` → `LengthLimitingTextInputFormatter`) rather than dropped. Confidence: 0.5
- Converges scattered raw library constants into named semantic accessors (e.g. `AppIcons.loadFailed()`, `AppIcons.imageBroken()`, `AppIcons.singleChoice(selected:)`) so a later art/glyph swap is a single-point change instead of a repo-wide hunt. Confidence: 0.5
- Carves out the replacement component's own fallback call site from mechanical sweeps — e.g. the `Icon(` fallback *inside* the `AppIcon` wrapper is retained and documented, since converting it would recurse infinitely — and excludes it explicitly from the residual scan. Confidence: 0.45
- After a design-language migration, judges the control by its runtime *feel* and typography against the app's pre-migration behavior, treating the library's own defaults as a defect source rather than a neutral baseline: a placeholder/hint that comes out at the library's larger label size (e.g. 17px) and fades away on an animation instead of disappearing the instant text is entered is reported as "字体太大 / 隐藏滞后"; the expected fix is to reproduce the app's previous compact size (≈13px) and instant, animation-free hide (e.g. a self-drawn hint layer) rather than accept the library default. Confidence: 0.5
- Expects text inputs to show an unmistakable focus state: clicking into an input must produce a blinking caret *and* a visible focus border change, matching how the same control behaves elsewhere in the app (a live-room input styled differently from the video-page comment input is reported as "样式不统一"). An input that focuses silently — no caret and no border change (e.g. because the caret color inherited a transparently-set border color) — is a defect, and getting only one of the two is not sufficient. Confidence: 0.5
