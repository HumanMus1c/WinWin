# Workflow preferences

- Takes a pre-change git snapshot before making changes (project convention: `git add -A; git stash create` → `git update-ref refs/snapshots/latest`), one snapshot per change round, so each round has an independent rollback point restored via `git reset --hard <SHA>`. Confidence: 0.7
- Verifies changes with a full `dart analyze` targeting 0 error / 0 warning and no newly introduced issues, plus both `flutter build windows --debug` and `--release`, before committing. Confidence: 0.6
- Writes a retrospective ("复盘") markdown doc into `docs/` for each change, structured by five elements (根因 / 方案 / 验证 / 总结 / 提交与回滚) with rollback SHAs and a manual on-device verification checklist. Confidence: 0.6
- Batches git pushes: commits locally throughout the work, then pushes to `origin/main` once at the end of the session ("推送按惯例在会话末尾统一执行"). Confidence: 0.6
- For multi-round work, records a plan file under `~/.commandcode/plans` named `{主题}计划-YYYY-MM-DD.md` (background/conclusion → decision → numbered execution steps → rollback → status checklist), surfaces it in the Plans panel for approval, and rewrites the status checklist and execution results as the round progresses; tracks steps with a todo list. Confidence: 0.6
- Executes approved changes step by step, in priority order, returning to the user for confirmation before starting. Confidence: 0.5
- Wants generated artifacts surfaced in the OS file explorer (open Explorer and select the file via `explorer.exe /select,"<path>"`) rather than only reported as a text path. Confidence: 0.45
- Applies scope discipline to defects found mid-round: a newly discovered bug that falls outside the agreed scope (e.g. a pre-existing build-phase `setState` bug surfaced while auditing the round's runtime logs) is to be reported with precise evidence — file:line, root-cause chain, proof it pre-dates the round (untouched file / introducing commit / first occurrence in the crash ledger), an existing in-repo pattern that fixes the same class of problem, and an explicit must-do vs optional rating — but NOT fixed silently; an explicit go-ahead is asked for first, because it is a new item beyond the round's three named tasks. Confidence: 0.5
- After reporting that he has retested on-device, expects the first step to be reading the newest runtime-log session and stating the log analysis (did the fix actually remove the target assertion/signature, which coverage probes newly fired, which new anomalies appeared) *before* any code is edited — the fix is executed only once that evidence is on the table, even when the change to make is already agreed ("我已再次复测，请你先分析一下日志再开始执行修复"). The analysis is also expected to end with an explicit verdict on whether the work may advance to the next phase/stage ("并判断是否能够继续后续阶段"). Confidence: 0.6
- When fixing a defect, expects a same-class sweep rather than a single-site patch ("同类站点统一排查 / 同类一次修完"): scan the whole codebase for the same structural pattern (e.g. every `if (index == ….length - 1) { loadMore() }` scroll trigger), verify each hit against the actual failure mechanism, fix every site that really has the defect, and leave the already-safe ones untouched — then report a per-site table with the verdict (已修 / 已安全) plus the evidence used to judge each one, and write that table into the retrospective doc and the commit body. Confidence: 0.6
- For dependency/migration rounds, prefers to lock the *exact* version that is behaviorally identical to what is currently frozen in the SDK (an exact pin, not a caret range — `material_ui: 1.0.0`, explicitly noting that `^1.0.0` would resolve to a newer, non-equivalent release), verify stability on that baseline first, and defer any feature upgrade to a separate, later round with its own snapshot and regression pass rather than jumping to the latest release in the same round. Confidence: 0.5
- Prefers interdependent work to be merged into a single round rather than sequenced as separate rounds (e.g. the SDK migration plus the component modernization that has to be redone on top of it), explicitly to avoid touching the same code twice and duplicating snapshots / builds / retrospectives. Confidence: 0.55
- Treats terminology/wording in the project's docs as something to keep consistent project-wide: a rename request ("将所有 X 改为 Y") is expected to be applied exhaustively to every occurrence — the retrospective docs, code comments, referenced document file names and the plan files under `~/.commandcode/plans/` — not just the one file first mentioned, with all hits enumerated before editing. Code comments are included, not just user-facing docs: when asked whether to also unify the in-code comments to the new wording he approves it (a bare "需要"), wanting the old term zeroed out across the codebase too ("静置" 字样全仓清零). Confidence: 0.5
- When comparing UI/visual design options, asks for an interactive single-file HTML demo that reproduces every candidate style (each with a manual trigger / static on-page preview) so the options can be seen and contrasted before any code is touched, rather than judging from written descriptions. Confidence: 0.5
- When presenting a plan with open choices, expects the decision points to be pre-answered with explicit defaults ("未批注则按默认执行") and the work to proceed on those defaults if he doesn't annotate them — he approves the plan and lets it run rather than answering each choice, so blocking on per-decision confirmation is unwanted. - For large mechanical/consistency sweeps (bulk conversions touching many call sites, e.g. ~50 `IconData` → widget sites), expects the work delivered incrementally in small per-component steps ("逐部件小步") with each part verified as it goes, rather than as one sweeping change. Confidence: 0.45
- Reviews a presented plan by annotating individual lines with corrections and expects every annotation to be addressed exhaustively: the plan file is rewritten in place at the same path (bumping its revision and adding a "本轮批注落实" summary at the top) and then re-presented for another review round — none of the comments may be dropped or merely acknowledged in chat. Confidence: 0.45
- Treats the upstream reference projects (PiliPlus, BiliPai) as the source of project *infrastructure* too, not just of code behavior: asks for their GitHub Actions workflows to be brought over and rewritten to fit this project ("补齐上游 piliplus 所用的对本项目可用的工作流 action，以及 bilipai 工作流，并修改为对本项目适用"), with each upstream workflow judged for whether it applies here and the reason recorded per file (e.g. skipping the upstream `sync-upstream` workflow because this repo is not a GitHub fork), and unchanged upstream conventions (action versions, packaging/artifact naming, draft-then-publish release flow, checksum evidence) adopted rather than reinvented. Confidence: 0.45
- Treats end-user distribution/packaging as part of the deliverable, not just the build: for Windows he expects a *modern installer* to be found and designed (not merely a portable zip / raw build output), and explicitly wants the code-signing question assessed alongside it ("寻找并设计一个现代化的安装器，以及是否需要注意安装器签名问题") — i.e. the signing/trust implications (SmartScreen, certificate options) should be researched and laid out as part of the plan rather than discovered at release time. Confidence: 0.4
- Judges a packaging/installer deliverable by the *whole lifecycle*, not just the fresh install: after the agent enumerated an installer's advanced capabilities he extended the requirement himself ("还需要覆盖更新时能提前探测到已安装的路径的能力") — i.e. in-place update must detect the previously installed path/version ahead of time (explicit `UsePreviousAppDir`/`UsePreviousTasks`-style inheritance plus a self-owned, queryable registry anchor) so an upgrade lands in the existing location instead of the default one, and the upgrade chain (install → re-run to upgrade → uninstall) is expected to be actually exercised rather than assumed. Confidence: 0.45
- Periodically asks for a scope review beyond the current target platform, wanting the feasibility of other platforms to be laid out and tiered (clear second-platform candidate / later candidate / not worth doing) instead of a flat yes/no — grounded in per-dependency platform support, which platform-specific code paths would have to be replaced, and the project/packaging work each platform needs. Confidence: 0.4
- Once a researched hardening/process option is shown to be unnecessary, prefers to drop it from scope entirely rather than keep a dormant/optional implementation path: after the installer-signing research confirmed the upstream reference project ships unsigned, he decided to abandon installer code signing and have it removed from the plan and the CI/pipeline, retaining the research only as a written decision record (动机/选项/决策 documented in `docs/`). Favors matching the upstream project's actual shipping practice over adding best-practice process it does not follow. Confidence: 0.4
- Names CI/CD workflow files and their `name:` fields so the target OS and architecture are explicit (e.g. `windows-x64-ci.yml` with `name: CI（Windows x64）`, `windows-x64-release.yml` with `name: Release（Windows x64）`), rather than generic `ci.yml` / `release.yml` — and after such a rename expects every downstream reference (docs, plan) synced to the new names. Confidence: 0.5
- Wants quality gates kept strict rather than relaxed to tolerate pre-existing issues: when a deviation was recorded because existing lints forced a tolerance flag (e.g. `flutter analyze --no-fatal-infos` for 6 repo-wide info-level lints), he directs that the deviations be "完善" — the underlying issues actually fixed (all lints cleared, installer warnings zeroed, `.gitignore` entries completed) and the gate restored to its strict form (`flutter analyze` with no flag) — a recorded accepted-exception is for him a to-do, not a standing tolerance. Confidence: 0.5
- Reassesses cloud CI/CD scope and drops automation that has stopped earning its place: he directed that the upstream-derived `windows-x64-ci.yml` quality gate be removed outright ("去除CI（Windows x64）工作流") and only the release workflow kept, once cloud-only environment drift (local pub mirror vs runner's pub.dev) kept breaking it and the local analyze / test / debug+release-build chain already covered the same ground — i.e. a previously wanted cloud workflow can later be cut, not just added. Confidence: 0.4
- For a library/design-language migration, mandates (and expects enforced) a strict retirement ordering rather than ripping out the old path as each piece is migrated: first add the new library's branch to every control that only has the legacy path → confirm tests pass → only then detach that control from the legacy path → and remove the legacy library and its style definitions only after the entire project no longer references them ("先给只有 X 的控件补 Y 分支 → 测试无异常 → 再脱离 X；全项目不再引用 X 后才统一移除 X 库与样式定义"). The existing dual-style switch must stay usable throughout (the user can still toggle styles until the removal point), so the layered plan (delete frozen branches → freeze tokens → converge icon mapping → enums/entries/test baseline last) is sequenced with the legacy path kept live as long as any reference remains. Confidence: 0.5
