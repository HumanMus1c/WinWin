# Workflow preferences

- Takes a pre-change git snapshot before making changes (project convention: `git add -A; git stash create` → `git update-ref refs/snapshots/latest`), one snapshot per change round, so each round has an independent rollback point restored via `git reset --hard <SHA>`. Confidence: 0.7
- Verifies changes with a full `dart analyze` targeting 0 error / 0 warning and no newly introduced issues, plus both `flutter build windows --debug` and `--release`, before committing — but scoped to what the change actually touches: build validation belongs only to changes affecting *build inputs* (Dart/Flutter code, `windows/` resources, `pubspec`, etc.), while doc-only changes (README, `docs/`, plan files and other non-build files) are explicitly exempt from build verification to avoid pointless work ("避免多此一举"). The pre-change snapshot and post-change commit/push still run as usual in both cases — i.e. verification effort should be proportional to the change's blast radius rather than applied ritualistically. Confidence: 0.65
- Writes a retrospective ("复盘") markdown doc into `docs/` for each change, structured by five elements (根因 / 方案 / 验证 / 总结 / 提交与回滚) with rollback SHAs and a manual on-device verification checklist. Confidence: 0.6
- Batches git pushes: commits locally throughout the work, then pushes to `origin/main` once at the end of the session ("推送按惯例在会话末尾统一执行"). Confidence: 0.6
- For multi-round work, records a plan file under `~/.commandcode/plans` named `{主题}计划-YYYY-MM-DD.md` (background/conclusion → decision → numbered execution steps → rollback → status checklist), surfaces it in the Plans panel for approval, and rewrites the status checklist and execution results as the round progresses; tracks steps with a todo list. Confidence: 0.6
- Executes approved changes step by step, in priority order, returning to the user for confirmation before starting. Confidence: 0.5
- Wants generated artifacts surfaced in the OS file explorer (open Explorer and select the file via `explorer.exe /select,"<path>"`) rather than only reported as a text path. Confidence: 0.45
- Applies scope discipline to defects found mid-round: a newly discovered bug that falls outside the agreed scope (e.g. a pre-existing build-phase `setState` bug surfaced while auditing the round's runtime logs) is to be reported with precise evidence — file:line, root-cause chain, proof it pre-dates the round (untouched file / introducing commit / first occurrence in the crash ledger), an existing in-repo pattern that fixes the same class of problem, and an explicit must-do vs optional rating — but NOT fixed silently; an explicit go-ahead is asked for first, because it is a new item beyond the round's three named tasks. Confidence: 0.5
- After reporting that he has retested on-device, expects the first step to be reading the newest runtime-log session and stating the log analysis (did the fix actually remove the target assertion/signature, which coverage probes newly fired, which new anomalies appeared) *before* any code is edited — the fix is executed only once that evidence is on the table, even when the change to make is already agreed ("我已再次复测，请你先分析一下日志再开始执行修复"). The analysis is also expected to end with an explicit verdict on whether the work may advance to the next phase/stage ("并判断是否能够继续后续阶段"); he restates the whole convention tersely in later rounds ("已复测，请分析日志，继续推进") — retest first, then analyze logs, then advance. Confidence: 0.65
- When fixing a defect, expects a same-class sweep rather than a single-site patch ("同类站点统一排查 / 同类一次修完"): scan the whole codebase for the same structural pattern (e.g. every `if (index == ….length - 1) { loadMore() }` scroll trigger), verify each hit against the actual failure mechanism, fix every site that really has the defect, and leave the already-safe ones untouched — then report a per-site table with the verdict (已修 / 已安全) plus the evidence used to judge each one, and write that table into the retrospective doc and the commit body. Confidence: 0.6
- Builds a sweep's coverage list from the *actual render path*, not from the shared component: a page that reimplements the same feature locally must still be counted. When the first pass of the send-button convergence touched the shared comment bar and the bangumi page but not `detail_page.dart` (which has its own `_buildCommentInputBar`), he came back with "视频播放页的评论发送按钮和弹幕发送按钮似乎没有调整"; the accepted root cause is that "同功能输入栏存在自有实现 ≠ 共享组件——批量清单必须以实际渲染路径为准", and the fix covers it plus a re-audit of all render sites, with the pitfall written into the retrospective. Confidence: 0.55
- For dependency/migration rounds, prefers to lock the *exact* version that is behaviorally identical to what is currently frozen in the SDK (an exact pin, not a caret range — `material_ui: 1.0.0`, explicitly noting that `^1.0.0` would resolve to a newer, non-equivalent release), verify stability on that baseline first, and defer any feature upgrade to a separate, later round with its own snapshot and regression pass rather than jumping to the latest release in the same round. Confidence: 0.5
- Prefers interdependent work to be merged into a single round rather than sequenced as separate rounds (e.g. the SDK migration plus the component modernization that has to be redone on top of it), explicitly to avoid touching the same code twice and duplicating snapshots / builds / retrospectives. Confidence: 0.55
- Treats terminology/wording in the project's docs as something to keep consistent project-wide: a rename request ("将所有 X 改为 Y") is expected to be applied exhaustively to every occurrence — the retrospective docs, code comments, referenced document file names and the plan files under `~/.commandcode/plans/` — not just the one file first mentioned, with all hits enumerated before editing. Code comments are included, not just user-facing docs: when asked whether to also unify the in-code comments to the new wording he approves it (a bare "需要"), wanting the old term zeroed out across the codebase too ("静置" 字样全仓清零). Confidence: 0.5
- When comparing UI/visual design options, asks for an interactive single-file HTML demo that reproduces every candidate style (each with a manual trigger / static on-page preview) so the options can be seen and contrasted before any code is touched, rather than judging from written descriptions. Confidence: 0.5
- When presenting a plan with open choices, expects the decision points to be pre-answered with explicit defaults ("未批注则按默认执行") and the work to proceed on those defaults if he doesn't annotate them — he approves the plan and lets it run rather than answering each choice, so blocking on per-decision confirmation is unwanted. Favors matching the upstream project's actual shipping practice over adding best-practice process it does not follow. Confidence: 0.4
- Names CI/CD workflow files and their `name:` fields so the target OS and architecture are explicit (e.g. `windows-x64-ci.yml` with `name: CI（Windows x64）`, `windows-x64-release.yml` with `name: Release（Windows x64）`), rather than generic `ci.yml` / `release.yml` — and after such a rename expects every downstream reference (docs, plan) synced to the new names. Confidence: 0.5
- Wants quality gates kept strict rather than relaxed to tolerate pre-existing issues: when a deviation was recorded because existing lints forced a tolerance flag (e.g. `flutter analyze --no-fatal-infos` for 6 repo-wide info-level lints), he directs that the deviations be "完善" — the underlying issues actually fixed (all lints cleared, installer warnings zeroed, `.gitignore` entries completed) and the gate restored to its strict form (`flutter analyze` with no flag) — a recorded accepted-exception is for him a to-do, not a standing tolerance. Confidence: 0.4
- For a library/design-language migration, mandates (and expects enforced) a strict retirement ordering rather than ripping out the old path as each piece is migrated: first add the new library's branch to every control that only has the legacy path → confirm tests pass → only then detach that control from the legacy path → and remove the legacy library and its style definitions only after the entire project no longer references them ("先给只有 X 的控件补 Y 分支 → 测试无异常 → 再脱离 X；全项目不再引用 X 后才统一移除 X 库与样式定义"). - For a multi-batch stage/mini-phase, wants a dedicated progress-tracking document (e.g. `docs/<主题>-进度追踪-YYYY-MM-DD.md`) that records the implementation progress of *every* phase in the stage, and mandates that it be shown to him at the start AND end of each phase (an explicit "每个阶段开始和结束时展示" convention, stated as a standing rule: "将本L阶段的所有阶段的实现进度写入文档，并在每个阶段开始和结束时向我展示"). The doc is updated and pushed as each batch lands, back-filling the batch's commit hash, net line count and verification results, and the progress table is re-presented in chat at both boundaries. Confidence: 0.55
- Wants that progress-tracking document to record each batch's *change details*, not just a one-line summary: he reads the batch log himself and calls out entries that only carry a摘要 ("L1-1…L1-4 这几次改动的细节内容没有写出来？"), so every batch entry must spell out the concrete five-part breakdown — 范围明细 (each file/control/门控 touched and what was removed), 关键删除项 (the actual deleted code: styles, magic values, helper functions, imports), 验证 results, 过程记录 (problems hit and how they were fixed), and 实机状态 (on-device verification status). He expects missing per-batch detail to be backfilled into the existing document retroactively (rewriting the log structurally), and the "改动细节" requirement then folded into the doc's standing 展示约定 so later batches are held to it. Confidence: 0.6
- Wants release versioning modeled as two independent numbers with a "version name may hold or even downgrade, version code must only ever increase" discipline — version code is a positive integer allocated as the global-history maximum + 1 (never written by hand), while the semantic version name is free to be reused/rolled back for re-releases and hotfixes. The stated reason is future-proofing for platform version sensitivity: Android refuses downgrade installs (`INSTALL_FAILED_VERSION_DOWNGRADE`), iOS rejects repeated/reverted build numbers, and Linux deb/rpm downgrades need special flags — so even when rebuilding from an older commit the code must exceed every past value to remain overwrite-installable. He further wants the version code to embed the build date (a date-coded integer such as `261006` for 2026-10-06, plus a same-day sequence suffix so repeat builds within one day still increase), so every build self-reports its compile date while staying strictly greater than all past codes. Confidence: 0.55
- Treats a plan/design that is still under discussion as a hard freeze on the project: while the scheme is unsettled he directs that the project itself not be touched ("目前还在设计阶段，暂不改动项目"), expects the plan file to carry an explicit stage statement to that effect ("设计讨论中 —— 方案定稿前不改动项目任何文件"), and only starts implementation once a definite scheme is agreed ("待讨论出确定方案再考虑变更"). Incidental cleanups spotted along the way (e.g. a stale hardcoded version string on the about page) are deferred rather than fixed opportunistically. Confidence: 0.5
- When a format/scheme is being designed, expects the design space to be surveyed against mainstream industry conventions and returned as ranked options with trade-offs so he can pick — e.g. for version names he asked what the common dot-separated `0.1.0` versus release-date-aligned `2026.10.06` styles are, whether a fourth segment is viable, and "how else can it be designed?", rather than being handed one recommendation. Confidence: 0.45
